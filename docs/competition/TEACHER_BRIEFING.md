# MAOEH 指导老师汇报材料（TEACHER_BRIEFING）

- 汇报日期：2026-11-15
- 材料基准：2026-11-14 夜间核实的源码、运行进程、真实浏览器操作与全量门禁
- 一句话：**MAOEH 是一个“能被审计的 AI 公司”——它不只让 AI 干活，还让每一步决策、每一次协作、每一个交付都能从事件日志里还原。**

---

## 1. 项目定位与参赛赛道

**定位**：多 Agent 组织仿真平台（Multi-Agent Organizational Emulation Hub）。不是聊天机器人，不是工作流自动化工具，而是把“一家公司怎么运转”变成可运行、可观察、可回放的系统：

- 有组织图：部门、岗位、汇报线、权威等级；
- 有员工：身份、职责、能力、权限、记忆策略、通信规则；
- 有流程：任务书 → 能力路由 → 工作流 → 交付物；
- 有治理：权限、审批、升级、拒绝；
- 有记忆：一切状态由**事件日志**推导，可回放、可审计。

**赛道**：人工智能应用 / 多智能体系统方向（以省赛正式通知为准）。

**与常见方案的区别**

| 常见做法 | MAOEH |
| --- | --- |
| 多个 LLM 角色互相聊天 | 角色是组织里的**岗位**，受组织图和权限约束 |
| 编排框架里画流程图 | 流程是**工作流定义 + 事件**，可回放、可审计 |
| 结果是一段对话 | 结果是**可运行的交付物**（真实起服务、真实 URL） |
| 出问题只能翻日志 | 能回答“谁、为什么、被谁批准/拒绝” |

## 2. 当前已经实现的能力（都有源码或运行证据）

1. **组织与权限**：7 个 AI 员工、15 个岗位、5 个部门；岗位权威与决策域参与真实授权；日志中有被拒绝的控制命令。
2. **完整认知执行链**：唤醒 → 上下文 → 真实模型 → 计划（≤8 步）→ 执行 → 领域事件 → 状态回写；每个周期有 `Runtime.CycleStarted/Finished` 与 `correlationId / causationId`。
3. **真实双 Agent 协作**：架构师遇到不能独立完成的设计问题 → 主动给工程师发消息请教 → 工程师给出具体方案 → 架构师采纳并提交 → 任务完成。两次独立运行均闭环。
4. **真实多平台文案生成（一鱼多吃）**：一份素材 → 小红书 / 抖音 / B站 / 公众号各一次真实模型调用，四平台格式与长度不同；页面标注生成方式（LLM/模型/调用次数），可编辑、审核、导出。
5. **真实四角色对抗质询（赛博沙盘）**：提案 / 质询 / 答辩 / 评审四个真实 Agent 逐轮发言，每条都是真实消息事件；评审给出带 `messageId` 的引用式评分；会话可保存回看。
6. **交付物预览运行时**：交付的 Python / Node 项目复制到隔离目录、真实启动子进程、动态端口，页面里打开的是真 URL。
7. **控制面与可观测**：暂停/恢复/指示/审批/注入任务/重分配；`/api/snapshot`、`/api/communications`、`/api/events`、`/api/runtime`、`/api/llm`；前端 2.5s 轮询。
8. **工程门禁**：53 个 typecheck 任务、33 个构建任务、173 个测试文件、1254 个测试、架构依赖规则、ESLint。

## 3. 当前存在的真实不足（不回避）

1. **图片、音频、视频生成未实现**：当前只有文本模型接入；一鱼多吃只做到图文文案，不得声称已生成图片。
2. **沙盘只验证了 1 轮真实会话**（两次）：多轮稳定性、并发会话队列、评分解析失败重试尚未验证。
3. **7 个 Agent 的认知是同构的**：画像全部是 `exec-strategic`，共用同一个模型；差异来自岗位职责、能力标签与权限，不是推理风格。
4. **“协商”仍未真实复跑**：`RequestCollaboration` 已加入动作空间、`buildPlan` 不再拒绝、提示词给出契约，但还没让真实模型自主选过它。
5. **实现类交付断言偏松**：赛博沙盘的历史任务 `task-44` 只交了实现报告也标记完成（旧账）；收紧规则是下一阶段的质量任务。
6. **协作剧场缺时间线**：Communications 页能看消息与协作请求，但没有把“任务交接 + 关键决策”按 correlation 聚合成一条时间线。
7. **频道成员不随招聘更新**：运行中再招人不会自动进入公司频道，需要 `Channel.MembersChanged` 类事件。
8. **旧人工沙盘页仅作历史存证**：已归档、不再由 Web 提供，见 §8。

## 4. 本次新增的真实成果

### 4.1 修复“通信已实现却从不发生”的三处断点

审计发现演示公司 79,557 条事件里 `Communication.*` 为 **0**。不是模块缺失，而是三处断点：

| 断点 | 修复 |
| --- | --- |
| 公司频道在日志重放**之前**创建，starter 公司当时只有 1 名员工（低于频道最小成员数 2），静默失败 | 改为先 `recover()` 再组建公司 |
| 认知提示词没有 `channelId`、没有消息契约，真实模型写不出合法 `SendMessage` | 新增 `## Communication` 段（频道、成员、最近消息、参数契约、何时该发/不该发） |
| 运行中的进程是旧构建，新代码没被加载 | 用新构建重启，并修正了 turbo 缓存误报的流程 |

修复后演示公司日志真实写入 `Communication.ChannelOpened`（7 名成员）。

### 4.2 真实双 Agent 协作（两次独立运行，因果链完整）

隔离实例、独立事件日志、真实 DeepSeek：

```
t1 cto-john 接任务 → 发 request 给 engineer-mike     causationId = Task.Assigned 事件
t2 engineer-mike 回 response（含具体方案）            causationId = request 消息事件
t3 cto-john 采纳并提交 → Task.Completed              causationId = response 消息事件
```

机器判定两次均 6/6 true；任务生命周期 `Created → Assigned → Accepted → Started → ProgressReported → Completed`；全程同一 `correlationId`。演示公司日志未被污染（仍只有 1 条频道事件）。

**过程不是一次成功**：第一次运行 CTO 在 `accepted` 状态直接提交，被任务状态机以 `invalid_transition` 拒绝 4 次。修复方式是把“当前状态允许哪些命令”由内核注入提示词（数据来自任务状态机本身），复跑即闭环。

### 4.3 一鱼多吃：从模板变成真实 LLM 生成

审计证据：原交付看板里四个平台的文案是前端 `generateAssets()` 里写死的字符串，只把素材前 60 字拼进去，没有一次模型调用。

新增 `/api/studio` + `/api/content/generate`：一份素材，逐平台构造格式契约，每个平台一次真实调用；页面显示 `LLM · deepseek / deepseek-flash · 4 次调用`，mock 模式显示`模板 · mock`。

浏览器实跑：四平台文案长度 443/341/468/821 字（历史证据），两两 4-gram 最大重合度 ≤ 0.098；页面内完成**编辑 → 通过审核（1/4）→ 导出 JSON（含编辑与审核状态）**。

### 4.4 赛博沙盘：从人工外壳变成真实四角色质询

审计时它是**人工逐条输入、人工切换角色**的演示页，评分由前端按字数与关键词计算。现在：

- `/api/sandbox` 工作台：输入议题 → 选回合 → 真实开跑；
- 角色按岗位能力从真实组织选座（CTO John 提案、QA Peter 质询、工程师 Mike 答辩、CEO Alex 评审）；
- 每条发言经 `CommunicationService` 授权、成员校验、写入事件日志并真实投递；
- 评审返回 JSON，每维度带 `evidence + messageId`；解析器校验 id 必须真实存在；
- 会话跑在**独立运行时与独立事件日志**，不写演示公司日志；
- 会话索引 + 事件日志，`GET /api/sandbox/sessions[/:id]` 可回看。

**真实浏览器操作**（headless Edge + CDP，真实点击）：4 角色 / 4 条消息 / 评分 **78/100** / **4 条评分全部引用具体消息** / 历史会话回看正常；截图在 `.maoeh/audit/browser/run-2026-11-14T12-33-58-538Z/screenshots/`。

## 5. 技术架构与核心创新点

### 5.1 架构（六层，依赖单向）

```
apps/web        控制台（React，2.5s 轮询读模型；沙盘入口指向 API 工作台）
apps/api        组合根 + HTTP（snapshot / command / events / preview / studio / sandbox）
apps/kernel     运行时：调度、唤醒、认知循环、计划执行、恢复
packages/       agent-*（认知/运行时/通信/定义/记忆）
                organization-*（组织模型/控制面/权威/权限）
                workflow-* / task-* / event-*（流程、任务、事件）
apps/projector  读模型投影
```

自动化测试守护的约束：`packages/*` 不依赖 `apps/*`；`apps/web` 不依赖后端包；只有 `llm-gateway` 接触模型 provider；`agent-runtime` 不引用提示词；事件机制不依赖持久化实现。

### 5.2 三个核心创新点

1. **组织即权限，权限即事件**：授权不是提示词里的“你是 CTO”，而是 `action × resource × 权威等级` 的真实判定；拒绝会写进日志。
2. **一切状态由事件推导**：任务、工作流、频道、协作请求、Agent 状态全部从日志重放；重启不丢历史，演示可复盘。
3. **协作是运行时的一等公民**：消息不是 UI 效果——`Communication.MessageSent` 会唤醒收件人、产生投递记录、进入同一 `correlationId` 因果链。

## 6. 两个应用样板的价值与现状

### 一鱼多吃（内容团队）

- **问题**：一份长素材要改写成多个平台的原生内容，人工成本高，平台差异难保证。
- **做法**：不是“一次生成再复制”，而是**每平台一份格式契约 + 一次独立生成**，并把生成方式（LLM/模板、模型名、调用次数）标在页面上。
- **价值**：可审核、可修改、可导出、可追溯。
- **现状**：图文链路真实可用；图片/音频/视频未做。

### 赛博沙盘（多角色对抗质询）

- **问题**：方案需要被多角色挑错，人工组织成本高且容易同质化。
- **做法**：四个真实岗位 Agent 在同一频道逐轮发言，评审给出带依据的结构化评分，transcript 与分数全部来自事件日志。
- **价值**：把“评审会”变成可复用、可追溯、可量化的组织能力；与双 Agent 协作共用同一套通信与事件引擎。
- **现状**：1 轮真实会话已用浏览器完整操作并验证（78 分、4/4 引用）；多轮与并发仍是待办。

## 11. 可能的提问与回答

**Q：这不就是多 Agent 框架吗？**
A：框架解决“怎么调用模型”，我们解决“一个组织怎么运转并可审计”：岗位权限、审批、任务书、事件溯源、交付物运行。

**Q：怎么证明不是写死的？**
A：消息有 `causationId` 指向上一条事件；任务状态由 `Task.*` 逐步推导；隔离验证脚本每次产生新 eventId 与新模型输出；沙盘评分里的 `messageId` 会被校验必须真实存在。

**Q：沙盘会话是不是绕过了 Agent Runtime？**
A：是部分绕过，我们主动说清楚：发言顺序由会话编排器驱动，不是内核 tick 唤醒；但角色、身份、岗位、职责来自真实组织，每条发言经真实 `CommunicationService` 授权并写入事件日志。用独立运行时是因为把会话消息注进演示公司会唤醒公司 Agent、产生第二轮非脚本对话。

**Q：旧的那个沙盘页面还能用吗？**
A：不能作为产品使用；它已归档，不再由 Web 提供，应用里也没有入口。它只是历史存证：人工输入、前端计数评分，不是 AI 质询。

**Q：图片/音视频呢？**
A：未实现，只有文本模型接入。一鱼多吃目前是图文链路；不会把模板或占位说成生成。

**Q：成本和延迟？**
A：四平台生成 4 次调用约 24s；双 Agent 协作 3 个认知周期约 6 次调用；沙盘 1 轮 4 次调用约 11–15s。全部经统一网关计数，`/api/llm` 可查。

**Q：数据安全？**
A：密钥只在服务端；页面与日志都不出现；生成页面同源调用 API；事件日志不含密钥。沙盘与协作验证都在隔离日志里，演示公司日志未被会话污染。

**Q：为什么不用 SSE/WebSocket？**
