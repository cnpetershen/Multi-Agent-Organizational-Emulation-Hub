# M1.4 · Deliverables Page — Verification Report

> Milestone: **M1.4 — Deliverables (CEO Workspace)**
> A new console page for the *end user / CEO*: several AI-employee tasks side by side, the
> three states that matter (**Running / Need action / Completed**), and — on opening a task —
> the delivery the organization actually produced (execution summary, generated deliverables,
> documents, acceptance).
>
> It is **not** a monitoring page: no company run statistics, no agent roster, no agent ids,
> no ticks, no runtime state, no events, no workflow trace, no debug payloads.

Gates: `pnpm lint` · `pnpm typecheck` · `pnpm test` · `pnpm architecture:check` · `pnpm build` ·
`pnpm test:e2e` — **all PASS** (§5).

**Verdict: M1.4 Deliverables page = PASS** (§8).

## 2. What Changed

### 2.1 Read model (`packages/organization-control`, `apps/api`)

| File | Change |
|------|--------|
| `src/types.ts` | **New** `TaskResultView` (`taskId`, `producedBy`, `summary`, `data`, `artifacts`); `TaskView` gains `result: TaskResultView \| null`. |
| `src/query.ts` | `taskView()` projects `task.result` (frozen data/artifacts copies). The **list** projection (`TaskSummary`, used by `/api/snapshot` and `/api/tasks`) deliberately stays lean: `result` and `goal` are only on the record read. |
| `apps/api/src/api-adapter.ts` | **New** `GET /api/tasks/:id` — the by-id counterpart of the task list, mirroring the M1.3 `GET /api/agents/:id` precedent. `200` with the `TaskView`; `404 {"error":"unknown task \"…\""}` otherwise. |

Why a record endpoint instead of widening the poll payload: the console re-reads the snapshot
every 2.5 s for every page. Delivering every task's full work product on every poll would put
the whole delivery content on the operator's critical path for a view that renders one task at a
time. The split is pinned by a test (§4.1 "keeps the list projection lean").

### 2.2 Console (`apps/web/src`)

| File | Role |
|------|------|

| `api.ts` | **New** `TaskRecord` / `TaskResultView` contracts and `parseTaskRecord()`: the record parser names the exact path of the first field the view cannot render (the console's existing discipline — a bad payload is an error, never a default). |

## 3. API Reference

### 3.1 New read

| Endpoint | Purpose | Notes |
|---|---|---|
| `GET /api/tasks/:id` | **new** — read one task record | `200` with `TaskView` (`goal`, `detail`, `outputs`, `result`, `reviews`, `verification`, …); `404 {"error":"unknown task \"…\""}` otherwise. The list (`/api/tasks`, `/api/snapshot.tasks`) still answers `TaskSummary`. |

### 3.2 The record the result view renders

```jsonc
{
  "taskId": "task-1",
  "title": "Define analysis brief",
  "status": "completed",
  "goal": "Complete step \"Define analysis brief\" of workflow \"Board directive\"",
  "detail": null,
  "positionId": "ceo",
  "workflowInstanceId": "instance-1",
  "outputs": [],
  "result": {
    "taskId": "task-1",
    "producedBy": "ceo-alex",
    "summary": "work complete",
    "data": {
      "problem": "churn is rising among the first cohort",
      "success_criteria": "root causes identified and ranked",
      "approach": "phased rollout behind a feature flag",
      "risks": ["capacity", "migration window"],
      "recommendation": "ship the analysis and start the pilot"
    },
    "artifacts": []
  },
  "reviews": [],
  "verification": { "kind": "deterministic", "requiredOutputKeys": ["problem", "recommendation"] }
}
```

Every field above is produced by the existing domain path (`TaskService.submit` → task fold →
`ControlQuery.getTask`); nothing is synthesized for the page.

## 6. Constraints and Locked Decisions Honored

* **No new architecture.** No new package, action, command, event, aggregate, state machine,
  wakeup source or permission. The change is one read-model field, one HTTP read route, one page
  and its copy.
* **The PROPOSED M1.4 design is not implemented.** `ARCHITECTURE-BASELINE.md` §17 requires an
  accepted ADR before `ACTIONS`/`Control` may grow; that design remains `PROPOSED` and untouched.
  This page reads facts the runtime already produces.
* **CEO view, not a monitoring console.** Company statistics, the agent roster, agent ids, ticks,
  runtime state, events, workflow traces and debug payloads are absent from the page — they stay
  on Overview / Agents / Runtime / Workflows / Events, where they belong. The **shared shell
  header** (connection status, runtime state, `Tick n`, Refresh) is global chrome rendered on all
  nine pages and is deliberately unchanged: hiding it on one page would fork the shell instead of
  the page.
* **Nothing is fabricated.** Every value on the page comes from an API payload: an unsubmitted
  task reads "Nothing has been delivered yet"; a payload the parser cannot render is a visible
  error naming the field, never a blank cell.
* **Role, not person.** Cards show the responsible *position*; the result shows the delivering
  *position*. Agent ids are carried on the wire (the API is unchanged in that respect) but never
  rendered.
* **Design system reused.** Cards, panels, pills, detail grids, objective blocks, notices,
  filters and spacing come from the existing components and `phase1` tokens; a locale switch
  cannot change a status colour (`tone` is fixed per state, labels are translated).
* **Full i18n.** 58 new keys in each locale; parity, placeholder and translation tests make a
  half-translated key a test failure rather than a blank cell.

## 7. Known Limitations and Follow-ups

* **Deliverable keys are data, not copy.** `result.data` keys (`problem`, `recommendation`, …)
  come from the executor's submission and render verbatim in both locales, exactly like API enum
  tokens elsewhere in the console. Localizing them would require a schema for work products,
  which the domain does not have yet.
* **Artifacts are references.** `result.artifacts` / `outputs` are artifact ids; the
  `artifact-system` store is not exposed over HTTP, so the page lists the references rather than
  fetching documents. A document viewer belongs to a later milestone (and to the
  `knowledge-system` / `artifact-system` read path).
* **No task-brief grouping yet.** This page shows tasks; grouping several work items under one
  human brief needs the `correlationId` read model of the PROPOSED M1.4 design (§5.4 of the design
  document). Until that is accepted, tasks are listed individually.
* **Completed includes cancelled.** The three states are the specified ones; a cancelled task sits
  in Completed and keeps its own "Cancelled" label rather than inventing a fourth state.
* **`n of m steps` is the workflow's own step progress.** For a standalone task (no workflow) the
  card says so explicitly instead of showing a fake stage.

**M1.4 Deliverables page = PASS.** All eight specified behaviours are implemented on the real

four levels (control-plane unit, HTTP chain, console unit/i18n, real-browser E2E), all six gates
