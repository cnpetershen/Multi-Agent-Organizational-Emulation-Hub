## 2. 本轮交付

### 2.1 能力词表：`frontend` / `backend`，回退链改为常量（`organization-model/capability/vocabulary.ts`）

- 新增 `frontend`（frontend / web / website / page / ui / 前端 / 官网 / 网站 / 网页 / 页面）与
  `backend`（backend / api / server / service / database / 后端 / 服务端 / 接口 / 数据库），
  英文线索按**词边界**、中文按**子串**，与既有条目同规则。
- `CORE_CAPABILITIES` 从「词表减去 marketing」改成**写死的交付弧四项**。词表是开放且会继续增长的，
  新增一个专精标签不得悄悄改变含糊指令所排的工作。
- 结果：`requiredCapabilitiesFor('开发一个官网') === ['implementation','frontend']`；
  `做前端页面 → ['frontend']`；`搭建后端服务 → ['backend']`。
- 种子岗位同步声明：`engineer` = `implementation, frontend, backend`（全栈），
  `frontend-engineer` = `+frontend`，`backend-engineer` = `+backend`。**岗位名不参与匹配**这一条不变。

> **设计边界**：`engineer` 声明 `frontend/backend` 是「这个坑提供什么能力」，不是「名字听起来像什么」。
> 匹配仍然是 id 精确比较；换一个叫「Game Developer」的坑，只要声明 `implementation` 就同样可被派活。

### 2.2 个人专长 `Employee.expertise`（模型 + 加载 + 匹配）

- `Employee.expertise?: readonly string[]`：与 `Position.capabilities` **正交**的第二层能力——
  座席说「这个坑归谁干」，专长说「这个人特别擅长什么」。
- 加载边界统一归一化（trim / 小写 / 去重 / 保序，`load-organization.ts` 的 `normalizeTags`），
  种子 YAML 与运行期创建两条路径结果一致。
- `CapabilityProfile.expertise` 暴露它；`buildCapabilityProfiles` 仍是从组织**派生**、不落库。
- `matchCapabilityCandidates` 变成**双路线**：
  1. 座席路线（既有，含空坑升迁）；
  2. 专长路线（person-level，**只扩大候选场，不参与升迁**）。
  `matchedCapabilities` 恒按**需求顺序**输出；新增 `expertiseMatched` 记录哪些能力靠个人专长覆盖。
  **评分公式未变**：`覆盖数 × 10 + 部门匹配 5`——覆盖率决定分数，与「哪条路线」无关。
- 种子专长（细粒度，故意避开词表 id）：Mike `typescript/react/node/frontend/backend`、
  John `architecture/systems_design/code_review`、Peter `testing/automation/playwright`、
  Jack `marketing/seo/copywriting/customer_research`、Bona `product_requirement/ux_research/roadmapping`、
  Alex `strategy/org_design/capital_allocation`。

## 5. 已知限制与有意延后

1. **专长是自由文本，不是受控词表**：`typescript` 与 `ts` 是两回事；控制台对未知标签原样显示。
   要收敛需要别名表，本阶段不做——先让组织能声明，再谈规范化。
2. **专长不参与空坑升迁**（有意）：升迁表达组织层级，专长表达个人能力；混在一起会让「为什么是他」无法解释。
3. **前端创建表单暂不接受 expertise 输入**：缺省时**仅当模板正是该坑现任**才继承其专长（跨坑的结构模板不继承），UI 保持轻量。
   命令层已支持，控制台要开口只需加一个输入框。
4. **专长标签统一小写**（加载与创建两条路径都归一化），显示时不还原原始大小写。

## 7. 追补修复：能力工作流在「同一坑位存在离职记录」时死锁（2026-10-05）

> 本节的 bug **不在 M1.6 交付范围内**，但它恰好只在真实控制台流程（`Start Work` → 持锁 → 等闸门）
> 上暴露：全量测试的种子组织没有「同坑双人记录」，所以四门 gate 全绿也没能拦住它。
> 记录在此，是因为触发路径正是本轮引入的「能力 → 生成工作流 → 逐坑推进」。

### 7.1 现象

控制台上点 `Start Work` 后，操作员循环持锁最多 `MAX_STEPS_TO_GATE = 24` 步轮询 `open` 闸门，
24 步耗尽仍无闸门 → 报 **「未出现审批闸门：运行时在 24 步后已释放」**。
（`apps/web/src/pages/Overview.tsx` 的 `stepToGate`，以及 `tests/e2e/console-loop.mjs`。）

### 7.2 根因（真死锁，不是用例抖动）

工作流按能力生成：每个能力一个 `stage`，末尾一个 `approval` 阶段（`stage-approve`）。
第 3 个 stage 的目标坑位是 `qa`。`WorkflowEngine.preflightStep` 用
`OrgGraph.resolveByPosition('qa')` 取「谁坐在这个坑上」，而当时的实现是**取第一个匹配的
employee 记录，完全不看雇佣状态**：

```ts
// 修复前
return organization.employees.find((e) => e.positionId === positionId) ?? null;
```

`peter-ai-lab` 的真实事件日志里，`qa` / `cto` / `engineer` 三个坑位**各自都先是一条
`offboarded` 记录、后面才是在岗者**——这是 M1.3 re-hire 的必然结果：
*辞退是状态变更、不是删除*（`Agent.Archive`），旧记录仍指向原坑位。于是
`resolveByPosition('qa')` 返回的是已离职的 `mack`，preflight 以
`employee "mack" has employment status "offboarded"` 失败 → `settleSubmitted(stage-3)`
被整体回滚 → stage-3 永远停在 `active` → 第 4 阶段和 `stage-approve` 永不进入 →
24 步内不可能出现闸门。

在 `tick` 标记上能看到对应证据：stage-3 的那个 tick 带 `partial_failure`。

> 契约早写在文档里（`03-data-model.md` §3.2.1：*任务派发的正确目标是岗位，由
> `resolveByPosition()` 解析到**当前在岗员工***）——**是代码违反了自己的契约**，
> 不是契约需要改。

### 7.3 修复

1. **`OrgGraph.resolveByPosition` 优先取「可执行」的占坑者**，仅当坑位上没有可执行者时才
   回退到第一个记录（保留回退是为了让上报链路/控制台仍能命名坑位主人，而不是把有人的坑报成空的）：

   ```ts
   const holders = organization.employees.filter((e) => e.positionId === positionId);
   return holders.find((e) => isExecutableEmployment(e.status)) ?? holders[0] ?? null;
   ```

   派活的调用方各自仍保留自己更严的规则：`TaskService` 在只有离职者时把任务留在岗位上，
   `WorkflowEngine` 拒绝进入「坑上无人可执行」的步骤——`resolveByPosition` 只回答
   「谁坐在这」，不回答「他能不能接活」。

2. **收敛重复的「不可执行雇佣状态」规则**。`suspended`/`transferred`/`offboarded`
   这三个状态被四处各写了一份副本（`task-system`、`workflow-engine`、`permission-system`，
   加上 `organization-model` 自己）。统一到 `EmployeeStatus` 旁边的
   `NON_EXECUTABLE_EMPLOYMENT_STATUSES` + `isExecutableEmployment()`（`employee.ts`），
   四处分发调用点全部改为引用同一实现。`on_leave` **刻意不在其中**：休假者仍占坑，
   只是不能接新活（那是 `isEmploymentAvailable` 的窄问题）。

### 7.4 回归测试（先证伪、后证实）
