## 1. K1 — Channel Bootstrap

### 1.1 Root cause

`createSimulation()` (the real composition root) built the Communication service with **empty
stores** and never opened a channel:

* `channels: createInMemoryChannelStore()` — always empty at boot.
* No runtime action can open one: `PLAN_ACTION_BINDINGS` has no channel-opening binding, and
  `AuthzService`/the control commands expose none either.
* `CommunicationService.sendMessage()` therefore failed **before** it ever looked at the
  recipient: `authorizeCommunication()` requires `channels.get(channelId) !== null`, so every
  agent `SendMessage` was answered with `unknown_channel` (verified in the M1.0.1 baseline probe:
  `ceo-alex:unknown_channel`, `channels 0`, `messages 0`).

The M0.7 module provides `Comm.openChannel` (and already emits `Communication.ChannelOpened`), but
**nobody called it** — the communication layer was never integrated into company formation.
Additionally, channels were pure in-memory state that nothing rebuilt from the log, so even a
deployment that opened a channel by hand lost it on restart.

### 1.2 Fix (no new mechanism)

`apps/kernel/src/simulation/simulation.ts` now performs **company formation** through the two
existing primitives — `Comm.openChannel` and the EventStore:

```ts
// deterministic id, e.g. company-future-ai-lab
companyChannelId(companyId)

await bootstrapCompanyChannel();   // company formation, BEFORE recover()
await recover();                   // rebuilds state (now including channels) from the log
```

* **Opener** — the employee occupying a *company-level* position (a position without a
  department; the CEO in the seed). The organization model already uses `departmentId: null` to
  mean "this role belongs to the whole company", so no new seniority concept is invented. Falls
  back to the roster's first member.
* **Members** — every organization employee, in roster order.
* **Type / id** — `group` channel `company-<companyId>` (satisfies the existing `channelIdSchema`).
* **Guard** — the existing channel contract requires ≥2 unique members, so a company with fewer
  employees boots without a default channel instead of throwing.
* **Record, not hidden setup (A3)** — the channel is opened through
  `CommunicationService.createChannel()`, and the returned `Communication.ChannelOpened` event is
  appended to the EventStore. It is the first event of a fresh log.
* **Replayable** — `recover()` now **projects channels from `Communication.ChannelOpened`**
  (`channelOpenedPayloadSchema` → `createChannel()` → `ChannelStore.save()`), exactly like tasks,
  workflow instances and agent state are replayed from their own events. A restarted kernel
  rebuilds the channel; the bootstrap is idempotent (it opens nothing when the log already holds
  that channel), so a restart appends **no** extra event and recovery parity is preserved.
* **Delivery follows the message wherever it entered the log** — the tick's communication-delivery
  consumer now processes the tick's input events *and* its cycle events (previously cycle events
  only). Delivery is idempotent, so re-seeing a message never duplicates a record. This closes the
  same "event exists, no consumer" gap for messages appended outside an agent turn (an injected or
  recovered `MessageSent`).

Verified chain (fresh simulation, no setup step): **CEO → CTO `SendMessage` →
`Communication.MessageSent` → delivery → recipient wakeup → reply delivered back**.

```
COMM: sent 4  deliveries [
  {messageId msg-1, recipientId cto-john,  channelId company-future-ai-lab, sourceEventId evt-4},
  {messageId msg-2, recipientId ceo-alex,  channelId company-future-ai-lab, sourceEventId evt-8},
  ...
]
COMM: turns [ ceo-alex:acted, cto-john:acted, ceo-alex:acted, cto-john:acted ]
```

## 2. K2 — Standalone Task Lifecycle

### 2.1 Root cause

Reading the existing semantics first (as required):

* `TaskService.submit()` moves a task to `submitted` and stores its `result`. Nothing else happens.
* `TaskService.complete()` is the **only** way to reach `completed`. It enforces the status
  machine (`complete` is legal only from `submitted`), a result precondition, permission, and
  `requireNotExecutor()` — **the executor may not verify its own work**.
* The only caller that ever completes a task is `WorkflowEngine.settleSubmitted()`, which is
  reached exclusively through `WorkflowEngine.advance(taskEvent)`:
  `evaluateVerification(task, step.verification)` → on `pass` the engine's own
  `systemActor('workflow-engine')` calls `tasks.complete()` and emits `Workflow.StepCompleted`.
* The kernel reactor (`runReactor`) is the deterministic consumer that drives that advance — and
  it explicitly skipped every task with `workflowInstanceId === null`.

So a task injected by `Organization.InjectTask` (which correctly creates **and assigns**, see
report D2) was worked to `submitted` by its assignee and then rested there forever: its executor
was forbidden from completing it, and no workflow step, command or rule owned the completion.
`status: created` → `submitted` → **stuck**.

### 2.2 Chosen approach (minimal, architecturally consistent)

The missing piece is **settlement authority**, not a new lifecycle. The task itself already
carries the rule the workflow engine would otherwise take from the step definition
(`Task.verification`), and `evaluateVerification` is already exported from `workflow-engine`. So
the kernel reactor — the layer that already turns task events into workflow transitions — applies
the **identical rule** to a task no workflow owns:

```ts
if (task.workflowInstanceId === null) {
  // submitted + evaluateVerification(task, task.verification) === pass
  tasks.complete({ taskId, actor: systemActor('kernel-reactor', correlationId), simTime,
                   verification: task.verification });
}
```

Properties that make this consistent rather than a bypass:

* It goes **through** `TaskService.complete()`. The task state machine, the result precondition and
  the "no self-verification" rule are all enforced inside the lifecycle; a task whose rule does
  **not** pass is left exactly where the lifecycle put it.
* The actor is a **system actor** (`kernel-reactor`), symmetric with the workflow engine's
  `workflow-engine` system actor. The executor still cannot complete its own work.
* The rule is the task's own declared `verification`, i.e. the same `evaluateVerification` used for
  workflow steps. No new command, no new package, no direct status write, no `task.complete()`
  shortcut that skips verification.
* Task-command budget is respected (`budget.tryTask()`; exhaustion marks `max_tasks`), and the
  task id is deduped per tick so a task cannot be completed twice.
* Workflow-backed tasks are untouched: the branch only triggers for `workflowInstanceId === null`,
  and the full suite (including the workflow vertical slice) stays green.

Observed lifecycle after the fix (acceptance Scenario F, no workflow involved):

```
Task.Created → Task.Assigned → Task.Accepted → Task.Started → Task.ProgressReported → Task.Completed
F: task after 5 ticks completed  (assignee cto-john, result present, completedAtSim set)
Task.Completed actor = kernel-reactor (system)
```

### 2.3 Residual limitations (deliberate, not bypassed)

* A standalone task whose declared rule **fails** (e.g. a missing required output key) stays
  `submitted`. Rejecting/retrying it needs a rejection policy that only a workflow step defines,
  and inventing one would be new behaviour — out of scope. The regression test asserts this
  explicitly, i.e. verification is **not** bypassed.
* A standalone task with `verification.kind === 'review'` waits for an approved review.
  `Agent.RequestReview`/`Task.RequestReview` currently only record a control fact (they do not call
  `TaskService.review()`), which is a pre-existing inconsistency between the M1.0 §9.3 table and the
  implementation. It does not affect the K2 fix (the default injected task declares no
  verification), and it is left as-is because it is outside K1/K2.

## 6. Can we enter M1.1?

**Yes — for K1/K2.** Both defects are fixed with the smallest in-scope change, verified by new
regression tests plus the full acceptance re-run, and all five gates are green. The two remaining
open items from the M1.0 report that touch these areas are explicitly *not* blockers and are
recorded above (§2.3): the "failed verification" and "review-verified" branches of the standalone
lifecycle need a product decision, and K3–K9 were out of scope by instruction.

Recommendation: M1.1 is unblocked with respect to K1/K2. K3–K9 and the two residual standalone
limitations above should be scheduled as their own hardening/feature items rather than folded into
the M1.1 entry work.
