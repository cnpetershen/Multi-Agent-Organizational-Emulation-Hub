## 1. Runtime Entry Point

There is **no production-like boot entry** in the repository (`apps/api/src/index.ts` and
`apps/kernel/src/bootstrap/` are still stubs). The real, runnable composition root is
`createSimulation()` in `apps/kernel/src/simulation/simulation.ts`, which is what the existing
integration/simulation suites drive.

Per the task rules ("如果必须建立最小 acceptance harness：只能复用现有 Simulation / Kernel /
EventStore / Cognition / Seed，不能创建第二套 Runtime"), the acceptance harness is a thin
**observer + scripted-employee** layer over the existing composition:

| Concern | Reused from |
|---|---|
| Composition root | `createSimulation()` (`apps/kernel`) |
| Operator surface | `createKernelControlPlane()` + `tests/helpers/control-fixtures.ts` (M1.0) |
| Seed organization | `agents/future-ai-lab/**` via `loadSeedOrganizationWithOperators()` |
| Seed workflows | `workflows/**` via `loadSeedWorkflows()` |
| Agent definitions / cognition profiles | `agents/future-ai-lab/agent-definitions`, `.../cognition` |
| Cognition executor | `createCognitionExecutor()` (`@maoeh/agent-cognition`) |
| LLM | `createMockLlmProvider()` (`@maoeh/llm-gateway`) |

New files: `tests/acceptance/runtime-harness.ts` (observer, prompt-driven cognition script) plus
6 acceptance test files. **Nothing was added to any `src/` tree to make the run possible.**

> **LLM honesty note.** `createMockLlmProvider` is the only provider implemented in this repo, so
> it is the current production cognition substrate. Everything else on the chain (scheduler,
> agent runtime, authorization gate, plan executor, task system, workflow engine, event store,
> control plane, recovery) is the real code path. The scripted employee reads the same cognition
> prompt a real model would read and answers the same JSON contract.

## 5. Cognition

* 4 cognition calls for the 4 productive turns; `provider.callCount` = 4 for the whole scenario
  (asserted `toEqual(4)`), i.e. **exactly one LLM call per productive turn**, plus 1 per failed
  attempt inside the error scenarios.
* No call without a valid input event. `buildCognitionContext` rejects missing
  `ActorContext`/`state`/`inputEvent`/`organization`/`profile`, and the executor re-validates that
  the actor matches the cognitive agent.
* No repeated cognition for the same `(agent, event)`: `turnContext.isProcessed` +
  `EventStore.markProcessed` are consulted before any turn.
* No "thinking without new events": between ticks 6–9 there were **0** LLM calls and 0 turns.
* Error paths behave: malformed output → `malformed_output` (non-retryable, 1 attempt);
  provider error → `provider_error` → `RETRY` wakeups, 1 + 3 retries inside a single tick then
  stop (bounded); unsupported action → `unsupported_action`.
* `UpdatePresence`/`Runtime.CycleStarted|Finished` are the only zero-LLM events; agent state
  versions advance by 2 per productive cycle (presence + cycle), consistent across recovery.

## 9. Communication

Before the fixes the Communication layer was **unreachable in the running kernel** (see §12
D3/D4). After the fixes, with a channel opened by the deployment:

```
ceo-alex SendMessage (request) → Communication.MessageSent (evt-4)
  → delivery ledger: {messageId msg-1, recipientId cto-john, sourceEventId evt-4}
  → [next tick] cto-john woken by evt-4 (correct recipient, correct event, correct actorContext)
  → cto-john SendMessage (response) → delivered back to ceo-alex → ceo-alex woken
  → one delivery record per (message, recipient); no duplicates; no message lost
```

Verified: sender/recipient channel membership is enforced, `sender_mismatch` and
`unknown_channel` are real refusals (never silent), deliveries are idempotent, and the recipient
really receives the event it was sent. Known gap K1 (no channel bootstrap in the runtime) and
observation K8 (an always-replying policy loops at one message/tick — kernel has no
back-pressure by design).

## 12. Defects Found

| ID | Severity | Symptom | Root Cause | Fix | Regression |
|----|----------|---------|-----------|-----|------------|
| **D1** | **P1** | Pause an agent while work is in flight → after `Agent.Resume` the agent never works again; its task stays `assigned` and the workflow stays `running/blocked` **forever** | `eligibleAgentsFor` dropped the wakeup for a paused agent at enqueue time while the tick cursor advanced past the event, and `Control.*` events are deliberately not wakeup-eligible — so the work was unrecoverable by design gap | Kernel now *defers* instead of dropping: `setPausedAgents()` detects the resume transition, `runSimulationTick` re-derives the agent's still-actionable unconsumed events (`deferredWorkFor` / `isStillActionable`), re-enqueues them with the **original** event as source, and `wakeupSource` keeps that event resolvable until the wakeup settles | `tests/integration/agent-pause-defers-work.test.ts`; acceptance Scenario C/D; `tests/unit/organization-control/intervention.test.ts` (assertion updated → now asserts recovery) |
| **D2** | **P2** | `Organization.InjectTask` writes `Task.Created` but never `Task.Assigned`; nobody is ever woken and the task rests at `created` forever ("Task 创建后无人接") | the command only called `TaskService.create()`, contradicting the frozen contract M1.0 §9.4 ("`Organization.InjectTask` → `TaskService.create()`，写入正常任务流，**由 Scheduler 唤醒**") and §11.7 (null assignee means "the position has nobody") | delegate to the existing `TaskService.assign()`, exactly as `WorkflowEngine.enterStep` does, and record `assigneeEmployeeId` on `Control.TaskInjected` | `tests/integration/inject-task-dispatch.test.ts`; acceptance Scenario F; `tests/unit/organization-control/observation-query.test.ts` + `intervention.test.ts` (assertions updated) |

## 13. Known Issues

Real, reproduced, deliberately **not** fixed in this phase (each needs a product decision, or is
observability-only and would require touching frozen interfaces). None of them breaks the accepted
runtime chain.

| ID | Sev | Issue | Evidence | Why deferred / minimal fix |
|----|-----|-------|----------|---------------------------|
| **K1** | P2 | The M1.0 runtime has **no channel bootstrap**: no channel is seeded and no runtime action can open one, so out of the box `SendMessage` fails `unknown_channel`. The agent-communication module is not integrated into the composition root | baseline `channels: 0`; probe `ceo-alex:unknown_channel`, `messages 0` | channel topology is a product decision (who may open which channel with which members). Minimal fix: seed `channels` data under `agents/future-ai-lab/` (or add an M1.1 operator command / channel-opening action). The acceptance harness opens the channel through the package's public `Comm.openChannel` so the rest of the chain could be verified |
| **K2** | P3 | A **standalone** (non-workflow) task can never reach `completed`: `TaskService.complete()` forbids the executor from verifying its own work and no other actor (no control command, no kernel rule) owns standalone completion, so the task rests at `submitted` | acceptance Scenario F trace: `task-1: assigned → submitted`, then idle forever | requires deciding who owns standalone verification authority (a new command or a new kernel rule = new capability, out of scope for acceptance). Minimal fix: `Task.Complete` control command, or route standalone submitted tasks to the creator |
| **K3** | P4 | `Task.*` / `Workflow.*` events carry `causationId: null` (40 of 51 events in the acceptance run), so the causal chain must be walked via `correlationId` + `seq` | acceptance stream dump; the same limitation is already recorded in M1.0 §11.3 | documented existing engine behaviour; fixing it touches task/workflow event emission |
| **K4** | P4 | `SimulationTickResult.emittedEvents[]` all carry `seq: 0` (and no `occurredAtWall`): the batch is the pre-append view, while `EventStore.append` stamps `seq` on a copy. Ordering/uniqueness must be read from the store | every acceptance trace line `-> evt-N seq=0`; `EventStore.append` assigns seq to `{...event, seq}` | the pre-append `seq: 0` contract is explicitly asserted today (`event-store.test.ts`, `event-contract.test.ts`), so changing it would contradict frozen tests; the control-plane observation surface already reads from the store |
| **K5** | P4 | A failed cognition turn records `llmCalls: 0` even though the provider was called, so LLM accounting undercounts failures | provider-error trace: 4 failed turns, all `llm=0`, `provider.callCount` = 4 | requires threading call metadata through `agent-cognition` → `agent-runtime` error results (cross-package, observability only) |
| **K6** | P4 | Tick 0's `System.SimClockTicked` marker is **virtual**: created in memory as `lastTickMarker` but never appended, so `evt-1` does not exist in the log (`recovery.eventCount = 0` at boot) | baseline: `events: []`, `recovery.eventCount 0`; also asserted by `tests/simulation/organization-loop.test.ts` | latent only: it becomes a dangling `causationId`/input event if a wakeup resolves to that marker (only for schedule-driven or unresolvable wakeups, which the current runtime never creates). Minimal fix: append the boot marker — but that changes an explicitly asserted boot contract, so it belongs to a deliberate decision |
| **K7** | P4 | The scheduler retains every wakeup record for the process lifetime (`records` is never evicted; `clear()` is unused) → unbounded memory in a long continuous run | `queueRecords` grows 1:1 with wakeups (5 after the run) and never shrinks across idle ticks | only affects very long runs; needs an eviction policy for settled wakeups in `runtime-scheduler` (shared package) — record, do not expand scope |
| **K8** | P5 | An employee policy that answers every message creates an unbounded 1-message-per-tick ping-pong; the kernel applies no back-pressure to messaging | communication probe: `msg-1 → msg-4` ping-pong across 4 ticks | by design the kernel cannot judge whether a message deserves a reply; this is a cognition/conversation-policy concern. The default acceptance cognition stays bounded (answers requests only) |
| **K9** | P5 | `SimulationTickResult.wakeupCount` counts wakeups *created* during the tick, so a control-plane `MANUAL` wakeup created before the tick reports `enqueued=0` although a turn ran | tick 1 of every intervention scenario: `enqueued=0` with 1 turn | semantic/observability naming issue; fixing it changes a public result field's meaning |

**Architecture issues (M1.0 §24) — recorded, not refactored:**
* **A1** — `agent-communication` has no integration point in the composition root (K1). Not an
  M1.0 blocker: the accepted business chain completes without messaging.
* **A2** — standalone-task completion authority is undecided in the M1.0 product boundary (K2).
  Not an M1.0 blocker: workflow-backed work completes fully.
Neither required (nor received) an architecture change; the frozen baseline was not touched.

## 15. Final Verdict

**PASS WITH KNOWN NON-BLOCKING ISSUES**

The decisive question — *"如果现在没有 UI，一个工程师通过现有 Runtime / Control Surface，能否真正
启动这家公司，让它自主工作，观察它工作，在运行过程中介入，然后让它继续自主工作？"* — is **YES**,
and it was demonstrated on the real composition root:

1. **Start** the company (`createSimulation` over the real seed) — 3 AI employees, 6 positions,
   4 workflows, clean budgets.
2. **Work autonomously** — one board instruction produced the full
   CEO → CTO → approval → CTO → `Workflow.InstanceCompleted` chain with 4 cognition calls, 3
   tasks, 1 gate, 0 duplicates, then genuine idle (no LLM calls, no wakeups).
3. **Observe** — per tick: input events, wakeups, agent turns, cognition calls, emitted events,
   task changes, workflow changes, agent-state changes; the stream is well-ordered (0 ordering
   violations) with no terminal-before-cause events.
4. **Intervene** — all 8 scenarios (Pause/Resume Simulation, Pause/Resume Agent,
   Agent.Instruct, InjectTask, human Approval, Audit) really changed runtime behaviour, not just
   the log; and refusal paths stayed fail-closed.
5. **Continue autonomously** — after every intervention the scheduler, runtime, workflow, task,
   communication, event store and recovery kept working, including recovery parity: a restart on
   the same event store reproduced the continuous path snapshot exactly and converged on the same
   final state.

Four real runtime defects were found by running (not by reading tests) and fixed with minimal,
in-scope changes — one **P1** (paused agent permanently lost its work and stalled the workflow),
two **P2** (injected tasks were never dispatched; the communication action was never permitted),
one **P3** (`MessageSent` had no consumer, so deliveries never existed) — each with a regression
test, and all five gates green afterwards.

The verdict is **not** a plain PASS because nine genuine issues remain open (K1–K9, §13): the most
substantial are the missing channel bootstrap (K1) and the unfinished standalone-task lifecycle
(K2), both of which need a product decision rather than a bug fix, plus observability gaps
(K3–K7) that would require touching frozen interfaces or shared packages. None of them blocks the
accepted runtime chain, and no architecture was refactored to hide them.

**M1.0 Runtime Acceptance PASS WITH KNOWN NON-BLOCKING ISSUES — stopping here, not entering M1.1.**
