## 1. Scope and Acceptance

The console must let an operator run the company, not just watch it:

1. **Start Work** — a human briefs the company with a title / objective / context; the CEO plans it.
2. **Agent instruction** — direct a specific agent and see the instruction acknowledged.
3. **Inject task** — put work into the queue, including a position nobody staffs (`qa`).
4. **Observe** — agents, tasks, workflows, runtime, events, communications all rendered from real query state.
5. **Decide** — an approval gate opens for the human, the operator approves/rejects, and the decision is auditable in the event log.
6. **Complete** — after the decision the workflow reaches `completed` and the console reports it.

Out of scope and untouched (how each was honored: §6): simulation engine, scheduler, clock,
agent-runtime / cognition core semantics, workflow state machine, task lifecycle, EventStore,
the M1.2-A tick driver, the M1.2-B event filter. No new packages, runtimes, state machines, or mock UI data.

## 3. How the Operation Loop Works

1. **One command path.** Every user action becomes a `ControlCommand` envelope (same schema
   the kernel already accepts) posted to `POST /api/command`; nothing in the console talks to
   the engine any other way.
2. **Start Work = hold → brief → walk to the gate.** The hold checkbox issues
   `Simulation.Pause` first, then `Agent.Instruct` to `ceo-alex` with title/objective/context
   folded into the instruction. Deterministic cognition turns that into
   `CreateProposal {workflowId: 'product-analysis', title: 'Board directive', goal: <instruction>}`
   (cognition untouched — the user's title surfaces as the first line of the objective).
   The page then issues bounded `Simulation.Step` commands until the workflow detail shows an
   open approval gate, and parks on Approvals.
3. **Gate visibility without a special API.** The engine emits `Workflow.ApprovalRequested`;
   while the runtime is held (and the approver paused when needed) the gate stays open.
   `getPendingApprovals()` is always empty in production, so Approvals composes open gates
   from `GET /api/workflows` details plus escalations plus `Workflow.Approval*` history events.
4. **The human decides, then the hold is released.** Approve/Reject issues `Workflow.Approve|Deny`
   → `Workflow.ApprovalGranted|Denied` with `decidedBy` in the event log → the page releases
   the hold → the company resumes and finishes the workflow.
5. **Observation is polling over real reads**: 2.5 s refresh of `/api/snapshot`,
   `/tasks`, `/workflows`, `/agents`, `/events`, `/communications`, `/simulation`; feedback
   banners are the only "UI state" and they never invent data.

## 6. Constraints and Locked Decisions Honored

* **No engine / scheduler / clock / cognition / workflow / task / EventStore changes.** All
  backend edits are read-model additions (`positions`, workflow detail views).
* **Layers stay separate**: console = presentation; `organization-control` queries = runtime
  read model; `ControlPlane.execute()` = the only write path.
* **Web never imports `@maoeh/*`** (enforced by eslint + dependency-cruiser `web-no-backend`).
* **Cognition contract preserved**: `deterministic-cognition.ts` and `workflow.yaml` untouched;
  `tests/unit/api/deterministic-cognition.test.ts` and `tests/acceptance/runtime-harness.ts`
  (`title: 'Board directive'`) still green.
* **Locked decision — agents auto-resolve approval gates.** Human approval is achieved by
  *holding* the runtime (`Simulation.Pause` + `Simulation.Step`) and pausing the approver
  (`Agent.Pause ceo-alex`), exactly as `runtime-reality.test.ts` requires. Removing
  auto-approve would break existing acceptance tests.
* **No new dependencies, packages, or state machines**; the E2E uses Node built-ins + a local Chrome.
* Original `console.css` rules were not modified — the operation-loop styles were appended.
* `getPendingApprovals()` was **not** patched to fake pending state; the Approvals page derives
  gates from workflow state instead (verified by `pending === []` in the integration test).

## 7. Known Limitations and Risks

* **Auto-resolve window (~21 ms in tests, ~100 ms in production)**: without the hold, a gate
  can be granted by the CEO agent before a human clicks. The console mitigates this by holding
  the runtime by default (checkbox on, sidebar `HELD FOR YOU`), but an API-level client that
  forgets to hold can still be outraced. A future "hold at gate" engine policy would fix the root cause.
* **Approvals is a derived view**: open gates are recomputed from workflow details + events on
  every poll, so a very long event history makes that page's composition the heaviest read in the console.
* **Feedback copy** uses position title + employee name (`Chief Executive Officer Alex`), which is
  accurate org data but reads long; a display-name / nickname concept does not exist yet.
* **E2E is environment-bound**: hardcoded Chrome paths (override with `CHROME_PATH`), fixed ports
  3199/4173/9444, Windows `netstat`/`taskkill` for cleanup. It is excluded from `pnpm test`
  deliberately, so CI needs a Chrome-provisioned job to run it.
* **One workflow shape exercised**: `product-analysis` (single `design-gate`, roles `[ceo]`).
  Multi-gate / multi-role workflows (`decision-making`, `hiring`, …) are not yet driven from the console.
* Evidence artifacts: the PNG is committed; `*.log` is gitignored by repo policy.
