## 0. 结论先行

M3.4 把 M3.3 的真实草案交给人类管理者：

```text
M3.3 工作流草案（编排文档 + engine draft 实例）
  → M3.4 执行方案 vN（可编辑）
      节点名称 / 目标 / 输入 / 输出 / 验收
      真实员工改派（能力校验）
      依赖新增/删除/修改 → DAG → 拓扑顺序
      结构 / 员工能力 / 依赖 / 完整性校验
      保存草案 ≡ 新版本（乐观锁）
  → 人类确认（独立动作）
      确认人 + 时间 + 版本 + 方案摘要
      不可覆盖的 confirmed 版本
  → M3.5 读取 confirmed 版本并启动任务实施
```

**确认只代表“人类确认执行方案”，不代表开始执行。** 本阶段不会：
- 创建 Task；
- 调用 `Workflow.ConfirmStart`；
- 进入 workflow entry stage；
- 唤醒 Agent 或调度器。

集成测试硬断言确认后 `/api/tasks` 为空，且没有 `Task.Created` / `Workflow.StepEntered` / `Workflow.DraftConfirmed` 事件。

## 1. 数据模型与版本

`ExecutionPlan`（见 `planning-types.ts`）：

| 字段 | 说明 |
| --- | --- |
| `planId / version / status` | `draft` 或 `confirmed`；每次保存/确认都追加版本 |
| `orchestrationId / orchestrationVersion` | 来源 M3.3 编排；原编排不被覆盖 |
| `requirementId / requirementVersion` | 需求依据 |
| `title / goal` | 方案标题与业务目标 |
| `nodes[]` | `nodeId / kind(task|approval) / title / goal / capability / employeeId / positionId / inputs / outputs / acceptance / dependsOn` |
| `order[]` | 由 DAG 计算出的拓扑顺序，不接受手填 |
| `validation` | blocking/warning、cycle、missingCapabilities、unassigned |
| `summary` | 节点/任务/员工/能力/交付物/workflowInstanceId |
| `change` | 相对上一版本的改名/改派/依赖/内容计数 |
| `workflowInstanceId / workflowId` | M3.3 engine 草案实例 |
| `confirmedAt / confirmedBy / confirmationNote` | 人工确认审计字段 |

存储：`stateDir/planning/planning.json` 的 `plans` 数组；按公司隔离；`PlanRecord { planId, companyId, currentVersion, versions[] }`。

规则：
1. 保存修改 → 新 version，`status=draft`；旧版本逐字保留。
2. 确认 → 新 version，`status=confirmed`；已确认版本不可改写。
3. 再次编辑已确认版本 → 从它派生出新的 draft version；confirmed 版本仍在历史里。
4. `baseVersion` 不匹配 → `409 version_conflict`。
5. 每个 orchestration 只打开一个 plan（`POST /plans` 幂等），避免重复方案。

## 2. 画布编辑

### 2.1 节点

- 修改 `title / goal / inputs / outputs / acceptance`。
- 节点集合来自 M3.3，不允许在 M3.4 增删节点；这保证 engine 草案实例与 plan 的节点一一对应。
- 输入/输出/验收均为列表编辑（一行一项）。

### 2.2 员工改派

- 下拉只列**真实且可执行**、且其岗位能力或 expertise 覆盖该节点 capability 的员工。
- 当前负责人若不覆盖能力，仍会显示（不静默替换），校验给出 `employee_not_capable` 阻塞。
- 改派通过 `Workflow.StepAssignmentOverridden` 事件同步到 engine 的 **分配视图**；不进入执行。
- 真实员工/能力来自现有 organization，不使用假员工。

### 2.3 依赖与顺序

- 复选框修改 `dependsOn`；允许保存非法依赖（人还在编辑），但校验会阻塞确认。
- 校验包含：
  - 自依赖；
  - 未知依赖；
  - 循环依赖（Kahn 剩余节点）；
  - 同一员工承担**无依赖路径**的并行任务 → `employee_conflict` warning。
- `order[]` 每次保存/确认由 `topologicalOrderOf(nodes)` 重算；画布布局按依赖深度分层，拖动只改变视图坐标，不改变执行顺序。

### 2.4 风险与预览

校验面板显示：
- 阻塞问题与警告；
- 缺能力、未分配、循环；
- 节点名与依赖的可读摘要。

画布展示完整 DAG、负责人、输入/输出/验收、节点顺序；右侧摘要展示节点数、可执行任务数、员工数、最终交付物。底部明确显示「此阶段不创建任何 Task」，并提供禁用的「开始执行（M3.5）」按钮。

### 2.5 交互

- 深色画布，缩放（50%–160%，打开时自动 fit）；
- 节点拖动排布、点击选中；
- 右侧 inspector 编辑；依赖复选框；
- 版本列表切换历史版本（历史版本只读）；
- 中英文切换。

## 3. 校验与人工确认

### 3.1 校验（`plan-validator.ts`）

阻塞：
- `missing_title / missing_goal / missing_input / missing_output / missing_acceptance`
- `missing_employee`（无真实可执行负责人）
- `employee_not_capable`
- `unknown_dependency / self_dependency / dependency_cycle`
- `missing_workflow_draft`

警告：
- `employee_conflict`
- `assignment_override_failed`

`validation.ok` 仅当 blocking 数为 0。

### 3.2 确认

`POST /api/plans/:id/confirm`：

1. `baseVersion` 必须等于当前版本；
2. 用当前 nodes + 真实 organization 重新校验；
3. 存在 blocking → `422 plan_invalid`，返回 `details.validation`；
4. 生成 version+1，`status=confirmed`；
5. 写 `confirmedAt / confirmedBy / confirmationNote / summary`；
6. **不调用** workflow 的 confirm/start，不创建 task。

保存与确认是两个 API 动作、两个状态；页面也提供两个按钮。若用户改完直接点确认，前端会先保存草稿再确认该版本，确保确认的是屏幕上的内容。

### 3.3 已确认方案

- `GET /api/plans/:id/confirmed` 返回最高版本的 confirmed plan（M3.5 的读取入口）。
- 已确认版本不可被 PUT 改写；后续编辑生成新 draft。
- 再次确认一个已 confirmed 的当前版本 → `409`，必须走“编辑 → 新版本 → 确认”。

## 4. 与既有模块的衔接

### 4.1 workflow-engine

- 复用 M3.3 的 draft 实例和 `StepAssignmentOverridden`；不新建状态机。
- 不调用 `Workflow.ConfirmStart`（该命令会进入 stage 并创建 task）。
- Plan 的节点/依赖/顺序是 M3.5 的输入；engine 的 definition 仍是 M3.3 生成的结构，M3.4 不篡改引擎定义。

### 4.2 现有「改派画布」的确认按钮

既有 `WorkflowCanvasPage` 的「确认执行」实际调用 `Workflow.ConfirmStart`，会开始执行。M3.3 的 plan 草案不能再复用它：

- API 的 workflow summary 增加 `planned` / `planningOrchestrationId`（`context.planning` 标记）；
- 对 `planned` 实例，按钮文案改为「在方案画布中确认（M3.4）」；
- 点击不会调用 `confirmStart`，而是导航到 M3.4 方案画布；
- 非 planning 的 M1.9/M2 draft 保持原有行为。

这样「确认方案」和「开始执行」在语义和入口上被明确拆开。

### 4.3 M3.2 协作剧场

- 不伪造规划事件；需求/方案文档不在组织事件日志中冒充 agent 活动。
- M3.4 的改派会产生真实的 `Workflow.StepAssignmentOverridden` 事件，剧场按真实事件展示。
- 确认本身是人工规划事实，记录在 plan 文档；M3.5 启动后才会产生真实任务/执行事件。

## 6. M3.5 交接

M3.5 应读取：

```http
GET /api/plans/:id/confirmed
```

并消费：

- `version / confirmedAt / confirmedBy / confirmationNote`；
- `requirementId / requirementVersion / orchestrationId / orchestrationVersion`；
- `nodes[]`（负责人、能力、输入、输出、验收、依赖）；
- `order[]`（已按 DAG 重算）；
- `workflowInstanceId`（M3.3 engine 草案）；
- `summary`。

启动执行属于 M3.5：它负责把这些已确认节点转成真实任务/进入 workflow stage，并承担调度与审批。M3.4 不提供该动作。

## 8. 已知边界

1. **节点集合固定**：M3.4 不新增/删除节点；增删节点需要 engine definition 重建，留给 M3.5 或后续。
2. **改派同步是展示级**：`StepAssignmentOverridden` 更新 engine 的分配视图；节点名称/依赖/输入输出/验收只存在 plan 文档，M3.5 负责按 plan 创建真实任务。
3. **方案存文件而非事件**：确认不是组织事件；这是规划/执行边界的刻意选择，避免在任务未开始时污染组织事实。
4. **单人确认**：当前本机单租户，`operatorId` 即确认人；多用户认证仍沿用 M1.5 的边界。
5. **画布位置不持久化**：拖动只影响当前视图；执行顺序始终由 DAG 决定。
6. **并行执行**：plan 记录完整 DAG，但 engine 仍按阶段串行；真正的并行调度属于后续执行阶段。
