# M1.7 · LLM Provider Configuration（真实模型接入与配置）

> 状态：**CURRENT**（实现契约，代码已落地）
> 从属：`ARCHITECTURE-BASELINE.md`（最上位：A4、§9 F6 唯一 Egress、ADR-008）、`05-runtime.md` §5.5（预算护栏）、`02-modules.md` §2.5（`FakeLlm` 为可测试性基石）、`08-adr.md` ADR-003 / ADR-008、`M1.0-organization-control-plane.md`
> 一句话：**默认仍是 mock；接入真实模型是「底座替换」而非「能力升级」** —— 配置只决定*谁来生成文本*，能力上限由**封闭 Action Space** 与**确定性授权闸门**锁死，换模型不会放宽任何一条。

## 1. 目标与非目标

### 1.1 目标

1. **给出唯一配置入口**：环境变量。此前仓库**没有任何** LLM 配置面（`@maoeh/config` 是 `export {}` 空壳、无 `.env`、无 dotenv），生产认知底座硬编码在 `apps/api/src/composition.ts` 里。
2. **默认零变更**：不设置任何 LLM 变量时，产出的配置是 `mode: 'mock'`，行为与 M1.7 之前逐字一致。
3. **接 DeepSeek**：走 OpenAI 兼容协议族，换厂商只改 `baseUrl` + `model`，不改代码。
4. **失败必须可诊断**：401 / 402 / 429 / 400 / 422 / 5xx 各自映射到不同错误码，不塌缩成一个 "provider_error"。
5. **重试不使预算与账本失真**：每次 HTTP 尝试**各自**消耗调用预算、**各自**落一条 `llm_calls`（ADR-008）。
6. **不静默降级**：`live` 缺密钥 = 配置错误并拒绝启动，绝不回退 mock。

### 1.2 非目标

- **不做 Web 配置界面**：浏览器里存 API key 会引入新的密钥泄漏面，且与「人类可观测」目标无关。密钥只走环境变量。
- **不做多 Provider 路由 / 故障转移**：`LlmGatewayConfig.providers` 已是数组（为将来留位），但今天只装配一个。
- **不做语义缓存**：属 `llm-gateway` 的既有规划职责，本轮不实现。
- **不改 Prompt**：现有 `packages/agent-cognition/src/prompts/` 已含 "JSON" 字样与结构示例，满足 DeepSeek JSON Output 的硬要求，无需改动。
- **不承诺能力提升**：见 §6 —— 这是本轮最需要纠正的预期。

## 2. 配置契约

### 2.1 环境变量（`packages/llm-gateway/src/config.ts` 的 `LLM_ENV`）

| 变量 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `MAOEH_LLM_MODE` | `mock` \| `live` | `mock` | 唯一开关；`live` 是显式选择 |
| `MAOEH_LLM_PROVIDER` | 字符串 | `deepseek` | 逻辑 id，进 `llm_calls`，可被 `LlmRequest.provider` 覆盖 |
| `MAOEH_LLM_BASE_URL` | http(s) URL | `https://api.deepseek.com` | `live` 时必须是绝对 http(s) |
| `MAOEH_LLM_MODEL` | 字符串 | `deepseek-flash` | DeepSeek-V4.1-Flash |
| `MAOEH_LLM_API_KEY` | 密钥 | 无 | `live` 时必填 |
| `MAOEH_LLM_THINKING` | `enabled` \| `disabled` | `disabled` | 见 §4.1 |
| `MAOEH_LLM_MAX_TOKENS` | 正整数 | `8192` | 防呆上限 1,000,000 |
| `MAOEH_LLM_TIMEOUT_MS` | 正整数 | `60000` | 单次尝试超时 |
| `MAOEH_LLM_MAX_ATTEMPTS` | 正整数 | `1` | 含首次；防呆上限 10 |
| `MAOEH_LLM_ALLOW_LIVE_IN_CI` | 布尔 | `false` | CI 下放行 `live` 的唯一途径 |

### 2.2 语义规则

- **空白即未设置**：`FOO=` 与不设置等价（沿用 `previewWorkspaceRoot` 的既有约定）。
- **一次报出全部问题**：`loadLlmGatewayConfig` 收集所有 issue 后统一返回，操作者一次改完，不必逐条试错。
- **不读 `process.env` 自身**：函数接收环境记录作为参数。网关因此不依赖 Node 全局，测试可注入精确环境，且**只有组合根**知道配置如何到达进程。
- **`live` 的三道闸**（任一不合即 `invalid_config`）：
  1. 缺 `MAOEH_LLM_API_KEY` → 拒绝；
  2. `baseUrl` 不是绝对 http(s) URL → 拒绝；
  3. 设置了 `CI` 且未显式放行 → 拒绝（`docs/architecture/02-modules.md` §2.5：CI 必须确定性）。

## 3. 归属裁定：为什么配置住在 `llm-gateway`，而不是 `@maoeh/config`

| 理由 | 依据 |
| --- | --- |
| 网关是当前**唯一**消费者 | `@maoeh/config` 至今零引用；指向空壳包只是把空壳搬到别处 |
| 架构测试已把 SDK 出口锁在本包 | `tests/architecture/a4-import-scan.test.ts`、`eslint.config.mjs` 的 `providerBan` 均只豁免 `packages/llm-gateway/**` |
| 不新增依赖边 | 组合根（`apps/api`）本就负责装配，C2 边界（控制面禁 import `llm-gateway`）不受影响 |

**升级触发条件**：出现第二个需要配置的子系统（如 event-store 路径、runtime 预算）时，**提升通用加载器**到 `@maoeh/config`，而不是搬运本 schema。

## 4. 三个必须显式处理的 DeepSeek 行为

### 4.1 Thinking 模式默认开启，会**静默**吞掉 `temperature`

DeepSeek 的 thinking 模式**默认开启且 effort 默认 `high`**；在该模式下 `temperature`、`presence_penalty`、`frequency_penalty` **被接受但无任何效果**（官方原文：*"will not trigger an error but will also have no effect"*）。

而 `LlmRequest.temperature` 是项目既有字段。若不处理，调用方设了温度却毫无作用且不报错 —— 这正是 `AGENTS.md` 禁止的 hidden behavior。

**裁定**：默认 `thinking: 'disabled'`。理由不止是让 `temperature` 生效：thinking 默认 `high` 会让每一轮认知都产出 CoT，在多 Agent 仿真下成本会失控（`05-runtime.md` §5.5 引用的研究：多 Agent 系统 token 用量约为对话的 15×）。provider 在 thinking 开启时**不发送** `temperature`，而不是发一个明知被丢弃的字段。

### 4.2 JSON Output 的三条硬要求 + 官方承认的偶发空返回

官方要求同时满足：① `response_format: {'type':'json_object'}`；② prompt 中出现 **"json"** 字样并给出 JSON 示例；③ 合理设置 `max_tokens` 防截断。并明确承认：**偶发返回空 content**。

① 由 `LlmRequest.responseFormat: 'json'` 承载，`agent-cognition` 在 `cognition-executor.ts` 显式传入；② 现有 prompt 已满足（`prompts/system.ts` "a single JSON object"、`prompts/cognition.ts` "## Required JSON schema" + 结构示例）。

**空返回的归属裁定（关键）**：当请求了 JSON 而 content 为空时，provider **返回 `provider_error`，不返回成功**。

> 若返回 `text: ''`，它会一路走到 `agent-cognition` 变成 `malformed_output` —— 一个**不可重试**的错误，且正是当年「控制台看着在跑、组织却什么都没做」的成因（`apps/api/src/composition.ts` 的注释记录了这个故障）。判为 provider 失败后，它才落进网关的重试、预算与 `llm_calls` 账本。

### 4.3 错误码映射（不塌缩成单一 provider_error）

| HTTP | `LlmErrorCode` | 可重试 | 理由 |
| --- | --- | --- | --- |
| 401 | `auth_failed` | ✗ | 密钥错了，重试只是浪费钱 |
| 402 | `account_unfunded` | ✗ | 需要人去充值 |
| 429 | `rate_limited` | ✓ | 限流是暂时的 |
| 400 / 422 | `invalid_request` | ✗ | 请求体错了，重试结果相同 |
| 5xx / 网络异常 / 畸形响应 | `provider_error` | ✓ | 传输与上游故障 |

`agent-cognition` 侧同步新增 `llm_auth_failed` / `llm_rate_limited` / `llm_account_unfunded`（`cognition-errors.ts`）。此前这三者会经 `?? 'llm_gateway_unavailable'` 兜底降级，把「密钥无效」误报成「网关不可用」，排查方向会完全跑偏。

## 5. 重试的归属，与预算 / 账本不变式

**归属不是个人偏好**：`ARCHITECTURE-BASELINE.md` §9 已把「路由/**重试**/结构化输出/Token 预算/语义缓存/成本记账」列为 `llm-gateway` 的职责。因此重试**不得**下沉进 provider。

### 5.1 为什么不能放在 provider 内部

`gateway.ts` 在调用 provider **之前**只 `budget.consume()` 一次、调用**之后**只 `recordLlmCall()` 一次。若 provider 内部偷偷重试 N 次 HTTP：

- 调用预算**少算 N 倍** → 成本护栏失效；
- 账本只留 1 行 → 违反 **ADR-008**（`llm_calls` 是成本与调用的真相源）。

### 5.2 不变式

1. **每次尝试各自 `budget.consume()`**，各自 `recordLlmCall()`（`callCount` 逐次递增，因此同一次 `requestId` 的多次尝试在账本上可区分）。
2. **`maxAttempts` 默认 `1`**：与引入重试前逐字等价，既有测试无需改动。
3. **只有可重试错误码进入下一轮**（§4.3）；`auth_failed` / `account_unfunded` / `invalid_request` / `provider_unavailable` 立即返回。
4. **预算撑不起重试时停止，并报告 provider 的真实失败**，而不是 `budget_exceeded` —— 否则会把操作者指向错误的问题。
5. **预算为 0 且尚未尝试** → `budget_exceeded`，provider 不被调用。

### 5.3 运行时预算会感知重试（预期内）

`run-tick.ts` 用 `cycle.llmCalls` 递减 per-tick 预算，而 `cycle.llmCalls` 取自 `llmMetadata.callCount`，即**认知调用的尝试次数**（`cognition-executor.ts` 的 `budget.callCount`）。因此 `maxAttempts=2` 时，一次「失败 + 重试成功」会从该 tick 的 32 次额度里扣掉 2 次，**挤占同 tick 的认知轮次**。这是 §5.2 不变式 1 的直接后果，也是「重试必须可见」的代价：它宁可少做几轮，也不隐藏花费。

### 5.4 运行时的两层重试是**不同层**

`packages/agent-runtime/src/cycle.ts` 的 `RETRYABLE_COGNITION_ERRORS` 决定**是否再次唤醒 Agent**（跨 tick），与本节的**单次调用内 HTTP 重试**正交。`llm_rate_limited` 同时加入该集合（限流应跨 tick 重试），而 `llm_auth_failed` / `llm_account_unfunded` **不加入** —— 重试它们会把整个运行预算烧在一个只有人能终止的循环里。

## 6. 能力上限**不因换模型而变**（本轮最重要的澄清）

| 约束 | 位置 | 效果 |
| --- | --- | --- |
| **封闭 Action Space** | `shared-types` 的 `ACTIONS`（48 个） | 模型只能在这 48 个动作里挑，无法发明新动作 |
| **授权闸门（第 ⑦ 步）** | `05-runtime.md`、ADR-003、BASELINE 公理 A4 | **确定性代码、零 LLM**。LLM 只能提议，内核才能执行 → 模型再强也拿不到多一分权限 |
| **Schema 强校验** | `cognitionOutputSchema` | 不过 schema 即 `schema_violation`，整轮失败 |

因此：**换模型换的是「文本生成底座」，不是「权限或能力」**。模型只影响认知循环第 ③④⑤⑥ 步的「怎么想」；第 ⑦ 步之后的「能不能做」全在确定性代码手里。

### 6.1 会变的 / 不会变的

| | 变化 |
| --- | --- |
| **会变** | 语义质量：`interpretation` / `consideration` / `conclusion` 从 mock 的机械文本变为真正读懂目标的内容 —— 而这恰是人类在控制台观察的部分 |
| **会变** | 可复现性**下降**：同一输入可能产出不同计划（这正是架构规定真实模型只在 `tests/simulation-live/`、默认不进 CI 的原因） |
| **会变** | 成本与延迟从 ~0 变为每次真实 token 与网络往返 |
| **不会变** | 权限、动作空间、工作流/审批/任务引擎、可执行性上限 |
| **可能变差** | mock 是被专门调优成「一定能产出可执行计划」的；真实模型可能产出被拒绝或不可执行的计划，导致**更多失败回合**。且 per-tick 的 `maxLlmCalls`（生产 32）是硬预算，耗尽时**当 tick 剩余唤醒推迟到下个 tick**（限流，非停机） |

> 结论：密钥让系统**更真实**，不是**更强**。

## 9. 已知限制与复审触发条件

1. **`llm_calls` 仍未物化**：实现落在 `@maoeh/observability` 的内存数组，Postgres DDL 在 `03-data-model.md` §3.9 但未落库（BASELINE §15 SCHEMA GAP）。**live 模式下的成本审计因此不跨进程存活**。
2. **live 回合不可重放**：ADR-005/006 的重放依赖事件流，而模型输出不入事件流。真实模型运行**不具备** mock 的逐字可复现性 —— 这是 `tests/simulation-live/` 默认不进 CI 的根本原因（该目录目前**尚不存在**）。
3. **`providers` 数组只装配一个**：多 provider 路由与故障转移仅预留了结构。
4. **per-provider timeout 未实现**：网关只有单一 `timeoutMs`，工厂取默认 provider 的值。
5. **per-tick `maxLlmCalls` 是 live 模式的限流点，不是停机点**：`apps/kernel/src/simulation/run-tick.ts` 在**每个 tick 内**重建预算（`createBudgetTracker(config.budget)`），生产值为 32（`apps/kernel/src/simulation/types.ts` 的 `DEFAULT_SIMULATION_BUDGET`）。耗尽时该 tick 剩余的 pending 唤醒被推迟到下个 tick —— **工作不丢失，组织不停机**。长仿真仍建议先摸清真实调用量。
6. **无 live 集成测试**：本轮只有真实调用冒烟 + 单测，没有 `tests/simulation-live/` 级别的端到端 live 验收。

**复审触发条件**：① 需要第二个配置消费方 → 提升加载器到 `@maoeh/config`；② 需要多 provider → 扩展 `providers` 装配与路由；③ `llm_calls` 物化后 → 把成本审计接进 `CycleResult.cost`；④ 真实模型产出质量被实测证伪 → 回到 mock 或引入结构化输出重试策略。

## 10. 与既有权威的关系

本文档**不修改任何基线契约**，只是把基线已授予 `llm-gateway` 的职责（§9 的「重试/Token 预算/成本记账」）与 F6 单出口在代码上落地：

- **F6（唯一 LLM Egress）**：provider SDK 与 HTTP 直连仍只在 `packages/llm-gateway/**`，由 `tests/architecture/a4-import-scan.test.ts` 与 ESLint `providerBan` 双重强制，本轮扫描仍为 0 违规。
- **A4 / ADR-003**：未触碰授权闸门；`agent-cognition` 仍只能经 `llm-gateway` 提议。
- **ADR-008**：重试的每次尝试都落账本，未削弱 `llm_calls` 的真相源地位。
- **C2**：控制面仍不 import `llm-gateway`（`tests/architecture/control-boundaries.test.ts` 通过）。
- **§5.5 预算护栏**：预算仍是最终约束，重试不能绕过它。
