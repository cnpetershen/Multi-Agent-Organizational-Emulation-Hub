# M3.9 — 需求沙盘 / 推广可观测性收尾

> **地位**：M3.1 事件协议的加法式扩展；不新建事件总线。
> **范围**：Document.RequirementAnalyzed / Document.RequirementConfirmed / Document.PromotionGenerated / Document.PromotionConfirmed。
> **验证**：独立 planning + 持久化 `events.jsonl`，真实 DeepSeek 全链路。

---

## 1. 设计

### 1.1 为什么复用 Document 聚合

既有 `EVENT_AGGREGATES` 固定为 14 个聚合，并由 `event-contract.test.ts` 钉住。新增 `Requirement` / `Promotion` 聚合虽然语义自然，但会改变既有协议断言。为保持向后兼容，M3.9 复用已登记的 `Document` 聚合：

| 事件 | Theater stage | 触发 |
| --- | --- | --- |
| `Document.RequirementAnalyzed` | sandbox | 需求分析成功落库后 |
| `Document.RequirementConfirmed` | sandbox | 人工确认产生新 confirmed 版本后 |
| `Document.PromotionGenerated` | promotion | 新推广方案 v1 落库后 |
| `Document.PromotionConfirmed` | promotion | 人工确认产生新 confirmed 版本后 |

事件名表达领域语义，聚合保持既有 14 个。

### 1.2 Payload

**Document.RequirementAnalyzed**

```text
requirementId, version, title
sourceKind: goal | sandbox
analysisMode: live | mock | sandbox | deterministic
inferredFieldCount
analyzedAt
```

**Document.RequirementConfirmed**

```text
requirementId, version, title
confirmedBy, confirmedAt
inferredAcknowledged
```

**Document.PromotionGenerated**

```text
promotionId, version, title
executionId, planId, planVersion, approvalId
generatedAt
provenanceMode
materialCount, channelCount
```

**Document.PromotionConfirmed**

```text
promotionId, version, title
executionId, planId, planVersion, approvalId
confirmedBy, confirmedAt
humanEdits[]
```

时间同时存在于事件信封 `occurredAtSim/occurredAtWall` 与 payload 的 wall-clock 字段；actor 由 `OrgEvent.actorKind/actorId` 记录。

### 1.3 真实性与边界

- Document.RequirementAnalyzed 的 actor 是发起分析的人类操作者；`analysisMode` 明确标记 AI/确定性/沙盘，不把 AI 推导写成用户陈述。
- Requirement.Confirmed 只在人工确认后产生；`inferredAcknowledged` 记录 inferred 字段是否被明确确认。
- Document.PromotionGenerated 记录 AI 生成/来源 mode、材料/渠道数量；不声称 Jack/Peter 执行了任务。
- Promotion.Confirmed 记录人工确认和 humanEdits；没有 Task/AgentMessage 伪造。
- 不为历史数据补造事件；没有新增回填脚本。

## 2. 幂等策略

- 需求分析：每次分析创建新的 requirement（新 id），不会对同一 id 重复写 analyzed。
- 需求确认：已 confirmed 且没有 answers 时服务端直接返回现有版本，不写 confirmed 事件；带 answers 生成新版本时写一条新事件，版本号不同。
- 推广生成：同一 execution 已有 promotion 时直接返回现有方案，不写 generated 事件。
- 推广确认：已 confirmed 的当前版本再次确认抛 `version_conflict`，不会产生第二条 confirmed。
- EventStore 的 `(companyId,eventId)` 唯一约束仍是最后防线；没有引入第二套去重表。

**原子性边界**：事件在业务 store 保存成功后追加；若事件 append 失败，业务数据已保存但事件缺失。当前实现与既有 M3.8 publication 事件一致，未新增事务型 outbox。

---

## 3. 存储与 Theater

- 事件写入既有 `EventStore` / `events.jsonl`，重启时回放。
- 不新增事件总线、订阅器或投影存储。
- Theater 复用既有 stage 映射：Requirement → sandbox，Promotion → promotion。
- Theater 只读；卡片只显示标题、版本、状态，不显示内部 ID/调试信息。
- 既有 `Document.Publication*`、Workflow/Task/Approval 事件不受影响。
- 中英文 Theater 文案同步增加 requirement/promotion 卡片。

## 6. 仍存边界

1. 事件 append 失败时没有 outbox/事务补偿；与既有 M3.8 事件相同的原子性边界。
2. Theater 仍有一个 unclassified 的 channel bookkeeping 事件；它不是业务阶段。
3. 推广事件只描述方案，不声称 Agent 任务；Jack/Peter 仍只是能力匹配。
4. 不进入 M4。
