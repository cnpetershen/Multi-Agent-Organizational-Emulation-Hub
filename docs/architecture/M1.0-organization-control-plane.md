# M1.0 · Organization Control Plane — 设计与复用裁定

> **地位**：M1.0 的实现契约。上游权威：`ARCHITECTURE-BASELINE.md`（§17 Architecture Change Process）→
> `package-registry.md`（包边界）→ `dependency-graph.md`（依赖方向）。冲突时以上游为准。
> 本文件记录 M1.0 的复用裁定与最小新增，供 M1.1 直接对接。

## 1. 目标与非目标

**目标**：让人类操作者能够 **观察 / 控制 / 干预 / 检查 / 审计** 这家已经能自主运行的 AI 公司。

闭环：

```text
Human Operator
  → ControlCommand（带 actor / reason / commandId / expectedVersion）
  → Validation
  → Identity → Permission → Authority
  → 现有 Domain Operation（task-system / workflow-engine / scheduler / event-store）
  → Domain Event（Control.* 为事实）
  → EventStore
  → Audit（commandId 关联）
  → Observation（只读投影）
```

**非目标（M1.0 明确不做）**：Web UI / Dashboard / React；新 Runtime；新 Cognition；新 LLM Provider；
新 Workflow/Task Engine；重写 Permission/Authority；直接写 `AgentState`/`WorkflowState`/`TaskState`；
wall-clock 驱动仿真；`while(true)` 仿真循环；新 simulation-engine 包。

## 2. 现有实现中可直接复用、不得重写的模块

| 能力 | 归属 | 复用方式 | 禁止重写 |
| --- | --- | --- | --- |
| 仿真 start/step/pause/resume/seek/tick/recover/inject | `apps/kernel` `createSimulation` | 控制面**只调用** `Simulation` 已公开方法 | ❌ 不新写仿真循环 |
| SimClock / 唤醒队列 / 预算 | `runtime-scheduler` | `Scheduler.pause()/resume()/seek()/enqueue()`、`createBudgetTracker` | ❌ 不新写调度 |
| Agent 状态机 / 乐观版本 | `runtime-state` | `StateStore.load/commit(expectedVersion)`，冲突码 `VERSION_CONFLICT` | ❌ 不新写版本控制 |
| 权限裁决 | `permission-system` | `AuthzService.can(actor, action, resource, ctx)` | ❌ 不写 `if (isAdmin)` |
| 决策权等级 | `authority-engine` | `AuthorityService.levelFor(employeeId, domain)` | ❌ 不新写等级表 |
| 身份 → ActorContext | `identity-system` | `Identity.actorContext(employeeId, correlationId)` | ❌ 不重构 Identity |
| 组织读模型 | `organization-model` | `createOrgGraph` / `createOrgSnapshot` | ❌ 不新写组织模型 |
| 任务状态机 | `task-system` | `TaskService.create/assign/cancel/review/...` | ❌ 不新写任务状态机 |
| 流程状态机 + 审批门 | `workflow-engine` | `WorkflowEngine.start/approve/gate/cancel/pause(resume)/wait()` | ❌ 不新写审批系统 |
| 事件信封 / 类型注册 | `event-system` | `createOrgEvent` + `EventRegistry.register` | ❌ 不绕过 Registry |
| 事件唯一写入口 | `event-store` | `EventStore.append/replay/isProcessed` | ❌ 不直写数据库 |

### 2.1 已确认的关键事实（来自 M0.1–M0.9 代码核读）

1. `Simulation` 的全部数据字段为 `readonly`，**且不存在 `status` 字段** → `simulation.status = ...` 是编译错误。
2. `Simulation` 暴露 `tick()` / `recover()` / `inject()` / `pause()` / `resume()` / `seek(tickNumber)`，
   以及 `scheduler` / `eventStore` / `stateStore` / `tasks` / `workflow` / `taskStore` / `instanceStore` / `agents`。
3. `Scheduler.paused` 是**纯内存布尔**：不是事件、不跨 `recover()` 存活。M1.0 的 Pause 必须落为
   `Control.SimulationPaused` 事件，使其可审计、可恢复、可观察。
4. `runSimulationTick` 在 `scheduler.paused` 时**提前返回**：不推进时钟、不追加事件、不移动 cursor。
5. 乐观并发既有码为 `VERSION_CONFLICT`（`runtime-state`），**仓库中不存在 `STALE_VERSION`**。
6. `Task.*` / `Workflow.*` 事件**不设置 `causationId`**（为 `null`），因此 Command → Event 的关联
   必须由控制面自己建立（`commandId` 写入 Control 事件 payload，Audit 记录 eventId）。
7. `CommandActor` 只有 `'employee' | 'system'`；**授权链没有 human 分支**。人类操作者必须建模为
   占据真实 `Position` 的 `Employee(kind:'human')`，走同一 `can()` 路径。
8. `parseEventType` 只接受 `EVENT_AGGREGATES` 中已登记的聚合名 → 新增 `Control.*` 事件**必须**登记聚合。
9. `EventStore.append` 对 `(companyId, eventId)` 重复会抛 `DuplicateEventError` —— 这是幂等的最后防线。

## 3. Control Plane 落在哪里

**裁定：新增 `packages/organization-control`，层归属 L6（Application / Control），依赖方向 L6 → 全部下层。**

理由：

- 控制面横跨 Orchestration（task/workflow）、Runtime（scheduler 驱动控制）、Domain（identity/permission/authority）、
  Infrastructure（event-store/audit），没有任何**单一**现有层能承载而不越界。
- 它**不是** L5 编排包：L5 禁止依赖 L4 Runtime，而控制面必须驱动 `runtime-scheduler`。
- 它**不能**是 L4 Runtime 包：L4 禁止依赖 L5 Orchestration，而控制面必须调用 `workflow-engine`/`task-system`。
- `apps/api` 是 HTTP/WS 边缘，其 registry 条款**禁止 `persistence`**，而 Control Plane 的
  command 处理需要经 event-store/audit 的持久化语义 → 领域逻辑不宜放在 `apps/api`。

**边界内含**：命令模型 / 校验 / 授权边界 / 控制服务 / 观察查询模型 / 审计模型。
**边界外**：HTTP 路由、WebSocket、UI（属 M1.1）；kernel 装配（属 `apps/kernel`）。

### 3.1 依赖边（新增，精确）

```text
packages/organization-control
  → shared-types            （类型根）
  → organization-model      （组织读模型）
  → identity-system         （ActorContext 构造）
  → permission-system       （can 裁决）
  → authority-engine        （levelFor）
  → task-system             （任务领域操作）
  → workflow-engine         （流程领域操作）
  → event-system            （信封 + 类型注册）
  → event-store             （唯一写入口）
  → audit-system            （审计）
  → runtime-scheduler       （pause/resume/seek 语义）
  → runtime-state           （AgentState 读取 / 版本）
  → observability           （LLM 成本观察，只读）
```

**明确不依赖**：`llm-gateway`（F6/F7）、`agent-cognition`（F12）、`agent-runtime`（避免成为第二套 Runtime，
亦避免 Agent RPC）、`apps/*`（F1）、`persistence`（经 event-store/audit 端口）。

> **控制面不 import `apps/kernel`**：它通过**注入端口**（`ControlSimulationPort`）驱动仿真，
> 由 `apps/kernel` 作为 composition root 完成装配。这保持 `packages/*` 永不依赖 `apps/*`（F1）。

## 5. Permission / Authority 接入方式

**唯一路径，禁止旁路**：

```text
command.actor.employeeId
  → identity.actorContext(employeeId, correlationId)      // 单一 ActorContext 工厂
  → validateActorLegitimacy(organization, actorContext)    // 预检
  → authz.can(actorContext, controlAction, resource, { domain, requiredRoles })
       ├─ allow:false + NO_PERMISSION/OUT_OF_SCOPE → UNAUTHORIZED / FORBIDDEN / OUT_OF_SCOPE
       └─ allow:false + NEEDS_APPROVAL             → Command 不得直接执行
  → authority.levelFor(employeeId, domain)                 // 决策权下限校验
  → 领域操作
```

`shared-types.ACTIONS` 新增 5 个控制动作（复用既有 Action 联合，不另造权限体系）：

| Action | 适用 resource 形态 |
| --- | --- |
| `ControlSimulation` | `simulation:<companyId>` |
| `ControlAgent` | `agent:<employeeId>` |
| `ControlWorkflow` | `workflow:<instanceId>` |
| `ControlTask` | `task:<taskId>` |
| `InjectOrganizationInput` | `organization:<companyId>` |

`minAuthority` 由 `PermissionRule` 既有的 `PermissionAuthorityThreshold` 表达（例如 Pause Simulation 需 `org` 域 ≥ L4），
`permission-system` 已有的阈值判定会给出 `NEEDS_APPROVAL(escalateTo)` → 控制面保留该语义为独立错误码
`NEEDS_APPROVAL`，并把它变成人类审批入口（`getPendingApprovals()`，见 §7.4）。

**人类操作者**：`Employee(kind:'human')` 占据真实 `Position`（含 `decision_domains`），因此
`AuthzService.can` 的 `employee.positionId !== actor.positionId` 校验自然通过，无需修改 `AuthzService`。

**校验顺序（冻结）**：

```text
1. 信封结构校验（validateCommand）           → INVALID_COMMAND / INVALID_TARGET
2. 幂等命中（audit.find(commandId)）         → 返回首次结果（replayed: true）
3. 操作者身份（identity.actorContext）       → UNAUTHENTICATED
4. 操作者合法性（validateActorLegitimacy）   → UNAUTHENTICATED（停职/越岗/跨公司在此拦下）
5. 操作者自述岗位一致性                       → OUT_OF_SCOPE
6. 权限 + 决策权（AuthzService.can）         → UNAUTHORIZED / OUT_OF_SCOPE / NEEDS_APPROVAL
7. 乐观并发（expectedVersion）               → STALE_VERSION
8. 领域操作（TaskService / WorkflowEngine / Scheduler / EventStore）
```

注意：`validateActorLegitimacy` 在 `can()` **之前**执行，因此停职操作者得到的是 `UNAUTHENTICATED` 而非
`UNAUTHORIZED` —— 两者都是 fail-closed，顺序本身是契约的一部分。

## 6. 错误模型（fail-closed）

**复用既有，不重复定义**：

- `AuthzDenialReason` = `'NO_PERMISSION' | 'OUT_OF_SCOPE' | 'NEEDS_APPROVAL'`（`permission-system`）
- `VERSION_CONFLICT`（`runtime-state`，即需求所称 STALE_VERSION）
- `TaskErrorCode` / `WorkflowErrorCode` 既有成员（`unknown_task` / `unknown_instance` / `instance_blocked` / …）
- `event-store` 的 `DuplicateEventError`

**控制面新增（仅补齐既有体系缺失的语义）**：

```text
UNAUTHENTICATED   INVALID_COMMAND   INVALID_TARGET   STALE_VERSION
ALREADY_PROCESSED INVALID_STATE     NOT_FOUND        CONFLICT
BUDGET_EXCEEDED   SIMULATION_PAUSED AGENT_PAUSED     WORKFLOW_BLOCKED
UNAUTHORIZED      FORBIDDEN         OUT_OF_SCOPE     UNSUPPORTED
```

`ALREADY_PROCESSED` 对应幂等命中（返回首次结果，`replayed: true`）。
`NEEDS_APPROVAL` 是唯一「不是拒绝、而是升级」的码：语义直接继承 `permission-system` 的 `NEEDS_APPROVAL(escalateTo)`。

### 6.1 拒绝也是事实，且必须一致

**契约（冻结）**：任何可表达的拒绝都恰好产生一条 `Control.CommandRejected` 事件
（`payload` 携带 `commandId` / `commandType` / `targetType` / `targetId` / `resultCode` / `issues`），
**且不产生任何事实事件**。结构性校验拒绝与授权/并发/状态拒绝走**同一条**路径。

实现上不硬编码信封前置条件：`Control.CommandRejected` 的 payload schema 对描述性字段宽容
（可空、可缺省、`resultCode` 可省），因此**即使命令自身字段非法，拒绝本身仍然可记录** ——
这正是「最需要留痕」的时刻。事件能否成立由 `EventRegistry` 的注册契约单独裁决。

## 7. 幂等 / 并发 / 恢复

### 7.1 幂等

`commandId` 是幂等键。控制面在**执行授权之前**先查 Audit：

```text
findAuditByCommandId(commandId)
  ├─ 命中且 verdict ∈ {accepted, rejected, failed} → 返回首次结果（replayed: true），不重复执行
  └─ 未命中 → 正常执行
```

同一 `commandId` + 不同 payload → `CONFLICT`。

### 7.2 乐观并发

`expectedVersion` 按目标聚合读取：

| 目标 | 版本来源 |
| --- | --- |
| Simulation | `Scheduler.clock.currentTick` |
| Agent | `StateStore.load(employeeId).version`（既有 `VERSION_CONFLICT` 语义） |
| Workflow | `WorkflowInstance.processedEventIds.length`（该聚合无独立版本号，`version` 是流程**定义**版本） |
| Task | 该任务的事件计数（`Task` 无版本字段） |

不匹配 → `STALE_VERSION` + `actualVersion`，**绝不 last-write-wins**。
Workflow / Task 的版本代理是对现状的显式适配，不假装存在聚合版本号。

### 7.3 恢复

Audit 是**审计记录，不是第二个 EventStore**（BASELINE §14）。恢复语义：

- 事实来源仍是 `EventStore`：`Control.*` 事件已在流中 → 可重放。
- **接受**的命令产生 `Control.*` 事实事件；**拒绝**的命令产生 `Control.CommandRejected`
  （payload 携带 `commandType` / `targetType` / `targetId` / `resultCode` / `issues`）。
  二者共同使「谁试图做什么、系统如何答复」完全可从事件流重建。
- 组合根（`apps/kernel`）启动时执行 `recoverControlPlane(control, audit, eventStore)`：
  1. `rebuildAuditFromEvents` —— 从 `Control.*` 折叠出审计记录（每个 `commandId` 恰好一条，
     接受方优先），使 `commandId` 幂等与审计轨迹跨重启存活；
  2. `control.hydrate(events)` —— 重建控制面内存投影（simulation paused / paused agents），
     使 `Simulation.Pause` 与 `Agent.Pause` 跨重启存活（`Scheduler.paused` 本身仍是纯内存态）。
- kernel 的 `recover()` 只折叠 `Task.` / `Workflow.` / `Runtime.` 事件，**不认识 `Control.*`**，
  因此对 M0.9 恢复路径零侵入。`Control.*` 事件也不参与唤醒（`NON_WAKEUP_PREFIXES` 含 `Control.`）。
- 两套折叠都按 `eventId` 去重，恢复可重复执行且不产生重复记录。

### 7.4 人类审批入口

`permission-system` 已经能回答「你有这个权限，但你的决策权不够 —— 去找这个人」。
控制面**不重建审批系统**，而是把该判定变成可执行入口：

```text
Agent/Operator Command
  → AuthzService.can(...) = NEEDS_APPROVAL(requiredAuthority, escalateTo)
  → Control.CommandRejected { resultCode: 'NEEDS_APPROVAL' }（事件，可重放）
  → Audit.details { requiredAuthority, escalateTo }
  → query.getPendingApprovals() → PendingApprovalView[]
  → 有权者重新下达同一条命令（或走既有 Workflow.Approve 门）
```

`Workflow.Approve` / `Workflow.Reject` 仍然复用 `WorkflowEngine.approve` 的 `required_roles` 与
`requiredAuthority` 双重校验：人类能审批，**只因为他真的占着那个岗位角色**，不是因为他是人类。

## 8. 观察模型（只读，不调 LLM）

```text
organization-control.query
  getOrganizationSnapshot()      getDepartments()      getEmployees()
  getAgents()                    getAgent(agentId)     getAgentRuntimeState(agentId)
  getAgentActivity(agentId)      getWorkflows()        getWorkflow(instanceId)
```

`occurredAtSim` 区间 —— 全部映射到 `EventStore.replay(from, to, filter)` 与内存筛选，**不调 LLM**。

## 9. Agent / Workflow / Task / Simulation 控制流程

### 9.1 Simulation Control

```text
Command:Simulation.Pause
 → Identity/Permission/Authority（ControlSimulation on simulation:<companyId>）
 → 幂等检查 / expectedVersion(=currentTick)
 → 状态校验（未运行 → INVALID_STATE）
 → scheduler.pause()                       ← M0.9 既有能力
 → append Control.SimulationPaused
 → Audit(accepted)
```

`Simulation.Step` = 执行 `Simulation.tick()` 一次（**在 paused 时也可单步**，属显式授权行为）。
`Simulation.Seek` = `Scheduler.seek(clock.at(tick))`；**不修改历史 EventStore**，`fromTick > toTick` 时
按当前 M0.9 能力返回 `UNSUPPORTED`（不伪造 rollback）。

### 9.2 Agent Intervention

| 命令 | 落地 |
| --- | --- |
| `Agent.Pause/Resume` | 控制面 paused-agents 投影 + `Control.AgentPaused/Resumed` 事件；`eligibleAgentsFor` 经注入的 `ControlStateReader` 排除被暂停 Agent（不暂停整个 Simulation） |
| `Agent.Instruct` | 产出 `Control.AgentInstructed` → `HumanInput` 语义事件；由既有 `eligibleAgentsFor`/Scheduler 唤醒该 Agent（复用 `WakeRequest.reason='MANUAL'`），**不直接调用 Cognition** |
| `Agent.CancelTask` | 委派 `TaskService.cancel({ taskId, actor })` |
| `Agent.RequestReview` | 委派 `TaskService.review(...)` |

### 9.3 Workflow / Task Intervention

| 命令 | 落地（复用既有领域操作） |
| --- | --- |
| `Workflow.Pause/Resume` | `WorkflowEngine.wait()` / `WorkflowEngine.resume()` |
| `Workflow.Cancel` | `WorkflowEngine.cancel()` |
| `Workflow.Approve/Reject` | `WorkflowEngine.approve({ decision:'granted'|'denied' })` |
| `Workflow.gate` 检查 | `WorkflowEngine.gate()`（只读，用于 Inspect） |
| `Task.Cancel` | `TaskService.cancel()` |
| `Task.Reassign` | `TaskService.assign()` |
| `Task.RequestReview` | `TaskService.review()` |
| `Workflow.Delete` | `WorkflowEngine.delete()`（**投影删除**：先整实例 `RejectStep` + 逐任务 `RejectTask` 全量预授权，再级联 `Task.Deleted` → `Workflow.InstanceDeleted`，折回 `null` 自检通过后实例记录离店） |
| `Task.Delete` | `TaskService.delete()`（**投影删除**：任意状态可删、流折回 `null`；打在工作流拥有的任务上 → 级联删除整只实例，走 `WorkflowEngine.delete()` 同一条预授权路径） |

> **删的是投影，不是事实**：两条删除命令只让记录离开存储（重启回放重建为空），`Task.Deleted` /
> `Workflow.InstanceDeleted` / 控制面审计全部**留在事件流上**——与 05-runtime「事件 append-only、
> 不可原地修改」不冲突：事实一条没动，可删的是物化出来的当前态。

### 9.4 Organization Input

`Organization.InjectTask` → `TaskService.create()`（写入正常任务流，由 Scheduler 唤醒）。
`Organization.InjectEvent` → `createOrgEvent` + `EventStore.append()`（**永远经 EventStore**，
绝不绕过 Scheduler/Runtime/Workflow/Task 直接驱动 Cognition）。

## 11. 已知限制（不在 M1.0 伪造）

1. `SimClock` / `paused` / 唤醒队列在生产实现中仍是内存态；跨进程恢复依赖 `EventStore` 替换为持久实现。
   控制面的 `Control.*` 投影与审计轨迹**已可跨重启重建**，但 M0.9 的唤醒队列本身仍会清空并依据未消费事件重新推导。
2. `seek` 只对齐时钟，**无历史回滚**；向后 seek 返回 `UNSUPPORTED`。
   「非对齐 tick」在当前入口**不可达**：端口调用 `clock.at(tickNumber)`，对齐由构造保证；命令层只能表达
   非整数 tick，由 `INVALID_COMMAND` 拒绝。这是能力边界，不是缺陷，但也不能被当成已覆盖的用例。
3. `Task.*`/`Workflow.*` 事件的 `causationId` 仍为 `null`（既有引擎行为）；控制面通过
   `Control.*` 事件 payload 的 `commandId` 与 Audit 建立关联，不修改既有引擎。
4. `Budget` 上限在仿真实例内不可变（`resolveSimulationConfig` 冻结）。
5. 单次 `tick()` 不可中断、无超时；控制面不提供 tick 取消。
6. `Task` 与 `WorkflowInstance` 无聚合版本号，`expectedVersion` 对二者退化为事件计数代理（§7.2）。
7. `Organization.InjectTask` 派发到岗位后 `assigneeEmployeeId` 可能为 `null`（`task-system` 的既有语义：
   岗位当前无人则留空）。控制面不收紧该行为。
8. 人类操作者必须**显式登记**为占据真实岗位的 `Employee(kind:'human')` 并授予控制权限；
   默认策略（`defaultControlPolicy()`）只授予 `board-operator` 岗位，未配置时一切控制命令 fail-closed。
9. 控制面自身的策略不是"管理员白名单"：它**只**表达 `Action × Resource` 授权，
   决策权阈值仍由 `authority-engine` / `PermissionRule.minAuthority` 裁决。
