# M2.1 — Assignment studio and delivery package

Status: CURRENT (implementation contract)
Depends on: BASELINE, registry, dependency-graph, M1.4, M1.6, M1.8, M1.9, M2.0

## 1. Why this layer exists

M1.8 put assignment overrides on the canvas, but the page still read like a form: a roster,
stage columns and a diff modal. M2.0 gave the company a network view and a delivery theatre.
The next visual pass had to answer two owner questions without changing the domain:

1. *What exactly did the CEO arrange, and how do I put a different teammate on one step before
   it starts?*
2. *What did the company hand over as one package — the game, the document, the 3D asset and the
   files together — and why was a preview missing?*

Both are **presentation** problems. No new command, event, endpoint or persistence was added.
The command path is unchanged:

```
Workflow.InstanceAssignmentOverride  (whole batch, fail-closed)
Workflow.ConfirmStart                 (draft → running)
```

The kernel still re-checks employment, required roles and authority before writing anything.

## 2. Assignment studio

### 2.1 Pure projection

`apps/web/src/assignment-canvas.ts` owns parsing and geometry only:

- `parseAssignmentInstances(rows)`: one instance per `/api/workflows` row that has steps; drafts
  first, then live work, then history, and within a rank the richer step count wins so the page
  does not open a one-step hiring gate when a five-step product exists.
- `parseAssignmentEmployees(employees, positions)`: executable roster, capabilities merged from
  the position and the employee's own expertise; `defined` is executable (the CEO is on the team
  and can hold an approval/step).
- `buildAssignmentGraph(instance, { staging, selectedStepId })`: deterministic vertical node
  positions, one edge between neighbours, stage bands, tone per status/draft, staged assignee.
- `isAdjustableStep`: only a `pending` `task` step can be pinned. An entered or approval step is
  shown as locked.

The page never derives organization truth from the graph; it only renders the rows it already
reads. The staging map is local UI state and is discarded when the instance changes.

### 2.2 Surface

`apps/web/src/pages/WorkflowCanvas.tsx` is now a dark studio:

```
┌──────────────────────────────────────────────────────────────────────┐
│ CEO ORCHESTRATION · workflow title · DRAFT / status · instance select│
├──────────────┬───────────────────────────────────────┬───────────────┤
│ team palette │ vertical node graph + stage rail      │ node inspector│
│ search       │ nodes · curved edges · live tone      │ seat / caps   │
│ drag cards   │ drop target on pending task steps     │ SoD / checks  │
├──────────────┴───────────────────────────────────────┴───────────────┤
│ staged count · reason · confirm / discard                            │
└──────────────────────────────────────────────────────────────────────┘
```

- **Drag** a team card onto a pending task node, or **tap** a teammate and then the node.
- The inspector also has an explicit employee select, so keyboard/small-screen use does not
  depend on HTML5 drag events.
- Selecting a node opens its facts: stage, capability, required roles, authority, status,
  effective assignee, staged/pinned badge and SoD warning.
- A draft shows the "CEO arranged this plan" banner and a confirm action; confirming with zero
  changes is the same action as before (`Workflow.ConfirmStart` only).
- A completed instance shows a read-only state, and every lock has a reason.

`apps/web/src/canvas.css` is the studio skin (dark theatre, mint/cyan/amber tones, stage rail,
node tone variables). The old `.canvas-board` class is retained because the operator-loop e2e
uses it as the page's readiness marker.

### 2.3 Accessibility and motion

- Nodes are `role=button` + keyboard activation only when editable; locked nodes stay readable
  but are not focus targets.
- The studio does not depend on animation: edges draw statically; `prefers-reduced-motion`
  removes the flow dash animation and card transitions.
- The page keeps the same `PageIntro` and shell vocabulary as the rest of the console.

## 3. Delivery package

### 3.1 One model, all steps

`apps/web/src/delivery-package.ts` folds the whole workflow into one model:

- `buildDeliveryPackage(workflow, anchor, records)` includes every `stepStates` task, always the
  anchor, and deduplicates by task id. It flattens `PackageFile` records with their step and task
  titles.
- `packageKindOf` classifies a delivered task as `game`, `3d`, `document`, `code` or `report`.
  Game wins over code; a 3D model file or a 3D HTML scene wins over a document.
- `deliveryPackageGroups(tasks, workflows)` groups the Deliverables workspace by workflow and
  adds standalone completed tasks as packages of one; the card opens the package anchor.
- `packageTaskIds` is the fetch list; `useTaskRecords` uses `Promise.allSettled` so one broken
  sibling cannot hide the rest.

### 3.2 The package surface

`apps/web/src/components/DeliveryPackage.tsx` sits on the delivery page above the live
`PreviewPanel` (which is wrapped in `#result-preview`):

- **Game slot** — a deliberately stylised board, a "run the live preview" action that scrolls to
  the one real preview runtime, and a link to the game's own delivery page.
- **Document slot** — the existing `DocumentPreview` sheet, rendered in a bounded scroll stage.
  Markdown is parsed into an AST (no `innerHTML`), HTML documents run in a `sandbox=""` frame.
- **3D slot** — `Model3DViewer` for a delivered `.obj`/`.stl` (wireframe, perspective projection,
  auto-rotation, reduced-motion aware); a 3D HTML scene links to the live preview. A `.glb`/`.gltf`
  is still listed as a 3D asset with format and download, but the UI does not pretend to render a
  binary it has not parsed.
- **Files slot** — every file grouped by step, individual download, and a real **Download all
  (.zip)**.

The package never starts a second preview server. There is one runtime and one truth; the game
slot is a map to it.

### 3.3 ZIP and 3D readers

- `apps/web/src/zip.ts` is a store-only ZIP writer (local headers, central directory, end record,
  CRC-32, UTF-8 names, fixed DOS timestamp). It is a dependency-free implementation of the
  container, not a concatenated blob; the unit test pins signatures, stored bytes and CRC.
- `apps/web/src/model3d.ts` reads ASCII OBJ (`v`/`f`) and ASCII STL (`vertex` triplets), refuses
  empty meshes, and normalizes the result for the viewer. Unsupported formats return `null` so
  the placeholder can be honest.
- `apps/web/src/components/Model3DViewer.tsx` draws the normalized edges on a 2D canvas with a
  real perspective projection; `prefers-reduced-motion` stops the rotation at one frame.

### 3.4 Deliverables page

The Deliverables page now opens with **Delivery packages** — dark package cards grouped by
workflow (and standalone deliveries) — before the existing task workspace. Each card opens the
anchor's delivery page, where the package above shows the game/document/3D/file slots.

## 5. Known limits

- **3D scope**: OBJ/STL text models render; binary glTF/FBX are listed but not parsed. A 3D HTML
  scene is previewed by the existing runtime, not by a second 3D engine.
- **ZIP scope**: store-only (no compression), text entries, built in the browser; it is a
  convenience for a delivery package, not a replacement for an artifact service.
- **Package fetch**: sibling records are read client-side with one request per task. A future
  backend package endpoint could replace that, but it would be a new read model and is out of
  scope for this presentation pass.
- **Preview lifetime**: the package links to the existing `PreviewPanel`; the runtime still owns
  start/stop and the detached child process. A failed start is recoverable from that panel.
- **Full-suite flake**: `preview-runtime-http` can time out under 155 parallel workers; the
  `--maxWorkers=4` run is the recorded green configuration.

## 6. Revisit triggers

- The assignment studio needs **branch transitions** (the current graph infers a linear order from
  `steps`; a real DAG editor needs the definition's transitions in the read model).
- Drag needs to persist node positions or support multi-select.
- A package needs to be **served/downloaded by the API** rather than assembled in the browser.
- Binary 3D or texture-bearing formats become a first-class delivery type.
- The package needs compression or very large files (move ZIP generation server-side).
