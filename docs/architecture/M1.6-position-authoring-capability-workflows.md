# M1.6 · Position Authoring & Capability Workflow Generation（岗位作者化与能力工作流生成）

> 状态：**CURRENT**（实现契约，代码已落地）
> 从属：`ARCHITECTURE-BASELINE.md`（最上位）、`package-registry.md`、`dependency-graph.md`、`M1.0-organization-control-plane.md`、`04-agent-lifecycle.md` §4.10、`03-data-model.md` §3.2.1
> 一句话：**能力挂在岗位上，流程由能力生成** —— 操作者可以边招人边建岗（部门 + 打字输入的新职位），CEO 分析目标得到能力清单，组织按 `Position.capabilities` 找坑派活，**任何环节都不读岗位名字**。

---

## 1. 目标与非目标

### 1.1 目标

1. **建岗作者化**：`Agent.Create` 允许操作者选择「已有部门 + 已有岗位」，或选「已有部门 + 打字输入新职位」（如 `Engineering / Game Developer`），命令原子地创建岗位并雇人。
2. **能力词表**：岗位声明它提供哪些能力（`product_requirement` / `technical_design` / `implementation` / `testing` / `marketing`），这是路由的**唯一**依据。
3. **目标分析**：CEO（或其认知层）把一段目标文本分析成能力清单，交给引擎生成工作流；没有显式线索时回退到核心交付链。
4. **生成工作流**：引擎按能力顺序生成「一步一能力 + 根岗位审批收尾」的 `WorkflowDefinition`，与磁盘模板走**同一条**启动/推进/审批路径。
5. **可回放**：生成用的 *capability plan* 写进启动事件，重启时按 plan 再生成同一个定义 —— 定义是派生状态，plan 才是事实。

### 1.2 非目标

- **不做岗位名字匹配**：`"Game Developer"` 与 `engineer` 岗位只有在都声明 `implementation` 时才等价；名字只用于展示。
- **不新建部门**：命令只加*岗位*，部门必须已存在（`unknown_department`）。
- **不给岗位配删除命令**：建错的岗位留下，靠归档员工 + `Task.Reassign` 处理空坑。
- **不把流程藏进 Prompt**：生成的工作流是显式定义与事件，认知层只负责产出 `{capabilities}` 参数。
- **不在引擎里做质量判断**：能力解析是确定性纯函数（组织模型），无 LLM；判断归 Agent。

## 2. 能力词表（`organization-model/capability/vocabulary.ts`）

| id（= 岗位标签） | label（步骤名） | 双语线索（仅用于**分析目标文本**） |
| --- | --- | --- |
| `product_requirement` | Product Requirement | requirement / prd / spec / brief / 需求 / 规格 |
| `technical_design` | Technical Design | design / architecture / technical / 方案 / 架构 |
| `implementation` | Implementation | develop / build / implement / code / demo / 开发 / 编码 |
| `frontend` | Frontend | frontend / web / website / page / ui / 前端 / 官网 / 网站 / 网页 / 页面 |
| `backend` | Backend | backend / api / server / service / database / 后端 / 服务端 / 接口 / 数据库 |
| `testing` | Testing | test / qa / verify / validation / 测试 / 验证 |
| `marketing` | Marketing | marketing / campaign / growth / 营销 / 增长 |

- `CORE_CAPABILITIES` = 交付弧四项（`product_requirement / technical_design / implementation / testing`），是「指令含糊」时的回退；`frontend` / `backend` / `marketing` 是**显式线索**，不进回退链。回退链是**写死的常量**而不是「词表减去 marketing」——词表开放且会继续增长，新增一个专精标签不得悄悄改变含糊指令所排的工作。
- `analyzeCapabilities(text)`：英文线索按**词边界**匹配（`\b…\b`，避免 `spec` 命中 `specific`），中文按子串；按词表顺序返回，可能为空。
- `requiredCapabilitiesFor(text)`：有命中就用命中，否则回退 `CORE_CAPABILITIES`，**永不为空**。
- 线索只做文本分析；**匹配永远是 id 精确比较**。线索不出现在岗位匹配路径里。

## 3. 能力 → 岗位解析（`organization-model/capability/resolve-capabilities.ts`）

`resolveCapabilityAssignments(org, capabilities, options?)` 逐能力求解，规则按序：

1. **声明式匹配**：候选 = `Position.capabilities` 含该 id 的岗位（`includes`，不看 title/key）。
2. **有人的坑优先**：沿 `reports_to` 链找最近的**有人**（employee 非 `offboarded`）祖先；候选键 = `depth（到有人坑的距离）→ authority → id`，全序确定。
3. **空坑升迁**：全部空缺时沿链上升到最近有人的管理者；整条链都没人时才返回空坑本身（任务留在岗位上，等 `Task.Reassign`）。
4. **没人会的直接丢弃**：`capabilities` 中无任何岗位声明的项被省略；结果为空 = 「这个组织干不了这个活」，调用方**不得**启动工作流（空流程 = 幻影工作）。
5. **排除席位**（`options.excludeSeatIds`，只给**拼计划的那条路**用）：列出的席位既不做候选，也在升迁链上被跳过；当它是唯一能承接的人时，该能力被省略（计划诚实地少一步），而不是把活派回刚把它派出去的人。

输出 `CapabilityAssignment { capability, matchedPositionId（自然归属）, positionId（实际承接）, escalated }`。

### 3.1 员工专长 `Employee.expertise`：第二条（person-level）匹配路线

岗位能力回答「这个坑归谁干」，**个人专长**回答「这个人特别擅长什么」。两者正交，都存在同一个 `CapabilityProfile` 上：

| 字段 | 来源 | 语义 |
| --- | --- | --- |
| `capabilities` | `Position.capabilities` | 座席提供的能力（路由契约，**默认**路线） |
| `expertise` | `Employee.expertise` | 个人细粒度专长（`typescript` / `react` / `seo` / `pytorch` …） |

- **匹配是双路线**：一条需求能力被满足，当且仅当「座席声明了它」（含空坑升迁）**或**「候选人的 expertise 含它」。第二条路线是 person-level 的，**不参与**空坑升迁——它只会**扩大**可被召唤的人，不会凭空造出座席。
- **评分只由覆盖数决定，与路线无关**：`matchedCapabilities 数量 × 10 + 部门匹配 5`，因此「座席持有者」与「专精者」在同一把尺子上比较；`expertiseMatched` 单独记录哪些能力是靠个人专长覆盖的，供审计与 UI 说明「为什么是他」。
- **`matchedCapabilities` 恒按需求顺序**输出（两条路线合并后统一排序），因此日志里「匹配了哪些能力」的表达稳定，不随哪条路线先命中而变。
- **可回放**：`Agent.Create` 命令与 `Control.AgentCreated` payload 携带可选 `expertise`；缺省时**仅当模板正是该坑现任**才继承其专长。`templateFor` 还会经「同部门 → 首位已部署 Agent」兜底取到一个**结构**模板，借它的 memory/tool policy 是对的，借它**那个人的**专长是错的（starter 公司只有 CEO 一个员工时，这条兜底曾把 CEO 的 `strategy` 复制给每一个新员工）。`recover()` 的 `projectAgentRoster` 读回它并重新落进 `Organization.employees`——个人专长与岗位能力一样，是**事件日志上的组织状态**（A3）。
- 加载边界统一归一化（trim / 小写 / 去重 / 保序），种子 YAML 与运行期创建两条路径结果一致。

## 4. 命令契约：`Agent.Create` + `newPosition`

```ts
AgentCreateCommand {
  employeeId, name, positionId, responsibilities[], …        // 既有
  newPosition?: {                                             // 新增
    departmentId: string;                                     // 必填，≤128
    title: string;                                            // 必填，≤120
    capabilities?: string[];                                  // 每项非空 ≤64
    reportsToPositionId?: string | null;                      // 缺省 = 部门 headPositionId
  };
}
```

- **结构校验先于一切**（`organization-control/validation.ts`）：字段缺失/超长 → `INVALID_COMMAND`，issue 指到 `newPosition.<field>`；API 边缘不做第二套 schema，原样透传给控制面校验。
- **语义（Runtime，`simulation.ts:materializeAgent`）**：
  1. 无 `newPosition` 且 `positionId` 不存在 → `unknown_position`；有 `newPosition` 且 `positionId` 已存在 → `duplicate_position`；
  2. `buildRuntimePosition` 纯函数构建：部门不存在 → `unknown_department`；id 撞车 → `duplicate_position`；`capabilities` trim + 小写 + 去重；
  3. **先建岗、后走既有装配**，`refuse()` 补偿：后续任一步失败都把岗位行弹出（员工行同样弹出），不产生「半个 Agent」——装配原子性（04 §4.10.3 规则 1）扩展到岗位行。
- **错误码映射**（`service.ts:fromLifecycleFailure`）：

| lifecycle code | 控制面 failure | field |
| --- | --- | --- |
| `unknown_department` | `INVALID_TARGET` | `departmentId` |
| `duplicate_position` | `CONFLICT` | `positionId` |
| `unknown_position` | `INVALID_TARGET` | `positionId` |

- **事件**：`Control.AgentCreated` payload 增可选 `position { departmentId, title, capabilities[], reportsToPositionId }`（zod optional）。这是**新建岗位的事实**，随日志回放。
- **读侧**：`PositionSummary.capabilities` 暴露给控制台查询。

## 5. 能力 → 工作流生成（`workflow-engine/workflow-generation.ts`）

`buildCapabilityPlan(org, capabilities)` → plan（空则 issue `capabilities` 拒绝）→ `generateWorkflowDefinition({instanceId, title, goal, plan, approvalRoles})`：

- **id**：`generated-<instanceId>`；≤64 直接用，超长走 FNV-1a 稳定摘要（`generated-<8位hex>`）——同一 instanceId 重放必得同一 id（事件 `idSchema` 上限 64）。
- **形状**（顺序 = 能力请求顺序，阶段名取**词表 label**，不取岗位名）：

```text
stage-1 … stage-n   各 1 个 task step（verification: null → evaluateVerification 即通过）
                    assignment = { kind: 'position', positionId: 解析出的坑 }
stage-approve       step-approve，requiredRoles = 组织根岗位 id（CEO 坑）
                    单独/单次批准； rejected|denied → fail，granted → complete
cyclePolicy: forbid · entryStageId: stage-1 · terminalStageIds: [stage-approve]
```

- 定义落库前过一遍 `validateWorkflowDefinition`（防御性：生成器自测之外的兜底）。
- **plan 入上下文**：`CAPABILITY_PLAN_CONTEXT_KEY = 'capabilityPlan'` 写进实例 context —— 它是随 `Workflow.Started` 事件持久化的事实。

## 6. 启动双路径与授权（`workflow-engine.ts` `start()`）

`WorkflowStartInput = { workflowId? , capabilities?, title, goal, actor, simTime, … }`：

| 路径 | 进入条件 | 顺序 |
| --- | --- | --- |
| 模板 | `workflowId` 给定 | 既有行为逐项保留：定义缺失 → title/goal issue → validateActor → 授权 `workflow:<id>` → instanceId → 重复实例 → `beginInstance` |
| 能力 | `capabilities` 给定 | instanceId 生成 → 空/重复检查 → `buildCapabilityPlan` → `generateWorkflowDefinition` → `validateWorkflowDefinition` → `definitions.save` → issues → actor → 授权 → `beginInstance({…context, …capabilityPlanContext(plan)})` |

- 两条互斥：都缺 → `invalid_input`（模板路径要求 `workflowId`）。
- **授权复用既有授权**：生成的 `workflow:generated-*` 资源经 `AuthzService.can(…, CreateProposal, 'workflow:…')`；操作者岗权限表（`simulation.ts DEFAULT_AGENT_POLICY`）已覆盖 `workflow:*`，无需新策略。
- `plan-executor.ts` 的 `workflow.start` 绑定同时接受 `args.workflowId` 与 `args.capabilities`（`readString` / `readStringArray`，缺参 = 空 → `invalid_input`）。
- **模板任务步一律声明能力**（4 个模板同一条契约）：`workflows/*/workflow.yaml` 的 `kind: task` 步只写 `assignment.kind: capability`，只有审批门写 `required_roles`。把任务步钉在 `position_id` 上等于绕过「能力 → 岗位」这条唯一路由——`product-analysis` 的入口/交付步与 `hiring` 的写需求/发 offer 两步就是这么固定交给 CEO 的，于是每个实例都由 CEO 执行。`workflow-definition.test.ts` 把这条钉在定义层，并顺带断言**每个声明的能力在种子组织里都有席位承接**（否则模板要到启动那一刻才发现开不起来）。
- **能力解析要不要排除启动者**：能力路径（`startCapabilities`）排除「写这个 plan 的席位」——没人执行自己派出去的活；模板路径（`assignmentSeat`）**不排除**，因为模板是被启动的、不是被拼出来的，排掉按下启动键的人会让只有一个员工的公司连模板都开不起来，也违背「空坑由上级兜底」这条既有规则（那条路的产物仍然对 `Task.Reassign` 可见）。两条对照由 `capability-start.test.ts` 钉死：四个模板都能启动、入口任务都不落到派活的 CEO 手上、只有 CEO 一个员工时模板仍以 CEO 兜底启动。

> **与 `02-modules.md` §2.4 的关系**：该节 `start(templateId, ctx): Promise<InstanceId>` 是早期规格伪码（实现早已返回 `Result<WorkflowOperation, WorkflowFailure>`）。M1.6 把真实签名固定在本文 §6；规格行以注释指向本文，**不静默择一**。

## 7. 重启再生成（`kernel/simulation.ts recover()`）

实例循环中：回放得到的实例若 `definitionStore.get(instance.workflowId) === null`，用事件 context 里的 plan 调 `regenerateWorkflowDefinition(instance, rootPositionIds)` 重新生成并落库。前提：

- plan 携带**已解析**的 `positionId`（不是裸能力），重启后不重新求解，避免组织变更导致定义漂移；
- 根岗位 id 在运行期不变化（`recover()` 在 `projectAgentRoster` 之前跑）；
- 模板定义从磁盘加载，不受影响。

## 8. 控制台 UI（`apps/web`）

- 岗位下拉新增哨兵项 `__new_position__`（`positionNew` 文案）：选中后展开「部门选择 + 职位名输入 + 能力勾选」。
- 能力勾选（`CAPABILITY_IDS` + `CAPABILITY_LABEL_KEYS`）至少 1 项，否则本地阻止提交（`newPositionRequired` / `newPositionRequiredDetail`）。
- 提交把 `newPosition` 透传 `createAgent`；成功后重置表单态；服务端错误照旧按 failure.field 回显。
- i18n：en/zh 键位对齐（`tests/unit/web/i18n.test.ts` 强制），新键 positionNew / department / selectDepartment / positionTitle / capabilities* / capabilityLabels.*。
- **能力与专长标签**：人员卡片的岗位能力 chips 之外，另起一行显示该员工的**个人专长**（`agents.person.expertise`）；Agent 档案（详情）分列「岗位能力」与「个人专长」两项。`CAPABILITY_IDS` / `capabilityLabels.*` 增加 frontend / backend，因此新建岗位与任务派发的勾选框同步扩展。未知标签原样显示（`capabilityLabel` 直通），控制台**不会**为它编造文案。

## 9. 认知层（LLM 侧）

- **确定性认知**（`apps/api/deterministic-cognition.ts`）：`Agent.Instructed` → `requiredCapabilitiesFor(instruction)` → `CreateProposal` args `{capabilities}`（不经 LLM 判断路由）。
- **LLM 认知提示**（`agent-cognition/prompts`）：`## Organization` 段列出每个岗位的 `Position capabilities:`；`## Plan conventions` 明确 `{workflowId}`（跑既有模板）与 `{capabilities}`（请求生成工作流）两套 `CreateProposal` 参数，禁止按岗位名派活。

## 11. 已知限制

1. **岗位不可删**：`newPosition` 只增不减；建错的坑靠归档员工后留在组织里（防空指针与事件回放一致性）。
2. **词表双层松紧**：分析侧词表封闭（7 项：交付弧四项 + `frontend` / `backend` / `marketing`）；岗位侧标签开放（任意 tag 可写），但未知 tag 永不被目标分析命中 —— 显式 `capabilities` 请求同理，解析不到就丢弃。
3. **生成定义不可复用**：每个实例一份定义（`generated-<instanceId>`），不提供「存成模板」；要复用就写磁盘模板 + `workflowId`。
4. **审批角色 = 根岗位 id**：审批落在 CEO 坑上而不是具体人；换 CEO 员工无需改定义。
5. **单进程计数 instanceId**：`instance-N` 由内存计数器生成，事件日志重放沿用原 id；跨进程并发启动不在范围内。
6. **专长标签是自由文本，不是受控词表**：`Employee.expertise` 接受任意标签（归一化为小写），匹配是**精确 id 比较**。因此 `typescript` 与 `ts` 是两回事；控制台对未知标签原样显示。要收敛就得引入别名表，本阶段不做——先让组织能声明，再谈规范化。
7. **专长不参与空坑升迁**：第二条路线是 person-level 的，只能扩大候选场，不能把「无人声明的座席」变成「有人」。这是有意为之：升迁表达的是**组织层级**，专长表达的是**个人能力**，混在一起会让「为什么是他」无法解释。
