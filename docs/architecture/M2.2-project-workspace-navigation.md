# M2.2 — Projects, approval gates and a collapsible shell

Status: CURRENT (implementation contract)
Depends on: M1.8, M1.9, M2.0, M2.1

## 1. Why this pass exists

M2.1 made the assignment studio and the delivery package readable, but four owner problems
remained:

1. **Unstaffed seats were invisible.** The palette only listed executable employees, so a vacant
   position could not be dragged onto a step and routed to hiring.
2. **A drop wrote intent immediately.** Dragging a person onto a node staged an override with no
   gate in the place the operator was looking. The inspector is the right place for that decision.
3. **The center was a scroll box.** A tall workflow forced scrollbar hunting; the Network page
   already had the better gesture (drag to pan, wheel to zoom).
4. **Drafts and deliverables hid the organization.** A draft read as a vertical list, not a
   company structure, and Deliverables rendered one card per task instead of one block per
   project with contributor rows.

This is still a presentation pass. No command, event, endpoint or persistence changed:

```
Workflow.InstanceAssignmentOverride  (whole batch, fail-closed)
Workflow.ConfirmStart                 (draft → running)
Workflow.Approve / Workflow.Reject    (existing approval gate)
```

The kernel continues to re-check employment, required roles and authority at commit time.

## 2. Assignment studio (M2.2)

### 2.1 Pure projection additions

`apps/web/src/assignment-canvas.ts` now also exposes:

- `parseAssignmentApproval(value)` and `AssignmentInstance.approval`: the workflow read model's
  `{ stepId, status, requiredCount, grantedBy }`, or `null`.
- `parseAssignmentEmployees(employees, positions, departments?)`: employees carry
  `departmentId`/`departmentName` (employee row first, position fallback).
- `parseAssignmentSeats(positions, employees, departments?)`: every seat in the chart, staffed or
  vacant. Offboarded holders keep their audit `positionId` but do not staff the seat.
- `groupEmployeesByDepartment` / `groupSeatsByDepartment`: the palette and structure header
  input, with staffed/vacant tally per department.

### 2.2 Left palette

The palette lists **open seats first**, grouped by department, then the executable roster grouped
by the same departments. Both cards are draggable:

- an employee payload is the employee id (`text/plain`);
- a seat payload is `seat:<positionId>`.

Tapping a card selects it; tapping a pending node then opens the same gate as a drop.

## 3. The approval gate in the inspector

A drop or a node activation never stages an override directly. It opens a gate bound to the
selected step:

- **Employee gate** — names the proposed teammate, role, department, capability and any SoD
  warning. *Approve & stage* puts the pin in the local staging map; the footer/modal still owns
  the commit.
- **Vacant-seat gate** — explains that the kernel can only pin an employee. It offers the roster
  (capability matches first) and a route to **Open hiring**; staging the chosen teammate is the
  only assignment action.
- **Workflow gate** — when the instance already reports an open approval, the same inspector shows
  `granted/required` and calls the existing `Workflow.Approve` / `Workflow.Reject` commands.
  An approval releases the console hold, exactly like the Approvals page.

The gate itself writes nothing. Every gate card repeats the kernel re-check sentence so the
operator cannot mistake a local approval for a committed event.

## 4. Pan / zoom viewport

`.assignment-viewport` replaces the scrolling center:

- pointer drag pans (`--pan-x` / `--pan-y`), native non-passive wheel zooms (`--zoom`);
- a 3 px movement threshold suppresses the node click that would otherwise fire after a pan;
- toolbar provides − / + / **Fit** / **Reset view**;
- pointer capture ends on up/cancel/leave, and `touch-action: none` keeps touch drags on the
  canvas.

Node state changes only when the operator activates a node (click, Enter or Space), never while
panning.

## 5. Company structure on the board

The board header prints one chip per department with `staffed/total` and the open count. Draft
instances get a tinted variant, so the plan is read against the company it will run in.

## 6. Deliverables: projects, not task cards

`apps/web/src/delivery-package.ts` adds:

- `deliveryProjects(tasks, workflows)`: one project per workflow instance (or one per standalone
  task), with step-ordered tasks, contributor grouping, anchor task for the delivery page,
  workflow gate state and the three workspace states (`needAction`, `running`, `completed`).
- `DeliveryProjectTask` keeps `stepId`, `stepTitle`, contributor/position ids and status, so the
  page can answer *who did what* without another fetch.
- Tasks whose workflow row is missing from a poll are kept as an orphan project under their
  instance id instead of disappearing.

`apps/web/src/pages/Deliverables.tsx` renders one block per project:

```
Project title · state · progress
[delivered] [contributors] [workflow steps]
Who did what
  Contributor  →  step · task · status · open / delete
```

The filter tabs now count projects, not tasks.

## 7. Collapsible shell

`apps/web/src/App.tsx` persists `maoeh.sidebar.collapsed` in `localStorage`. On desktop the
collapsed rail keeps icons (with `title`/`aria-label`), hides copy, and gives the page the extra
width. The toggle is hidden below 701 px, where the existing drawer/scrim behaviour owns the
sidebar; a persisted collapse never changes the mobile drawer width.

## 9. Known limits

- The graph still infers a linear order from `steps`; branch transitions remain a definition-level
  read-model gap (same as M2.1).
- A vacant-seat gate stages an existing employee acting in the open seat; it does not create the
  position's employee. Hiring remains the `Agents` page / hire-gate workflow.
- The project block intentionally does not fetch result payloads; it opens the existing delivery
  route, which owns package assembly and previews.
- Sidebar collapse is a shell preference, not per-company state.

## 10. Revisit triggers

- The definition exposes transitions: the studio becomes a real DAG editor.
- Assignment overrides need a first-class gate event instead of local staging.
- Deliverables needs server-side project summaries for very large task sets.
- The shell needs more than one navigation density (for example, a compact tablet rail).
