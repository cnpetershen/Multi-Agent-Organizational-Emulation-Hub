# M2.4 — 多 Agent 协作韧性 + 文档双语交付

## 目标

让一条公司任务书能稳定走完：

```text
Work.SubmitBrief
  → CEO 拆成工作流草稿
  → 人确认草稿（改派画布）
  → 需求 / 实现 / 测试 / 审批
  → 最终交付物
```

中间不能因为 LLM 计划的参数形状、一次失败、一次重试或文档语言而卡死；文档类最终交付物必须能中英文互看。

## 审计发现的真实卡点

### 1. 多阶段任务书被拆成独立任务

CEO 对 `brief-17` 连续三次使用 `DispatchWork`，生成 `task-35/36/37` 三个 `workflowInstanceId = null` 的独立任务。画布只承载工作流实例，所以画布永远不会出现这些任务。

修复：

- `packages/agent-cognition/src/prompts/cognition.ts` 明确：多能力/多阶段任务书必须 `CreateProposal`，只有真正单一原子任务才用一次 `DispatchWork`。
- 当前 `brief-17` 用 `CreateProposal` 重拆为 `instance-13`（Product Requirement → Implementation → Testing → Approval），已完整跑通。

### 2. 计划执行器只接受一种参数形状

真实 LLM 输出过：

- `ProduceArtifact` 用 `contentOutline` / `sections` / `description`，没有 `content`；
- `SubmitReport` 只有 `data`，没有 `summary`；
- `ProgressReport` 用 `message`，没有 `summary`。

旧执行器一律 `invalid_args`，任务停在 `accepted` / `started`。

修复（`apps/kernel/src/simulation/plan-executor.ts`）：

- 大纲/章节/描述会物化为交付内容；
- `SubmitReport` 的摘要从 `data` 的键派生；
- `ProgressReport` 的 `message` 可以作为摘要。

### 2b. 执行人把自己当经理，重复派工 → permission_denied

`instance-14` 的 Implementation（`task-44`）被指派给 Agent Engineer，但它计划先 `AcceptTask` 再 `DispatchWork` 给 `engineer` 席位；执行人被 A1/A2 权限门拒绝，任务停在 `accepted`。同样的计划在重试时还反复 `StartTask`，触发 `invalid_transition`。

修复：

- 提示词明确：收到 `Task.Assigned` / `Task.Started` 时执行人是“执行者”，必须 `StartTask → ProduceArtifact/SubmitReport`，不能 `DispatchWork` / `CreateProposal`；
- `StartTask` 在 `assigned` 状态自动先 `AcceptTask`，不再要求模型记住两条命令；
- `AcceptTask` / `StartTask` 对已推进状态是幂等 no-op，`SubmitReport` 对已完成任务也是 no-op；
- `permission_denied` 进入有界重试。

### 2c. 一个僵尸任务占住座位

`task-15` 长期停在 `submitted`，QA 的 `currentTaskId` 仍是它；新工作流的 Testing 任务无法获得 QA。清掉这个旧任务后，Testing 才被唤醒。

这不是新工作流的错误，但它是“多 Agent 看起来卡住”的真实来源：**座位被历史任务占用**。任务页和运行时应该把“已提交但未关闭”的旧任务清出。

### 3. 一次计划失败就被标记已处理，不再重试

`packages/agent-runtime/src/cycle.ts` 只把网络/额度错误视为可重试；`invalid_args` / `invalid_transition` 一次失败就永久标记 processed，任务再也不会被唤醒。

修复：把这两类计划错误加入有界重试。调度器仍按 `maxRetries` 截断，不会无限循环。

### 3b. 交付文字冒充 `index.html`

真实记录里，Implementation 的 `index.html` 值只有一句 “Self-contained runnable cyber sandbox…” 也通过了确定性验证（验证只检查 key 是否存在）。页面于是把一句描述当成可运行页面。

修复：

- `SubmitReport`/`ProduceArtifact` 的 `data` 中出现 `.html` key 时，值必须以 `<!doctype html` 或 `<html` 开头；否则 `invalid_args` 并重试。
- 旧的三条占位任务（`task-48`/`49`/`50`）已删除。

### 3c. 页面显示的是工作流，不是用户要的沙盘

`instance-14` 的交付是需求/设计/实现报告/测试/推广文档，页面因此看起来像“关于工作流的文档”，而不是“沙盘环境”。

修复：

- `apps/web/public/sandbox.html`（**已归档 2026-11-14**：归档至 `docs/competition/legacy/sandbox-manual.html`，不再由 Web 提供；真实会话引擎见 `/api/sandbox`）曾提供人工推演页：角色切换、陈述/质询/答辩/裁决、localStorage、结束评分与 JSON 导出；
- `Results` 对“沙盘/对抗质询/cyber-sandbox”项目在**交付包之前**嵌入该运行时（现已指向 `/api/sandbox`），并提供全屏打开；
- 工作流与文档仍然保留在下方，作为过程记录，而不是产品本身。

### 4. 文档被归成报告，双语入口不出现

文档只在 `result.data['*.md']` 里、不在 `artifacts` 时，交付类型曾是“报告”，`DocumentPreview` 不渲染。

修复（`apps/web/src/results.ts`）：

- delivered file 中有 `.md/.markdown/.txt/.html` 时归为 document（HTML 若带脚本仍是 code/game/3D，优先）。

### 5. 文档只有一种语言

新增：

- `POST /api/translate`（`apps/api/src/translation.ts`）：服务端调用同一个 OpenAI-compatible provider，保留 Markdown 结构；没有 provider 返回 `501`，不伪造译文。
- `DocumentPreview` 自动识别源语言：
  - 中文文档 → English 按钮翻译；
  - 英文文档 → 中文按钮翻译；
  - 可切回原文；
  - 显示“机器翻译，保留 Markdown 结构”。
- 最终交付物区域与交付包里的文档共用同一个双语组件。

## 从“解析错”到“可验收”的契约

1. **步骤契约**：`generateWorkflowDefinition` 为每个能力生成 `CAPABILITY_HANDOFF`，写清该步必须交什么（实现必须是代码/页面/服务，测试必须对真实 artifact 出证据）。它作为任务 `detail` 随事件传给执行人，不替换任务的完整 mandate。
2. **实现契约**：`capability === 'implementation'` 的提交必须含代码文件 key 或 `artifacts`；只有 `implementation_report` 会被判 `invalid_args` 并重试。
3. **HTML 契约**：`index.html` 的值必须是真实 HTML 文档，不能是一句描述。
4. **幂等状态**：`StartTask` 在 `assigned` 状态自动 accept；Accept/Start/Submit 对已推进状态是 no-op，避免重试把成功任务再次打回 `invalid_transition`。
5. **角色契约**：`Task.Assigned` 是被指派步骤，执行人不得再 `DispatchWork`；权限拒绝进入有界重试。
6. **产品页面**：沙盘类交付在 Results 页先给可运行运行时，工作流文档只作为过程记录。

## 边界

- 翻译是**机器翻译**，长文档可能被 provider 的 max tokens 截断；原文始终保留，可随时切回。
- 重试是**有界**的：同一个计划形态连续失败会在 `maxRetries` 后停止，不会用重试掩盖真正的坏交付。
- 任务书是否生成工作流仍由 CEO 判断；单原子任务合法地留在任务队列，不强行塞进画布。

## 五件交付可信事项

1. **新链路验收**：game / product 两条 acceptance 走真实认知、真实 workflow、真实 capability 路由，并要求人工 gate 后才完成。
2. **机器可读契约**：生成的 `WorkflowStep` 带 `acceptanceCriteria` 与 `requiredArtifacts`；实现步骤必须交 runnable-code-or-page。
3. **artifact 门禁**：implementation 任务提交必须含代码文件 key 或 artifacts；workflow 在 implementation 完成时再审计一次，缺 artifact 不能进入 Testing。
4. **人工最终 gate**：生成的审批步骤 `humanOnly: true`；ControlActor 不是 human 时返回 `human_approval_required`，Agent 不能自批。
5. **回归测试**：workflow-generation-contract 覆盖契约字段与 humanOnly；acceptance 覆盖“先 blocked、人工批准、再完成”；implementation 报告不能再绿。
