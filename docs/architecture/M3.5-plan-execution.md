## 0. 审计结论（先查再写）

已有能力：

- `GET /api/plans/:id/confirmed` 已有确认方案读取；
- M3.3 draft 实例 + `context.planning`；
- workflow-engine 的 start / stage / confirm / wait / resume / override；

- Agent 调度器通过 tick + 事件唤醒真实 Agent；

缺失（本轮补齐）：

1. confirmed plan → workflow definition 的**忠实翻译**（不是重新规划）；

未新建：第二套 workflow engine、TaskSystem、事件总线、调度器。

## 1. 从 confirmed plan 启动

### 1.1 启动前校验

`POST /api/plans/:id/start`：

- `baseVersion` 必须是当前版本；
- 当前版本必须已 confirmed；
- 用实时组织重新跑 M3.4 `validatePlan`，有 blocking → `422 plan_invalid`；
- 必须有 approval node（M3.6 交接）；
- 同一 plan + planVersion 已有 execution → 直接返回原 execution（幂等，不重复建任务）。

### 1.2 方案到 workflow 的忠实映射

`execution-plan-workflow.ts`：

- **一个 confirmed node = 一个 stage / step**，按 plan 的拓扑 `order[]`；
- task 名称 = plan node title；负责人 = plan node employee；输入/输出/验收写入 step description、requiredArtifacts、acceptanceCriteria；
- approval node = human-only approval step，roles = 组织 root positions；
- task completed → 下一 stage；rejected → fail；approval granted → 下一 stage/complete；denied → fail；
- 生成的 definition 只使用 plan 数据，不调用能力解析、不重新选员工、不改节点。

> 这不是“重新生成方案”。M3.4 confirmed plan 是唯一输入；翻译只把每个已确认节点映射成既有引擎的 step。M3.3 的 capability-generated draft **不被改写**，作为来源记录在执行上下文中。

### 1.3 执行实例

- 新实例 id：`execution-${planId}-v${planVersion}`；
- workflow definition 存 `simulation.definitions`，`context.executionPlan` 带完整 plan snapshot；
- 通过既有 `workflow.start` 启动，引擎在 entry stage 创建第一个真实 Task；
- `startedBy` 记录人类 operator（`ceo-alex`），actor 使用该员工的 identity；
- 事件由 API 注入事件日志（引擎只返回事件，caller 落库）；
- 执行记录写入 `planning.json` 的 `executions`。

### 1.4 恢复

`regenerateWorkflowDefinition` 新增 `executionPlan` 分支：重启后从 started event 的 plan snapshot 重建完全相同的 definition，不依赖易失 store，也不回退到 M3.3 能力图。

## 2. 真实任务与调度

| 需求 | 实现 |
| --- | --- |
| 节点→Task | 引擎 `enterStage` 用 plan step 创建 Task |
| 负责人一致 | step 使用 `kind:'employee'`；引擎修复为直接把任务分配给该员工，不再二次按 position 解析 |
| DAG 依赖 | plan 已拓扑排序；引擎一次进入一个 stage，前置完成才创建后续 task |
| 只有可执行任务进入调度 | TaskSystem 的 create/assign/accept/start 链路；Engine 不伪造完成 |
| 真实 Agent | 既有 tick + scheduler 唤醒员工；模型输出经 TaskSystem 提交 |
| 不并行破坏 | 遵循现有串行 stage 推进 |

### 2.1 状态

TaskSystem 现有状态原样透出：`created / assigned / accepted / started / blocked / submitted / completed / rejected / cancelled`。

执行状态由真实 workflow instance + tasks 派生：

`not_started / running / awaiting_approval / paused / completed / failed / cancelled`。

- 失败来自真实 `Task.rejected` / workflow aborted；不伪造 failed task；
- 重试遵循现有 TaskSystem / workflow 规则（本阶段 plan step `maxAttempts:1`）；
- 暂停/恢复/取消继续使用既有 workflow/task/control 命令，不另造状态机；
- 重复 start 返回同一 execution，不重复创建 task。

## 3. 执行读取 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/plans/:id/start` | `{baseVersion}`；幂等启动 confirmed plan |
| GET | `/api/executions` | 当前公司执行列表 |
| GET | `/api/executions/:id` | 执行详情：真实任务状态、负责人、结果、artifacts、审批门 |

`ExecutionView` 包含 plan/version、workflow instance、startedBy/At、任务数组、summary（完成/失败/活跃/全部完成/artifacts）、approval（open/granted/denied）。

**交付物**：优先 `Task.result.artifacts`；若 Agent 把文件写在 `result.data` 的文件键/`files[]` 中，则从真实 data 派生；不生成占位文件。

## 4. 剧场与协作协议

- 所有事件来自引擎/TaskSystem：`Task.Created → Task.Assigned → Task.Started → Task.ProgressReported → Task.Completed`、`Workflow.StepEntered`、`Workflow.ApprovalRequested`；
- correlationId / trace / seq 保留；
- 员工状态随真实事件变化；
- Theater 只读，不参与执行控制；
- 不使用模拟消息填充剧场。

---

## 5. 审批交接

- plan 的 approval node 被翻译成 human-only approval step；
- 所有必需 task completed 后，引擎进入 approval stage，产生真实 `Workflow.ApprovalRequested`；
- execution 状态变为 `awaiting_approval`，`approval.status='open'`；
- M3.5 **不批准**、不推广、不发布；
- M3.6 读取：

```http
GET /api/executions/:id
GET /api/workflows
```

并消费 execution 的 `approval` / `tasks` / artifacts / plan version。

## 6. UI

方案画布（M3.4）新增执行区：

- confirmed plan 展示执行摘要（方案版本、任务/员工、最终交付物）；

- 启动后轮询 `/executions/:id`，显示真实任务状态、负责人、尝试次数、交付摘要、artifacts；

- 未确认、已有 execution 或验证阻塞时不能启动；
- 方案确认后内容仍不可变；执行不修改 plan。

## 8. 已知边界

1. **串行 stage**：plan DAG 已拓扑排序，引擎仍按现有机制一次一个 stage；真正的并行调度不在本阶段。
2. **一个 plan 版本一个 execution**：幂等；要重新执行需新的 confirmed 版本（或后续显式运行版本机制）。
3. **无暂停/取消按钮**：继续使用既有 control/task 命令；M3.5 只读展示真实状态。
4. **失败重试**：沿用现有 `maxAttempts:1`；没有在 plan 中新增重试策略。
5. **approval 只打开，不决定**：M3.6 负责审批、推广、发布。
6. **execution 记录是启动索引**：运行状态实时从 workflow instance + TaskStore 派生，不在文件里复制一份易漂移的状态。
7. **M3.3 draft 实例不被启动/改写**：M3.5 用 confirmed plan 生成新的执行实例；source draft id 保留在执行记录里以便追溯。
