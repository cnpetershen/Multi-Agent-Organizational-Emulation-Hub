## 0. 结论先行

M3.3 只完成业务主线的第一步和第二步，并把结果交给 M3.4：

```text
用户业务目标 / 真实沙盘会话
  → 结构化需求方案 vN（草稿 / 待澄清 / 已确认）
      · 用户原话逐字保留
      · 其余字段一律标为 AI 推断
      · 阻塞问题未回答时不可确认
  → 智能体编排草案（真实员工、能力、依赖、输入输出、验收）
      · 能力无席位 → 明确报告，不静默分配
  → 现有 workflow-engine 的画布草案实例（awaitConfirmation）
      · 只产生 Workflow.* 事件；不产生任何 Task.*
      · M3.4 在改派画布读取、调整、由人确认后，才允许进入任务实施
```

**本阶段没有启动任何正式任务。** 编排成功时创建的是 `Workflow.InstanceStarted` 草稿实例（`context.draft = true`），不含 task；画布上显示「草案 / 草稿 / 等待确认」。

## 1. 需求沙盘

### 1.1 三个真实来源

| 来源 | 行为 | 不做什么 |
| --- | --- | --- |
| **live** | 一次真实模型调用（`responseFormat: json`），严格 zod schema；未知字段留空并生成澄清问题 | 不把推测写成用户需求；失败就报错 |
| **sandbox** | 复用现有 `赛博沙盘` 会话：`buildSandboxBriefDraft` 把真实 transcript / 评分转成需求字段 | 不重新开一场沙盘，不二次编造 |
| **deterministic** | 无模型（mock/测试）时：只保留用户目标原话，用既有能力词表从用户自己的话中识别能力，其余全部变成澄清问题 | 不补任何业务事实 |

### 1.2 结构化契约

`RequirementPlan`（见 `planning-types.ts`）包含：

- `source.goal`：用户原话（逐字，trim only）；
- `title / background / audience / constraints / scope{in,out}`；
- `deliverables[]`、`acceptanceCriteria[]`、`risks[{risk, mitigation, severity}]`；
- `requiredCapabilities[]`（来自既有能力词表或用户填写）；
- `clarifications[{id, question, why, blocking, answer, status}]`；
- `gaps[{area, detail, blocking}]`；
- `provenance{mode, provider, model, stated, inferred}`——**stated 永远只有 `source.goal`**；其余字段即使为空也列入 inferred，UI 明确标注「AI 建议/推导」；
- `status: draft | needs_clarification | confirmed`；
- `version / createdAt / updatedAt / confirmedAt / confirmedBy`。

状态判定：

- 任一 blocking clarification 仍 open 且无答案；或
- 交付物、验收标准、所需能力任一为空；
→ `needs_clarification`，不能确认、不能编排。

确认时：

1. 回答阻塞问题；
2. 显式 `acknowledgeInferred: true`（UI 的确认按钮就是这一步）；
3. 生成**新版本**，`status = confirmed`；已确认版本不可变，后续编辑生成新的 draft 版本。

### 1.3 版本机制

- 文件存储 `stateDir/planning/planning.json`（原子 tmp+rename），按公司隔离；
- `RequirementRecord { requirementId, companyId, currentVersion, versions[] }`；
- 每次保存/确认都追加版本，`version` 单调递增；
- 更新必须带 `baseVersion`，旧版本 → `409 version_conflict`；
- 需求列表与详情 API 返回版本历史；页面可切换历史版本（只读）。

### 1.4 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/requirements/analyze` | `{goal}` 或 `{sourceSessionId}` → 需求 v1 |
| GET | `/api/requirements` | 当前公司需求摘要列表 |
| GET | `/api/requirements/:id` | 需求 + 全部版本 |
| PUT | `/api/requirements/:id` | `{baseVersion, patch}` → 新版本 |
| POST | `/api/requirements/:id/confirm` | `{version, answers, acknowledgeInferred}` → 已确认版本 |

## 2. 智能体编排

`orchestrator.ts` 是纯函数：已确认需求 + 真实 `Organization` → 编排草案。**不调用模型、不虚构员工**。

### 2.1 员工选择

1. 对每个 capability 调用 `resolveCapabilityAssignments(organization, [capability])`；
2. 取该 seat 上真实且可雇佣的员工（`isExecutableEmployment`）；
3. 无 seat 或无员工 → `missingCapabilities` + `unassigned`，草案 `blocked`；
4. 同一员工承担多个节点 → `resource_contention`（warning，执行顺序串行化）；
5. 绝不把能力缺失的任务分配给不匹配的员工。

### 2.2 节点与依赖

节点类型：`task` + 一个 `approval`（人类门）。每个 task 节点包含：

`nodeId / title / capability / employeeId / positionId / inputs[] / outputs[] / acceptance[] / dependsOn[] / order / status`。

能力排序（拓扑）：`product_requirement → technical_design → implementation/frontend/backend → testing → marketing → release → approval`；依赖由能力类别显式建立，Kahn 拓扑排序得到 `order`，出现环则 `dependency_cycle` 阻塞。

输入/输出/验收：

- 输入 = 依赖节点的输出；第一个节点 = `已确认需求 vN`；
- 输出按能力类型（设计文档、可运行交付物、验收报告、推广计划、发布包…）；
- 验收 = 能力契约 + 需求自身的 `acceptanceCriteria`。

### 2.3 冲突与阻塞

| code | 含义 |
| --- | --- |
| `missing_capability` | 能力无可用席位/员工 |
| `unassigned_task` | 节点无负责人 |
| `resource_contention` | 同一员工承担多个节点（warning） |
| `missing_deliverable` / `missing_acceptance` | 需求不完整（正常应在确认前拦截） |
| `dependency_cycle` | 依赖成环 |
| `workflow_draft_failed` | 引擎拒绝创建草案 |
| `assignment_override_failed` | 草案已创建但固定负责人失败（warning；画布按席位解析） |

`status = ready` 必须同时满足：需求已确认、无 blocking conflict、无 missing capability、无 unassigned。

### 2.4 草案实例（交给 M3.4）

ready 时调用现有 `simulation.workflow.start({ capabilities, awaitConfirmation: true, context.planning })`：

- 生成/保存 `WorkflowDefinition`，创建 `Workflow.InstanceStarted` 与分配事件，并**手动 append 到事件日志**（引擎只返回事件，由调用方负责落库）；
- `context.planning` 携带：`requirementId / requirementVersion / orchestrationId / orchestrationVersion / capabilities / nodes` 摘要；
- 引擎的 draft 路径**不进入 entry stage**，因此不创建 task；
- 通过 `workflow.overrideAssignments` 把编排选中的员工固定到 `step-1…step-N`（失败仅 warning，不阻塞草案）；
- 编排记录保存 `workflowInstanceId / workflowId / workflowVersion`，M3.4 用现有 `/api/workflows` 与改派画布读取。

### 2.5 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/orchestrations` | `{requirementId, version}` → ready/blocked 草案；ready 时创建画布草案实例 |
| GET | `/api/orchestrations` | 当前公司编排草案列表 |
| GET | `/api/orchestrations/:id` | 单个草案（含节点/依赖/冲突/实例链接） |

## 6. 已知边界

1. **需求方案存文件而非事件**：规划事实是版本化文档；只有「画布草案实例」进入事件日志。这是有意的：草稿阶段不应污染组织事实。若未来需要需求审计事件，应新增领域事件，而不是把文件搬成假事件。
2. **编排是确定性的**：员工选择只读真实席位/能力；未使用模型“建议”员工。模型只参与需求理解。
3. **执行是串行的**：草案节点按拓扑顺序进入引擎阶段，不支持并行分支；真实依赖已记录在 `dependsOn`，M3.4 可按需调整。
4. **live 模型质量**：需求分析依赖 DeepSeek 的 JSON 输出；schema 校验失败会直接报错，不降级伪造。
5. **无认证**：沿用本机单租户（M1.5）；规划 API 按当前公司作用域读写。
6. **沙盘来源**：需要已有且至少 2 条发言的沙盘会话；否则明确 `sandbox_not_ready`。
