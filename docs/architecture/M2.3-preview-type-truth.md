# M2.3 — Preview type truth and the full chain

Status: CURRENT (correctness pass)
Depends on: M1.4, M1.6, M1.8, M1.9, M2.0, M2.1, M2.2

## 1. The failure

A real, playable `index.html` delivery was classified as a **document** on the delivery page.
The cause was in `deliverableKind`:

- the delivery carries `artifacts: ['index.html']`;
- `DOCUMENT_FILE` includes `.html`;
- the code/document/report classifier therefore returned `document` before anyone asked whether
  the page was a game.

The package could still show a game slot, but the page below it rendered a document sheet and the
"Final deliverable" block spoke in document language. The same problem existed for a CSS 3D
product tour: `index.html` was a document, and the 3D scene was only visible if you knew to open
the preview. This is the exact "明明是游戏却呈现文档 / 游戏不能试玩" report.

## 2. The fix: ask for the artifact's meaning before its extension

Two pure classifiers now live outside the page:

### `apps/web/src/playable.ts`

`isPlayableGame(task, files)` returns true when:

- the delivery declares `playable: true` / `game: true` and ships an HTML entry;
- the task title names a known game (catches SVG tic-tac-toe with no `<canvas>`);
- an HTML page has a canvas plus a loop/key handler;
- an SVG page has a script plus a click/key handler.

A chart dashboard and a static HTML page still return false.

### `apps/web/src/spatial.ts`

`isSpatialDelivery(files)` returns true for:

- a `.obj`/`.stl`/`.glb`/`.gltf`/`.fbx`/`.ply` model file;
- an HTML page containing three.js/WebGL/model-viewer markers;
- a CSS `preserve-3d` / `perspective` / `rotateX|Y` / `translateZ` product tour.

It is shared by `results.ts` and `delivery-package.ts`, which removes the old circular dependency
between `results` and `document-preview`.

### `deliverableKind(result, task?)`

The optional task lets the classifier ask the two questions first:

```
game → 3d → code → document → report
```

`game` and `3d` are now first-class `DeliverableKind` values with their own labels and final
deliverable blocks. A `game`/`3d` delivery no longer falls into `DocumentPreview`:

- `documentPreviewOf` refuses a playable game or a spatial delivery before looking at Markdown;
- `DeliveryPackage` classifies the same task as `game`/`3d` and renders the correct slot;
- the Network delivery theatre labels a 3D card as `3D scene`.

File-shaped data keys now recognize model extensions, so a `{ "scene/product.obj": "..." }`
delivery is downloadable and previewable as a model rather than silently disappearing.

A second cause was the **project card anchor**. `deliveryProjects` opened the first completed
task, which is usually the requirement/design document. The multi-step `一鱼多吃` project
therefore opened `task-30` (Product Requirement) — a page with no preview — instead of
`task-32` (Implementation). `previewAnchor` now prefers an implementation/frontend/3D task over
documents and QA, while keeping workflow order for ties. A project card now opens
`/results/task-32`, whose preview serves the actual dashboard `200` with title
`一鱼多吃 · 多模态内容看板`.

Two more causes surfaced when the owner still saw a blank region:

- **Duplicate project titles.** The early `res-brief-1` run (1/2, a 445-byte placeholder) and the
  real `instance-12` run (5/5) rendered as two identical project cards. `deliveryProjects` now
  keeps one block per normalized title and chooses the richer run. The demo company's obsolete
  `res-brief-1` workflow was then deleted entirely, so the old "Implementation / 1 step" page can
  no longer be reached by mistake.
- **Stale failed state.** An API restart reaps detached previews; the panel then inherited
  `failed` and only auto-started from `stopped`. The hook now retries a stale `failed` state once
  (two capped attempts, then stop). After a stop/start the project card's preview frame carries
  the dashboard title and all four cards. The runtime now writes the detached child's output to
  `.maoeh/preview/<task>/preview.log` and includes the tail in `logs`, so a future `code 1` names
  its cause instead of only its exit code.
- **Cross-host iframe.** The runtime reports `127.0.0.1`; a console opened at `localhost` embedded
  a cross-host frame. `previewFrameUrl` keeps the port/path and swaps the host to the console's
  hostname, and the panel offers an explicit "open in a new tab" link as the escape hatch for
  browsers that still refuse the frame.

## 3. The chain, end to end

The live demo now contains a real, completed chain:

```
Work.SubmitBrief
  → CEO decomposes into 5 capability steps
  → draft on the assignment canvas (open seats, human review, gate)
  → Workflow.ConfirmStart
  → Product Requirement / Technical Design / Implementation / Testing
  → approval gate granted
  → delivery package: 3D product tour + documents + test report
```

workflow steps. `task-27` delivers a self-contained `index.html` 3D product tour plus README and
design note; `task-28` is the QA report.

## 5. Known limits

- A full-page headless screenshot sometimes does not paint a cross-origin preview iframe; the
  iframe is verified with the frame-level preview e2e and by opening the preview URL directly.
- 3D classification is a heuristic over file text. A 3D page that only uses WebGL without any of
  the markers above still runs through the preview, but the package may label it code until a
  stronger signal is delivered.
- Binary `.glb`/`.gltf` is listed and downloadable, not parsed into a wireframe.
- The browser package ZIP is store-only; large packages should move server-side later.

## 6. Revisit triggers

- A new artifact family (audio, video, PDF, spreadsheet) needs its own classifier and preview.
- Preview frames need a first-class "content type" from the runtime instead of browser-side
  inference — that would make this module unnecessary.
- The chain needs a resume-after-failure path for a preview whose detached process exits; the
  panel already offers restart, but the runtime's reaper policy should be reviewed separately.
