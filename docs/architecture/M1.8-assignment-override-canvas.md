# M1.8 · 编排画布与「实例级一次性改派」（Assignment Override）

> 状态：已接受（2026 · M1.8，与 ADR-015 一致）
> 关联：ADR-003（LLM 只提议）、ADR-005（事件溯源 + CQRS）、ADR-014（DispatchWork）、M1.6（capability 工作流）

## 目标

CEO 依据 capability 目标生成流程定义并启动实例之后，人类在**激活前**（至少在 step 未
进入之前）把流程里某个 task step 的执行席位改派给指定员工，并能在提交前**先看 diff、
再确认**。确认即一条 ControlPlane 命令，确定性校验、事件落盘、可回放、可审计。

## 决策

1. **一次性覆盖（per-instance），不写回 definition**。override 以事件写入该实例的
   事件流，折叠进 `WorkflowInstance.context.assignmentOverrides`（`{ [stepId]: employeeId }`）。
   definition 与其他进行中的实例不受影响。
2. **LLM 不参与**（ADR-003）。整个流程 callCount = 0；人类提交者必须带 ActorContext
   （`ceo-alex`，与控制台其他命令一致）。
3. **原子批量**：`Workflow.InstanceAssignmentOverride` 一次携带 N 条 override；全部
   校验通过才提交；任意一条失败 → 命令拒绝，不产生任何事件（fail-closed）。
4. **只允许改未激活的 task step**：step 已进入（active / done / rejected）或非 `task`
   类 step 一律拒绝。`approval` step 的执行人由 approval 策略与 `requiredRoles`
   决定，不存在「改派」语义，不在此命令范围内。
5. **override 在 step 真正激活（`enterStep`）时消费**，解析顺序为：
   1. definition 里该 step 若本身是 `assignment.kind === 'employee'` → 按 definition 固定；
   2. `context.assignmentOverrides[stepId]` 存在且该员工存在且为可执行雇佣状态
      （`isExecutableEmployment`）→ 派给该员工（task 创建为 `{kind:'employee'}`）；
   3. 否则回落到原有 capability / position 解析逻辑。
   回落时 override 条目保留在 log 与 context 中（审计可见），但不生效 —— 这是
   「员工在确认与激活之间被归档」的确定性处理，不静默丢弃用户决定。
6. **二次确认 = 先 diff 后整体提交**。确认弹窗展示：变更摘要（N 步换人）、每条
   override 的硬校验结果（员工存在 / 雇佣状态 / `requiredRoles` 命中的
   `position.id|key|roleCode` / `requiredAuthority` domain×level 阈值）、影响范围
   文案（仅本实例）、可选理由（逐条，进入事件 context）。任一硬校验失败 → 确认按钮
   禁用。UI 校验只是体验层；内核（engine `overrideAssignments`）再校验一遍，
   内核为安全边界。
7. **SoD（职责分离）不在本命令里静态判定**，仍由既有的 gate（`gate()` 的 permission /
   authority / assignment check）与审批路径 `requiredRoles` 在运行时强制执行。
   画布只做**提示性警告**（「该员工也是前置步骤的执行人」），不作为硬闸门 —— 静态
   无法判定「这一步在验证哪一步的产物」。
8. **审计**：`execute()` 追加 `Control.WorkflowInstanceAssignmentOverridden`
   （`{ ...controlEnvelope, instanceId, overrides: [{stepId, employeeId, previousEmployeeId, reason}] }`）。
   engine 侧每个真实变更另落 `Workflow.StepAssignmentOverridden`（workflow 聚合，
   进 `WORKFLOW_EVENT_TYPES`，fold 消费）。两个聚合各司其职：Control 聚合回答
   「谁、何时、为什么」，Workflow 聚合回答「这个实例的上下文现在是什么」。
9. **expectedVersion**：`instance.processedEventIds.length`，与 `Workflow.*` 其他
   命令一致；并发改派需客户端传入，冲突返回 `STALE_VERSION`。
10. **幂等**：`commandId` + `fingerprintOf` 兜底；no-op（override 与当前值相同）
    仍计 accepted，但不产生事件。

## 事件与 fold 契约

新增 workflow 聚合事件：

```
Workflow.StepAssignmentOverridden
  { instanceId, stepId, employeeId, actorId, previousEmployeeId: string | null, reason: string | null }
```

fold：`context.assignmentOverrides` 以 `{...existing, [stepId]: employeeId}` 合并；
`buildInitial` 不处理该事件（实例创建时不存在）；`replayWorkflowInstance` 自然恢复。
删除后又 override 的语义不存在（删除事件之后 fold 已返回 `null`，事件被忽略）。

## 验收（现有使用不受影响）

1. `pnpm build` / `pnpm typecheck` / `pnpm lint` / `pnpm test` 全绿（仅新增测试）。
2. console 现有页面零行为变更；`/api/snapshot`、`/api/workflows` 等响应形状不变。
3. 新增单测覆盖：fold 回放 override、engine 校验路径（未知 step / 已激活 / 非 task /
   未知员工 / 归档员工 / requiredRoles 不命中 / requiredAuthority 不足 / 批量原子性 /
   no-op）、control 命令路径（accepted / STALE_VERSION / 校验失败拒绝）。
4. 回放验收：删除 projection，replay event log，`assignmentOverrides` 恢复一致。

## 复审触发条件

- override 需要写回 definition 或影响其他实例（说明 per-instance 语义失效）；
- 需要一等公民的 SoD 静态检查（引入「步骤产物 → 验证者」关系建模）；
- override 数量成为度量「生成质量」的输入（那时应改 capability 映射，见 ADR-015 备注）；
- 出现激活中 step 改派的真实需求（需重新引入 task 级 reassign 语义，并重新论证 gate）。
