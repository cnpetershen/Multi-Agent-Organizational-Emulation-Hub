# M3.6 — 人工审批与交付物审核

> **地位**：M3.6 实现契约（从属 `ARCHITECTURE-BASELINE.md` / `package-registry.md` / `dependency-graph.md`）。
> **前序**：[M3.5 任务实施](./M3.5-plan-execution.md) · [M3.4 方案确认](./M3.4-plan-canvas-confirmation.md) · [M3.2 Theater](./M3.2-collaboration-theater.md)。

## 0. 审计结论

可直接复用：

- M3.5 `GET /api/executions/:id` 的任务、负责人、`Task.result`、artifacts、approval 状态；
- workflow-engine 的 approval stage 与 `Workflow.ApprovalRequested`；
- `workflow.approve({decision:'granted'|'denied', humanApproval:true})`；
- TaskSystem 的已完成任务与真实交付；
- M3.1 事件、M3.2 Theater 只读展示；
- 既有 Results 页面查看单个 task 的完整交付。

确实缺失并本轮补齐：

1. execution 级审批记录（审批人、时间、动作、意见、前后状态、关联任务/交付物）；
2. 服务端审批校验、幂等/并发保护、审批历史；
3. 交付审批工作台（真实交付内容预览、验收对照、三条决定）；
4. 审批通过后给 M3.7 的明确读取入口。

没有新建审批引擎/事件总线；审批仍由既有 workflow approval gate 推进。

---

## 1. 数据模型

`ExecutionApprovalRecord`（planning store `approvals`）：

```text
approvalId, companyId, executionId, planId, planVersion, workflowInstanceId
approvalKey, approvalStepId
action: approve | reject | request_changes
reason, decidedBy, decidedAt
taskIds[], artifacts[]
before/after: { executionStatus, approvalStatus, workflowStatus }
```

审批记录是**追加式**、不可覆盖。plan/execution 原始版本不变。

`ExecutionReviewView`：

- `execution`：M3.5 ExecutionView（真实 tasks/results/artifacts）；
- `plan`：该 execution 对应的 confirmed plan 版本（含节点目标/输入/输出/验收）；
- `history`：该 execution 的审批记录。

## 2. 审批 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/execution-approvals` | `{ pending, history, approved }` |
| GET | `/api/execution-approvals/:executionId` | 审核详情：execution + plan + history |
| POST | `/api/execution-approvals/:executionId/decide` | `{action, reason?, approvalKey?}` |

### 2.1 服务端校验

- execution 必须存在；
- 当前 status 必须是 `awaiting_approval`；
- workflow approval 必须 open；
- 所有 plan task 节点必须 completed，且有非空 `Task.result` 与至少一个真实 artifact；
- `reject` / `request_changes` 必须有书面原因；
- 审批 actor 必须是人类 operator（employee seat）；
- 可选 `approvalKey` 必须与当前 gate 一致（stale 保护）。

### 2.2 三条路径

| action | engine | 结果 |
| --- | --- | --- |
| `approve` | `approve({decision:'granted', humanApproval:true})` | approval granted → workflow completed；execution completed |
| `reject` | `approve({decision:'denied', humanApproval:true})` | approval denied → workflow failed/aborted；execution failed |
| `request_changes` | `approve({decision:'denied', ...})` | 与 reject 同一引擎拒绝门，但审批记录 action 不同、原因作为返工意见；execution failed；不进入 approved |

`request_changes` 不是批准，也不会进入 M3.7。记录 `taskIds`、`artifacts`、原因，供返工时关联原任务/原交付物；修改后的方案由人类在 M3.4 重新确认，再由 M3.5 新 execution 执行（M3.6 不自动开任务）。

### 2.3 幂等与并发

- 同一 execution 已有审批记录：
  - 相同 action → 返回原 decision（idempotent 200）；
  - 不同 action → `409 approval_already_decided`；
- gate 已关闭/尚未打开 → `409 approval_not_open`；
- 并发请求：engine 的 open-gate 检查与审批记录保证只有一个 decision 落库；测试用 `Promise.all` 验证只有一条 history。

## 3. 工作台

`DeliveryApproval` 页面（导航：交付审批）：

- 待审批 execution 列表；
- 详情：
  - plan 版本、确认人、execution 状态；
  - 每个 task 的真实负责人、状态、尝试次数；
  - plan 节点目标、输入、输出、验收标准；
  - Agent 真实提交的 summary 与 artifacts；
  - artifact 内联内容预览（来自 `Task.result.data` 的真实文件/文本）；可打开完整 Results；
  - 失败记录；
  - 审批历史与 before→after 状态；
- 决定表单：批准 / 驳回 / 要求修改；驳回与返工必须填写原因；
- 批准后展示 approved 结果、关联 artifact 数与状态 transition。

审批动作只有服务端校验通过才生效；前端按钮不是安全边界。此外，generic `Workflow.Approve` / `Workflow.Reject` 控制命令对带 `context.executionPlan` 的执行实例会被拒绝，避免绕过工作台和审批记录；旧 `Approvals` 页面也不再列出执行交付闸门。

---

## 4. Theater 与事件

- 审批请求：`Workflow.ApprovalRequested`；
- 批准：`Workflow.ApprovalGranted`；
- 驳回/返工：`Workflow.ApprovalDenied`；
- 审批历史记录不是伪造 Agent 消息；Theater 只读真实事件；
- 事件保留 correlationId / seq / trace。

---

## 5. M3.7 交接

只接受 **approved** 记录：

```http
GET /api/execution-approvals
```

`approved[]` 中每条记录包含：

- `executionId`
- `planId / planVersion`
- `approvalId`
- `decidedBy / decidedAt`
- `artifacts[]`
- `before / after` 状态
- `taskIds[]`

详细成果可继续读：

```http
GET /api/execution-approvals/:executionId
GET /api/executions/:executionId
```

未 approved 的 execution（pending/rejected/request_changes）没有 approved 记录，M3.7 不得推广。

## 7. 已知边界

1. `request_changes` 使用现有引擎 denied 分支（gate 只有 granted/denied）；返工由人类回到 M3.4 调整方案、再经 M3.5 新 execution 执行。M3.6 不自动创建返工任务。
2. 单租户、单人类 operator；不做多级企业权限。
3. 审批记录保存在 planning store；workflow/task 事实仍在事件日志。
4. 不自动批准、不推广、不发布。
5. 审批记录在 engine 成功后写入；极端进程崩溃窗口仍需以事件日志和后续对账处理（当前单进程/本地文件边界）。
