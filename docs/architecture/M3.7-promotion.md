# M3.7 — 推广策略与推广方案管理

> **地位**：M3.7 实现契约（从属 `ARCHITECTURE-BASELINE.md` / `package-registry.md` / `dependency-graph.md`）。
> **前序**：[M3.6 交付审批](./M3.6-delivery-approval.md) · [M3.5 任务实施](./M3.5-plan-execution.md) · [M3.2 Theater](./M3.2-collaboration-theater.md)。
> **代码**：`apps/api/src/promotion-strategist.ts` / `planning-types.ts` / `planning-store.ts` / `planning-service.ts` / `api-adapter.ts`；`apps/web/src/promotion.ts` / `pages/Promotion.tsx` / `promotion.css`。

## 0. 审计结论

可直接复用：

- M3.6 `GET /api/execution-approvals` 的 approved 记录（executionId、planId/version、approvalId、批准人/时间、artifacts、before/after）；
- M3.6 `GET /api/execution-approvals/:executionId` 的真实 execution/plan/任务/交付物；
- M3.5 execution、Task.result、artifacts；
- 现有 LLM gateway（策略建议，带 live/mock provenance）；
- 真实组织中的 marketing / testing 员工能力（Jack / Peter）；
- M3.1 事件、M3.2 Theater 的只读组织视图；
- 现有 Results、PlanCanvas、导航、i18n。

确实缺失并本轮补齐：

1. 从 approved execution 派生推广方案；
2. 推广策略、渠道、材料、贡献者与来源追踪；
3. 推广方案 draft/confirmed 版本、baseVersion 乐观锁、不可覆盖历史；
4. 人工编辑、确认人/时间/摘要；
5. M3.8 confirmed 交接接口；
6. 推广工作台。

未新建审批引擎、工作流引擎、事件总线或第二套推广执行链。

---

## 1. 数据模型

`PromotionPlan`（planning store `promotions`，追加式版本）：

```text
promotionId, version, status: draft | confirmed
executionId, planId, planVersion, approvalId
approvedAt, approvedBy, sourceTitle
title, goal, valueProposition
audience[], audienceNeeds[], coreMessages[]
channels[{channelId,name,reason,contentType}]
materials[{materialId,type,platform,title,body,source,sourceArtifact}]
schedule[], metrics[], risks[]
contributors[{employeeId,name,role,capability,basis:'capability'}]
provenance{mode,provider,model,approvedArtifacts[],aiFields[],humanEdits[]}
summary{materialCount,channelCount,artifactCount}, summaryText
createdAt/updatedAt, confirmedAt/By, confirmationNote
```

- 原 approved execution/approval/plan 不修改。
- 每个版本保留；UI 可查看历史。
- 已确认版本不可覆盖；编辑派生新 draft。

---

## 2. 来源校验

`POST /api/promotions { executionId }` 只接受：

- M3.6 `ExecutionApprovalRecord.action === 'approve'`；
- 执行完成（`completed`，或 approval record 的 `after.executionStatus === 'completed'`，用于事件日志未持久化但审批事实已持久化的恢复场景）；
- 有真实 artifacts；
- 对应 plan/version 存在。

pending/rejected/request_changes 的 execution 一律 422 `promotion_invalid`。

---

## 3. 策略与材料

- `promotion-strategist.ts` 通过既有 LLM gateway 生成结构化建议；prompt 明确禁止编造用户反馈、市场数据、合作关系、推广效果和发布记录。
- 无 live 模型时用确定性 fallback（从 approved title/goal/deliverables/audience/artifacts 推导），不增加市场事实。
- 模型返回空字段时仅用同一 approved evidence 的确定性建议补齐；不填入市场数字。
- 推广材料由 approved strategy + approved artifact 名单确定性组装：项目介绍、核心卖点、宣传标题、小红书/抖音/B站/公众号版本。**刻意不调用内容工作室生成营销叙事**，避免把顺滑但无来源的用户反馈/业绩写进已确认方案。
- `provenance` 区分 live/mock、provider/model、approvedArtifacts、aiFields、humanEdits；UI 标注 AI 草稿/人工修改。
- contributors 按真实组织能力匹配（marketing→Jack，testing→Peter），标记 `basis:'capability'`；这不是 Agent 任务执行，UI 明确说明。

---

## 4. 版本与人工确认

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/promotions` | 方案摘要列表 |
| POST | `/api/promotions` | 从 approved execution 创建 v1 draft（同 execution 幂等） |
| GET | `/api/promotions/:id` | 版本记录 |
| PUT | `/api/promotions/:id` | `{baseVersion, patch}`；派生新 draft |
| POST | `/api/promotions/:id/confirm` | `{baseVersion, note?}`；生成 confirmed 版本 |
| GET | `/api/promotions/:id/confirmed` | M3.8 交接；只有 confirmed |

- `baseVersion` 不匹配 → 409。
- 确认校验：title/goal/value/audience/coreMessages/channels/materials 非空，每个 material 有正文；来源 approval 仍为 approve。
- 确认记录 `confirmedBy`（人类 operator）、`confirmedAt`、`confirmationNote`、`summaryText`。
- 确认不改变 execution/approval/plan，不发布、不调用外部平台、不写 published 字段。

---

## 5. 工作台

`Promotion` 页面：

- 左栏仅 M3.6 approved execution；
- 展示 plan/execution/approval 来源、真实 artifacts 预览与 Results 入口；
- 推广策略字段编辑；
- 渠道编辑；
- 材料编辑（AI 草稿/人工修改标记）；
- 保存新草稿、确认、版本历史；
- 确认后展示 confirmedBy/At、摘要与 M3.8 handoff 状态；
- 明确提示确认不等于发布。

---

## 6. M3.8 契约

```http
GET /api/promotions/:id/confirmed
```

返回 confirmed `PromotionPlan` 加上 `promotionVersion`：

```text
promotionId, promotionVersion, executionId
planId, planVersion, approvalId
goal, valueProposition, audience, audienceNeeds, coreMessages
channels[], materials[]
schedule[], metrics[], risks[], summaryText
confirmedBy, confirmedAt
```

未确认方案返回 404；M3.8 不需要重新生成内容。

## 7. Theater 与边界

- 推广方案由**工具**生成，不创建 Agent 任务，因此不存在推广 Task/Workflow/AgentMessage 事实；工作台明确标注贡献者是能力匹配，不是已执行任务。
- M3.9 追加真实 `Document.PromotionGenerated`（新方案 v1 落库后）与 `Document.PromotionConfirmed`（人工确认新版本后）事件，Theater 归类为 promotion；payload 含 execution/plan/approval 版本、provenanceMode、humanEdits，不含伪造员工执行。
- 不伪造推广任务、员工执行或发布记录。
- Theater 继续展示真实的 M3.6 审批事件与现有组织事件；若未来通过 M3.5 执行 marketing 能力任务，Theater 的 capability→promotion 映射会自动归类。
- 本轮不为了“剧场热闹”生成虚假推广 Task 事件。

## 9. 已知边界

1. 不自动发布、不调用社交平台、不写发布记录。
2. 贡献者为真实能力匹配，但没有创建 Agent 促销任务；不声称员工已执行。
3. 材料为证据摘要式渠道版本，营销表现需人工编辑/补充；不编造市场数据。
4. 单租户单 operator；不做多级推广审批。
5. 推广方案存 planning store；event log 仍记录审批/执行事实。
