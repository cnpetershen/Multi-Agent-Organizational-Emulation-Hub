# M3.1 — 统一协作事件协议

> **地位**：M3.1 实现契约（从属 `ARCHITECTURE-BASELINE.md`、`package-registry.md`、`dependency-graph.md`）。
> **配套**：M3.0 遗留核查见 [`../competition/M3_0_LEGACY_AUDIT.md`](../competition/M3_0_LEGACY_AUDIT.md)。
> **代码**：`packages/organization-control/src/collaboration/`、`packages/task-system/src/task-{types,events,service,fold}.ts`、`packages/agent-communication/src/`、`apps/kernel/src/simulation/`。

---

## 0. 结论先行

M3.1 建立的不是第二套事件系统，而是**既有事件日志之上的统一协作语义层**：

1. 十一种协作类型全部有裁定：7 类复用既有事件（已实现），4 类保留为未来引擎的契约（未实现、不发假事件）。
2. 消息可追踪 `sent → delivered → processed/failed`，发送与处理都可幂等。
3. 任务交接是一条真实的双向链：`Task.HandoffRequested → Accepted|Declined → Task.Assigned → …终态 → Task.HandoffCompleted`，接收方真的执行并交付。
4. 协作过程可按 `session / task / workflow / agent / causation` 追溯，断链会被显式报告而不是被猜平。
5. 没有破坏 M2 的状态机、审批门和事件溯源；新增字段全部可选，旧日志原样重放。

未做（刻意）：决策/冲突事件没有发射器；协作剧场 UI 属于后续模块。理由见 §8。

## 1. 设计裁定

| 问题 | 裁定 | 理由 |
| --- | --- | --- |
| 是否新建协作事件总线？ | **否** | 所有协作事实已经是（或将是）同一份 append-only 日志上的领域事件。新建总线会产生第二个真相源。 |
| 十一种类型是否都要新事件？ | **否，先复用** | 消息、任务指派/接受/进度/交付、审批在 M0–M2 已有语义；只有交接链与「消息已处理」是真实缺口。 |
| 追溯字段是否强制填满？ | **否，按适用性** | `Task.Accepted` 是执行者自身行为，没有接收方；硬填一个 `receiverAgentId` 才是假数据。 |
| 投影能否写日志？ | **否** | trace / lifecycle / audit 都是纯读模型；读一次不产生任何事实。 |
| 保留类型能否先发空事件占位？ | **否** | 这正是 M3 禁止的「看起来在协作」。保留类型只声明类型名、聚合与归属，等真实引擎实现。 |

### 2.1 已实现类型的 Schema

每个已实现类型都注册在事件注册表（`registerTaskEvents` / `registerCommunicationEvents` / `registerWorkflowEvents`）里，payload 由 zod 校验，未注册事件写不进日志。

- `Communication.MessageSent`：`messageId, channelId, senderId, recipientIds[], subject, body, messageType, dedupeKey?`
- `Communication.MessageProcessed`（M3.1 新增）：`messageId, channelId, recipientId, outcome: handled|failed`
- `Task.HandoffRequested`（新增）：`handoffId, taskId, fromEmployeeId, toEmployeeId, fromStatus, reason, note, title?, goal?, requiredOutputKeys?, capability?`
- `Task.HandoffAccepted`（新增）：`handoffId, taskId, fromEmployeeId, toEmployeeId, previousStatus`
- `Task.HandoffDeclined`（新增）：`handoffId, taskId, fromEmployeeId, toEmployeeId, reason`
- `Task.HandoffCompleted`（新增）：`handoffId, taskId, fromEmployeeId, toEmployeeId, outcome, summary, resultSummary, artifactCount`

`Task.ProgressReported` 的 `phase` 只有 `progress | submitted | reviewed`（`task-events.ts`），因此一个类型承载两种协作语义是安全的：投影按 phase 分流。

#### M3.9 可观测性事件

为避免新增第 15/16 个 EVENT_AGGREGATES 破坏既有 14 聚合协议，M3.9 复用已登记的 `Document` 聚合：

| 事件 | Payload |
| --- | --- |
| `Document.RequirementAnalyzed` | `requirementId, version, title, sourceKind, analysisMode, inferredFieldCount, analyzedAt` |
| `Document.RequirementConfirmed` | `requirementId, version, title, confirmedBy, confirmedAt, inferredAcknowledged` |
| `Document.PromotionGenerated` | `promotionId, version, title, executionId, planId, planVersion, approvalId, generatedAt, provenanceMode, materialCount, channelCount` |
| `Document.PromotionConfirmed` | `promotionId, version, title, executionId, planId, planVersion, approvalId, confirmedBy, confirmedAt, humanEdits[]` |

事件只在业务操作成功落库后写入；无历史回填。详细设计见 `M3.9-observability-events.md`。

### 2.2 保留类型为什么不发事件

`DecisionProposed / DecisionAccepted / ConflictDetected / ConflictResolved` 的归属引擎（`packages/decision-engine`、`packages/escalation-engine`）目前都是空脚手架（`export {};`）。如果现在给它们编一个 payload schema 并发射，日志里会出现没有真实推理、没有参与方、没有决策规则的「协作」，正是本阶段明令禁止的假协作。因此协议只声明**类型名、聚合、归属包、追溯适用范围**，状态为 `reserved`；架构测试同时钉住：

- implemented 类型必须在事件注册表中存在；
- reserved 类型必须**没有**注册事件（防止偷偷发 schema-less 事实）。

等 M3.2 引入真实协商/冲突处理时，由归属包定义 payload schema、注册事件、并把状态改为 implemented；协议表不用改形状。

## 3. 追溯字段

### 3.1 信封字段（`OrgEvent`）

事实本身已经携带：`eventId, seq, companyId, type, version, occurredAtSim, occurredAtWall, actorKind, actorId, subjectType, subjectId, payload, causationId, correlationId, traceId`。

### 3.2 协议字段映射

| 协议字段 | 来源 | 说明 |
| --- | --- | --- |
| `sessionId` | `OrgEvent.correlationId` | MAOEH 没有独立 session 聚合；一次任务书 / 一次沙盘会话 / 一次操作员指令就是一条 `correlationId`。协议按产品语义称它为 session，投影时从信封读取，不复制字段。 |
| `correlationId` | `OrgEvent.correlationId` | 同一事实的原始 id。 |
| `workflowInstanceId` | `payload.instanceId`（Workflow.\*）或 `Task.Created.workflowInstanceId`（Task.\*） | 任务类事件本身不携带 instance；`buildCollaborationTrace` 从同一日志的 `Task.Created` 解析，解析不到就是 `null`，绝不猜。 |
| `taskId` | `payload.taskId` | 任务类与交接类事件都有。 |
| `senderAgentId` | `actorId`，或 payload 的 `senderId` / `fromEmployeeId` / `employeeId` / `requestedBy` | 谁发起了这个事实。系统 actor（如 `kernel-reactor`）保留真实 actor，不伪装成 AI 员工。 |
| `receiverAgentId` | `recipientIds[]` / `toEmployeeId` / `assignment.assigneeEmployeeId` | 只有真正被指向谁才填；`Task.Accepted` 这类自身行为为空。 |
| `timestamp` | `occurredAtSim`（业务时钟）+ `occurredAtWall`（墙钟） | 业务判断用 sim 时钟；审计保留墙钟。 |
| `payload` | `OrgEvent.payload` | 领域原始 payload，不做二次编码。 |
| `causationId` | `OrgEvent.causationId` | 直接原因事件 id；没有原因（领域根）就是 `null`。 |

### 3.3 每类事件的适用性

`CollaborationTraceApplicability` 明确声明哪些字段**适用**，避免「为了好看」强制填充：

| 类型 | session | workflow | task | sender | receiver | causation |
| --- | --- | --- | --- | --- | --- | --- |
| AgentMessage | ✓ | — | — | ✓ | ✓ | ✓ |
| TaskAssigned | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| TaskAccepted | ✓ | ✓ | ✓ | ✓ | — | ✓ |
| TaskHandoff | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| ProgressReported | ✓ | ✓ | ✓ | ✓ | — | ✓ |
| DeliverableSubmitted | ✓ | ✓ | ✓ | ✓ | — | ✓ |
| ApprovalRequested | ✓ | ✓ | — | ✓ | — | ✓ |
| Decision/Conflict（保留） | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

`correlationKeys` 列出该类型额外值得索引的身份键（如 `handoffId`、`messageId`、`approvalKey`）。`Task.Assigned` 只声明它真的携带的 `taskId / attempt / assignment`。

### 3.4 断链报告

`buildCollaborationTrace` 返回 `danglingCausation[]`：某事件的 `causationId` 指向投影窗口外时，显式列出，而不是静默丢弃。调用方若故意只投影一个窗口，可传 `requireCausationInWindow: false` 表明「窗口外不是缺陷」。

## 4. 消息生命周期

三种事实，三处存放，各有职责：

| 状态 | 证据 | 性质 |
| --- | --- | --- |
| `sent` | `Communication.MessageSent` | 持久领域事实 |
| `delivered` | 通信服务的投递账本（由 `MessageSent` 重建） | 运行时读模型；投递进收件箱不是组织状态变化，因此不发事件 |
| `processed` | `Communication.MessageProcessed`（`outcome=handled`） | 持久事实；每个收件人一条（`failed` 被 `handled` 升级时会有第二条，投影以 `handled` 为准） |
| `failed` | 同一事件的 `outcome=failed` | 真实的终态：该轮不可重试且失败 |

规则：

1. **幂等发送**：`sendMessage` 的 `dedupeKey` 以「发送者 + key」为索引；重复发送返回原消息、原事件、`duplicate: true`，不追加第二条 `MessageSent`。索引在重启时从日志重建，所以重启后的重试仍能去重。
2. **幂等处理**：同一 `(messageId, recipientId)` 的相同结果不会重复记录；`failed` 可以被后续 `handled` 升级为第二条事实（重试成功才是真相），但 `handled` 永不降级。
3. **结果不可降级**：先 `failed` 后 `handled` 以 `handled` 为准（重试成功才是真相）；`handled` 不会被后来的 `failed` 覆盖。
4. **只有真实收件人能被标记处理**：服务校验收件人确在该消息的 `recipientIds` 中。
5. **处理发生在轮次结算之后**：`run-tick` 只有在没有待重试时才写 `MessageProcessed`；可重试失败保持 `delivered`，由调度器重试，避免把「正在重试」误报成「已失败」。

读面：`ControlQuery.getMessageLifecycle()` → `GET /api/collaboration/messages`（`{ messages: [...] }`）。

## 5. 任务交接链

### 5.1 状态与顺序

```text
Task.HandoffRequested            （发送者：现任执行者或任务创建者）
  ├─ Task.HandoffDeclined        （接收者拒绝，附理由；任务留在发送者手里）
  └─ Task.HandoffAccepted        （接收者接受）
       └─ Task.Assigned          cause = HandoffAccepted（执行权真正转移）
            └─ …提交/交付…
                 └─ Task.HandoffCompleted   cause = 任务终态事件
```

- 接受事件与重新指派事件**成对**出现：`HandoffAccepted` 是决定，`Task.Assigned` 是转移，后者的 `causationId` 指向前者。这样「谁同意了、什么时候真正换手」在日志里是两件可分别审计的事实。
- 交接结束时写 `Task.HandoffCompleted`，`outcome ∈ {completed, failed, rejected, cancelled, reassigned}`，`resultSummary` 携带交付结果摘要，`artifactCount` 携带交付物数量。
- 任务 id 全程不变，结果仍挂在同一个任务上；`attempt` 保留（换手不是重试）。

### 5.2 领域规则（全部经真实 `TaskService` 校验）

| 规则 | 行为 |
| --- | --- |
| 谁可以发起 | 当前执行者或任务创建者；其余人 `not_task_owner` |
| 接收者 | 必须是真实员工且 `isExecutableEmployment`，不能是自己或当前执行者 |
| 任务状态 | 仅 `created/assigned/accepted/started/blocked` 允许（`ALLOWED_TASK_COMMANDS.handoff`）；`submitted` 及终态不允许 |
| 待处理交接 | 同一接收者重复请求 = no-op；改指他人 = `handoff_pending` |
| 接受者 | 只有被点名的接收者本人；非接收者 `handoff_not_recipient` |
| 重复接受 | 已是该接收者执行 = no-op；否则 `handoff_already_accepted` |
| 拒绝 | 必须给理由；重复拒绝 = no-op（第一次理由为准） |
| 权限 | 三个动作都走 `HandoffTask` 权限动作 + `task:<id>` 资源 |
| 结算 | 任务 completed/failed/rejected/cancelled，或被手动改派离开接收者，都会结算交接 |

### 5.3 唤醒（谁在什么时候被叫醒）

- `Task.HandoffRequested` → **接收者**被唤醒（这是它做决定的地方）。
- `Task.HandoffAccepted / Declined / Completed` → **发送者**被唤醒（结果反馈）。
- 接受后的 `Task.Assigned` → 接收者作为执行者被唤醒，开始真实执行。

这三条都在 `apps/kernel/src/simulation/eligibility.ts` 中，和既有的任务唤醒规则并列，不另建调度器。

### 5.4 交接链的读面

`GET /api/collaboration/trace` 返回按日志顺序的 `entries[]`；每条含 `kind, type, sessionId, taskId, workflowInstanceId, handoffId, senderAgentId, receiverAgentIds, causationId, phase, outcome, summary`。`collaborationTraceOfTask(trace, taskId)` 取一条交接链的全部环节。

## 6. 幂等、重试与异常记录

| 场景 | 机制 | 证据 |
| --- | --- | --- |
| 重复发消息 | `dedupeKey`（发送者 + key） | 不追加第二条 `MessageSent`，返回 `duplicate: true` |
| 重复请求同一交接 | `requestHandoff` 同接收者 no-op | 不追加第二条 `HandoffRequested` |
| 重复接受/拒绝 | `acceptHandoff` / `declineHandoff` no-op | 不追加第二条决定事件 |
| 重复消息处理 | `markProcessed` 同结果 no-op；`failed → handled` 允许升级一次 | 相同结果不重复；升级是第二条真实事实 |
| 计划失败可重试 | `run-tick` 有界重试（`maxRetries`） | `TurnResult.retryable` + 调度器 `RETRY` |
| 不可重试失败 | 轮次结算为 failed，消息写 `outcome=failed` | `Communication.MessageProcessed` |
| 任务无法推进 | 45 tick stall watchdog：`started` → `Task.Failed`，`accepted` → `Task.Rejected` | 真实任务终态事件 |
| 事件契约破坏 | 注册表校验 payload；未注册类型写不进 | `EventContractFailure` |
| 交接无人应答 | 不静默：legacy audit 的 `dangling_handoff` 报告 | `auditLegacyWork` |

失败不是「没发生」：每一种失败都留下可读事实（终态任务事件、失败的处理结果、stall 记录），而不是让状态停在 `started` 假装还在跑。

## 7. 与 M2 的兼容

1. **未改既有事件类型与 payload 形状**。`Communication.MessageSent` 只增加可选 `dedupeKey`；旧日志没有该字段，重放不受影响。
2. **新增 5 个事件类型**（4 个交接 + 1 个 `MessageProcessed`），全部注册 schema，通过注册表校验。
3. **任务折叠只增字段**：`Task.handoff`（旧任务为 `null`），不影响既有状态机、`allowedTaskCommands`、审批门与工作流结算。
4. **恢复等价**：重启后从日志重建任务（含交接）、消息、投递账本、处理标记、去重索引；集成测试验证「重启前后 trace 与 lifecycle 逐字段相等」。
5. **不新增依赖、不新增总线、不改 Kernel 分层**：协作投影在 `organization-control`（读侧），交接在 `task-system`（领域侧），唤醒在 `kernel`（运行时侧）。

## 8. 权限与组织治理

- 动作空间新增 `HandoffTask / AcceptHandoff / DeclineHandoff`（`shared-types`），认知提示明确「交接是换手，不是让别人替自己通过验收」。
- 领域层统一用 `HandoffTask` 权限动作授权（请求、接受、拒绝），资源为具体任务；没有「任何员工都能改派」的旁路。
- 接受必须由被点名者本人完成；系统不能代替员工接受。
- 人类审批门（`Workflow.ApprovalRequested`）保持不变，仍是最终批准通道；M3 没有把审批自动化掉。
- 保留类型未来需要各自的权威规则（谁能提议、谁能裁决、冲突如何升级），本阶段不预设。

2. **trace 读全公司日志**：38 个任务 / 13 万事件的现场规模可接受；更大规模需要按 session 分页或增量投影，届时保持同一字段契约。
3. **sessionId 是 correlationId 的语义别名**：没有独立 session 聚合；若未来需要「会话」实体，应从 correlation 建读模型，而不是改事件信封。
4. **协作剧场 UI 未做**：本阶段只交付真实事件与读面；UI 必须消费这些真实事件，不允许预设脚本。
5. **M2.1 Live 闭环未改动**：唯一新增的运行时路径是交接动作与消息处理标记；M2 的工作流/审批链路由全量回归测试保护。
