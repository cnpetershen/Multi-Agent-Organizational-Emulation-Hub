## 0. 结论先行

协作剧场不是一个新的聊天页，也不是开发者日志后台，而是**公司运行视图**：

```text
真实事件日志（M3.1 同一份 append-only 事实）
  → GET /api/theater/history        历史窗口 + 七阶段证明
  → GET /api/theater/stream?cursor= SSE 尾部，按 seq 续传
  → 浏览器：员工舞台 / 协作现场 / 阶段透镜 / 回放 / 暂停·继续
```

- SSE 直接读公司自己的事件日志，**没有第二条总线**；断线按 `seq` 续传，重复事件由客户端按 `seq` 去重。
- 历史回放只读同一份事件，**不重新执行任何任务**；回放展示的事件与原始事件逐字段一致。
- 七个业务阶段是**证据透镜**，不是事件分类器：一个消息、一次操作员暂停没有阶段，显示为「尚未进入业务阶段」，而不是被塞进某个还没发生的阶段。
- 暂停/继续调用真实 `Simulation.Pause` / `Simulation.Resume` 控制命令；Running / Paused 读 `snapshot.simulation.paused`，不做本地动画伪装。

## 1. SSE：一条以 seq 为游标的真实事件尾部

### 1.1 端点

```text
GET /api/theater/stream?cursor=<seq>&company=<companyId>
```

- `cursor` 是客户端已渲染的最后一条事件的 `seq`；缺省时从**最新**事件开始（不重放全量历史）。
- `Last-Event-ID` 头同样可作为游标（浏览器 `EventSource` 自动重连时使用）。
- 帧格式：

```text
retry: 3000

event: hello
data: {"companyId":"...","cursor":123,"latestSeq":456,"resync":false}

id: 457
event: theater
data: {"seq":457,"eventId":"evt-...","type":"Communication.MessageSent","occurredAtSim":...,"actorId":"...","payload":{...},"stage":null,"stageBasis":null}
```

- 每 1 秒拉取一次 `seq > cursor`（批次上限 200），15 秒心跳注释行；客户端离开即清理。
- 只过滤 `System.*`（每 tick 的时钟标记）与 `Runtime.*`（认知循环遥测）；两者仍在日志里，游标照常越过，只是不出现在剧场。

### 1.2 断线续传与重复保护

1. 客户端保存最后收到的 `seq`；断线后以 `?cursor=<seq>` 重连。
2. 服务端只发送 `seq > cursor`；边界事件即使被重复发送，客户端 `mergeTheaterEvents` 也按 `seq` 去重。
3. 游标超前（内存日志重启、或游标来自另一家公司）→ 服务端发 `event: reset` 并从最新处重新开始；客户端清空并重建。
4. 公司切换 → 服务端发 `event: reset {reason:'company_changed'}` 并结束；客户端按当前公司重连，绝不混读两家公司。

### 1.3 校验与治理

| 检查 | 行为 |
| --- | --- |
| 方法 | 非 GET → 405 |
| 游标 | `cursor=abc` / 负数 / 不安全整数 → 400，不静默从头开始 |
| 公司 | `company` 与当前运行时公司不一致 → 409，流不打开 |
| 范围 | 事件按公司 `companyId` 过滤；只读，不产生任何事件 |
| 权限 | 这是本机单租户控制台（M1.5 无登录设计）；SSE 的权限边界是**公司作用域 + 只读**，不提供跨公司读取。真正的写权限仍在 `POST /api/command` 的 Control Plane 授权。 |

## 2. 七阶段模型：只证明，不猜测

`packages/organization-control/src/collaboration/theater.ts` 是唯一裁定处：

```text
sandbox 需求沙盘 / orchestration 智能体编排 / canvas 调整画布 /
implementation 任务实施 / approval 审批 / promotion 推广 / release 发布
```

### 2.1 判定顺序

1. **事件类型本身是阶段边界**：`Control.WorkBriefed` / `Document.RequirementAnalyzed` / `Document.RequirementConfirmed` → 需求沙盘；`Workflow.DraftConfirmed` / `Workflow.StepAssignmentOverridden` / `Control.WorkflowInstanceConfirmed` / `Control.TaskReassigned` → 调整画布；`Workflow.Approval*` / `Control.WorkflowApprovalDecided` / `Control.TaskReviewRequested` → 审批；`Control.DelegationDecided` / `Control.AgentCreated` → 智能体编排；`Document.PromotionGenerated` / `Document.PromotionConfirmed` → 推广；`Document.Publication*` → 发布。
2. **本事件携带的 capability**：`marketing` / `promotion` → 推广；`release` / `deployment` → 发布；`product_requirement` → 需求沙盘；`implementation` / `testing` → 任务实施。
3. **任务已学到的阶段**：`Task.Assigned` / `Task.HandoffRequested` 上的 capability 会记入 `TheaterStageTracker`，该任务后续的 `Started` / `ProgressReported` / `Completed` 继承同一阶段。
4. **类型默认**：`Task.*` 与工作流步骤默认任务实施。
5. **无证据 → `null`**：消息、操作员暂停、未知类型保持未归类。

### 2.2 为什么不全归类

需求明确「不要将当前所有事件强行归类为某个尚未发生的业务阶段」。所以：

- 消息是两个同事的沟通，可能属于任何阶段，因此无阶段；
- `Control.SimulationPaused` 是运行控制，不是业务阶段；
- `Runtime.CycleStarted` 根本不出现在剧场；
- 只有任务自己声明了 `marketing` / `release` 等 capability 时，推广/发布才会亮起。

七个阶段因此是**可扩展的词表**：后续的需求沙盘、智能体编排、发布模块只要发出既有事件类型或声明 capability，就会自动出现在正确的阶段里，不需要改协议。

## 3. 页面：公司运作视图

`apps/web/src/pages/Theater.tsx`（`/` 控制台内的「协作剧场」页）：

| 区域 | 内容 | 数据来源 |
| --- | --- | --- |
| 顶部状态 | 实时/重连/离线、Running/Paused、暂停·继续按钮、仿真时间 | SSE 状态 + `snapshot.simulation` |
| 业务阶段 | 七个阶段 + 「尚未进入业务阶段」，计数可点击过滤 | 每事件的 `stage` |
| AI 员工 | 真实姓名、职位、部门、当前任务、空闲/暂停、最近是否行动 | `snapshot.agents/employees/tasks` + 近期事件 |
| 协作现场 | 消息（发送者→接收者、正文、已处理/失败）、交接（双方、任务、状态、结果）、任务进展、审批、工作流、任务书 | SSE / history |
| 历史回放 | 按 `correlationId` 加载一段真实会话，播放/暂停/单步/倍速，退出回实时 | `/api/theater/history?correlationId=` |

产品约束：

- 不显示 `taskId` / `handoffId` / `eventId` / `correlationId` 等技术 ID；员工显示姓名，任务显示标题，操作员显示「操作员/系统」。
- 操作员给 AI 员工的原始指令**不展示正文**（可能引用内部 id），只显示「操作员向 X 下达指令」。
- 中文/英文双语来自既有 i18n；所有阶段、卡片、回放文案都走 locale。
- 深色卡片配色沿用 Network / Assignment 的暗色体系，青色=消息、琥珀=交接、薄荷=任务、玫红=审批、紫色=工作流。

## 4. 历史回放 = 只读原始记录

1. 页面从已加载的历史中按 `correlationId` 分组，一组就是一个工作会话。
2. 点击会话 → `GET /api/theater/history?correlationId=...&limit=300`，服务端按同一条日志返回该会话的事件（含 `seq/type/actor/payload/stage`）。
3. 页面按时间逐步揭示这些事件；播放只是客户端计时器，**不调用任何运行时接口、不重新执行任务**。
4. 因为回放与实时使用同一投影（`buildTheaterEvents` + `buildFeed`），同一事件在两种模式下的卡片一致。
5. 回放期间实时 SSE 仍在后台接收；退出回放立即回到最新状态。

## 5. 与既有架构的兼容

| 约束 | 实现 |
| --- | --- |
| 复用 M3.1 协议 / trace / messages | 舞台阶段基于 `OrgEvent`；消息/交接卡片复用 M3.1 的 payload；没有新事件类型 |

| 事件游标 / 续传 / 重复 | §1.2；游标错误显式 400，超前 reset |
| 历史回放不重执行 | §4 |
| 不破坏 M2 / M3.1 | 未改任务状态机、消息生命周期、交接状态机；只新增查询与渲染 |
| 不引入依赖 | 无新依赖；前端用原生 `EventSource` |
| 不伪造 | 所有卡片来自真实 `payload`；空阶段保留未归类 |

## 7. 已知边界

1. **SSE 每连接一次全量扫描取 `latestSeq`/prime**：当前 13 万事件规模可接受；更大规模应给 `EventStore` 增加 latest-seq 索引或分页游标。
2. **history 限 200/300 条**：会话很长时回放截断为最近 N 条；UI 已标注总数，但尚未分页。
3. **阶段依赖 capability 质量**：未声明 capability 的旧任务默认任务实施；这是默认而不是猜测，页面对未归类保持诚实。
4. **无登录**：API 仍是本机单租户（M1.5 设计）；SSE 只做公司作用域校验，不做用户认证。
5. **3001 由开发 watcher 托管**：`turbo watch build dev` + `node --watch` 会在源码变更后自动重建/重启；本轮没有手工重启，但演示前如需冻结构建应先停止 watcher。
6. **七个业务模块未开发**：本阶段只做剧场与阶段关联；需求沙盘/编排/画布/推广/发布的产品页留给 M3.3。
