# 2026-10-06

## 诊断：「大多数岗位 Agent 完不成任务」（根因 + 已修 A + 待决 B/C）

**用户报障**：项目里大多岗位 agent 好像没能力完成任务。

**证据（真实日志，不是推测）**：`%LOCALAPPDATA%\maoeh\future-ai-lab\ss\events.jsonl`（700 行，公司 `ss`，
`seed: starter`，操作员 `user-test`）。任务终态：

```
task-1 [COMPLETED] who=ceo-alex
task-2 [ASSIGNED]  who=agent-engineer  assigneeEmployeeId=null
task-3 [ASSIGNED]  who=ai-engineer     assigneeEmployeeId=null
per-employee: 只有 ceo-alex 跑过 4 个 cycle
```

新增诊断工具（可复用）：`scripts/diagnose-events.mjs`（任务生命周期汇总）、`scripts/dump-events.mjs`（事件流）、
`scripts/probe-seats.mjs`（旧规划选坑复现）、`scripts/probe-routing.mjs`（能力路由实测）。

**三条根因（相互独立，都可复现）**：
- **A（已修）**：`deterministic-cognition.ts` 的 `Control.WorkBriefed` 分支**绕过能力路由**——
  `dispatchSeats()` 按「负载最低 + positionId 字典序」从**全 15 个岗位**里取两个坑，
  新建公司所有坑负载为 0 → 选到字母序最靠前的 **`agent-engineer` / `ai-engineer`（都是空坑）**，
  与真实日志逐字一致。**违反 README/AGENTS/`vocabulary.ts` 的「能力 → 岗位，永不按名字/负载」铁律**。
- **B（未修，设计决定）**：派到空坑的任务**没有解锁路径**。
  `task-service.ts:580` 允许 `assigneeEmployeeId = null`；`eligibility.ts:182`
  的 `Task.Assigned` 分支 `if (assignee === null) return []` → **不唤醒任何人**。
  工作流步进路径（`workflow-engine.ts:511`）会因空坑报 `invalid_definition` 并回滚，所以问题可见；
  而 `DispatchWork` 建的是**独立任务**（`workflowInstanceId: null`），**绕过该守卫**，
  静默停在 `assigned`——无事件、无失败、无重试、无告警。
- **C（未修，设计决定）**：`Work.SubmitBrief.verificationKeys` 是**自由文本**（例：`"多用户在线运行"`），
  旧实现把它当 `Task.verification.requiredOutputKeys`。于是交付塑形走「按名字逐键作答」，
  产出 `{"多用户在线运行": "多用户在线运行: <目标>"}`、`artifacts: []`——
  **结构上不可能**产出 `content`/`entrypoint`/`.html`。即使有人执行也"通过验收"却交出与游戏无关的一句话。

**已落地修复（A）**：`apps/api/src/deterministic-cognition.ts` 的 `WorkBriefed` 分支
改为 `requiredCapabilitiesFor(briefGoal)` → 单个 `CreateProposal{capabilities}`，
与 mandate 路径**同一条能力路由器**；删除 `dispatchSeats`/`workCatalogSeats`/`FALLBACK_DISPATCH_SEATS`/`CatalogSeat`。
实测：lab 种子 → `engineer-mike`（能干）；starter → 路由器返回空 → **不建工作流**（不再产生卡死任务）。

**改的测试**：`tests/unit/api/deterministic-cognition.test.ts` 的 work-brief 块
（5 条旧契约 → 4 条新契约）；新增 `tests/integration/starter-company-brief.test.ts`（钉死不变量：
派出去的活必须有能执行的人；自由文本验收键不得变成 `requiredOutputKeys`）。

**为什么这个缺陷长期没被发现**：`tests/acceptance/game-mandate-deliverable.test.ts` 等验收测试
全部用 **lab 种子**（有 `engineer-mike`），而用户实际用的是 **starter 公司**（只有 CEO）。
**验收测试的组织形态与真实产品形态不一致**——这是本轮最有价值的教训。

**未验证**：本环境**跑不了 vitest**（DSH 沙箱禁止 esbuild 以管道 stdio 起子进程：`spawn EPERM`，
平台限制，非配置问题）。已做：`apps/api` `tsc --noEmit` ✅、构建 ✅、dist 级实测 ✅、
新增测试文件用 `tsc -p`（bundler resolution + 路径映射）单独类型检查 ✅（唯一残留报错是
`tests/helpers/simulation-fixtures.ts:201` 的**既有** `exactOptionalPropertyTypes` 问题，不是本轮引入）。
`pnpm test` 需在普通终端执行。

**待用户裁定（B/C 路线）**：starter 公司只有 CEO，所有交付能力都挂在**下级**岗位，
`startCapabilities` 又把 actor 自己的坑（CEO）`excludeSeatIds` 排除 → 无工作流 → 什么都不会被生产。
- 路线 A：空缺即招人（绑定 `RecommendHire` → `Agent.Create`，需事件化 + 审批闸门）
- 路线 B：放开 excludeSeatIds，坑全空时由管理者亲自执行（1 行改动，但与 W3「管理层只拆解不执行」冲突）
- 路线 C：先用管理者招人，招人本身走闸门

> 附：`ACTIONS` 里的 `RecommendHire` 与 `ProduceArtifact` **都没有**绑定进
> `plan-executor.ts` 的 `PLAN_ACTION_BINDINGS` → 发出即 `unsupported_action`（同族的"空头支票"）。
