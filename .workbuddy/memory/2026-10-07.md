## 诊断：ss 账户「交付成果只有前端」，后端需求未满足（未改代码，仅查证）

**用户报障**：需求 `前端Web SPA 后端用python，后端用来记录每次排名和得分`（俄罗斯方块），
CEO 拆解 → 派活 → 交付页，但成果**只有前端**，与需求不符。

**证据（真实日志 `%LOCALAPPDATA%\maoeh\future-ai-lab\ss\events.jsonl`，947 行，seed=starter/operator=user-test）**：

1. **拆解是对的**：`Workflow.InstanceStarted res-brief-2` 的
   `capabilityPlan.capabilities = ["implementation","frontend","backend"]`（3 步）。
   `instance-1`（Board directive，已删）当时只解出 `["implementation"]`（旧词表，"后台"/"俄罗斯"没覆盖到 frontend/backend）。
2. **三步全落给同一个人**：3 个 step 的 `assigneePositionId=engineer`、`assigneeEmployeeId=engineer-hire`
   （`engineer` 坑声明 implementation+frontend+backend → 每个能力都解析到它；`frontend-engineer`/`backend-engineer` 是空坑）。
   即 **没有分工**，一名工程师串了 Implementation/Frontend/Backend 三步。
3. **三份交付物实质是同一份**：`task-4/5/6` 的 `result.data` 分别
   `{name:Implementation,entrypoint:implementation/index.html}` / `{...Frontend,frontend/index.html}` /
   `{...Backend,backend/index.html}`，`stack` 全 = `["TypeScript","HTML5","Node.js"]`，
   artifacts 只 = `<slug>/index.html` + `<slug>/README.md`。
   **把步骤名 Implementation/Frontend/Backend 归一后，三份 content 逐字节相同**（174 行）；
   `Backend` 那份 `<html>` 里是 canvas + JS 的客户端俄罗斯方块，**没有 fetch/localStorage/服务端**，
   "python" 只出现在被引用的 goal 文本里。

**根因（交付塑形按「执行者座席能力」而非「步骤能力」）**：
- `apps/api/src/deterministic-cognition.ts:749` `Control.AgentInstructed`→`Task.Assigned` 分支调
  `deliverableFor({goal,title,requiredOutputKeys,capabilities})`，**`capabilities` 来自 prompt 的
  `Position capabilities:` 行 = 执行者自己的坑标签**（文件顶部注释亦明说「generated workflows: shape the
  delivery from the executor's own seat tags」）。
- generated 工作流 step 的 `verification: null`（`workflow-generation.ts:117 taskStep`），
  所以走「按座席能力塑形」这条路。engineer 三标签都能干 → `deliveryShape` 全 = `code`
  （`SHAPE_BY_CAPABILITY`: implementation/frontend/backend 都→code，`SHAPE_PRIORITY` code 优先）；
  `stackFor` 全量叠加 → 三份 stack 一样。
- `detectGame(\`${title}\n${goal}\`)` 命中 `俄罗斯方块` → 每步都返回同一份 `gamePage(tetris,…)`
  （`apps/api/src/game-deliverables.ts`）→ 纯客户端 HTML。
- **步骤自己的能力（backend）从没进入 `Task.Assigned` payload**：payload 只有
  `title/goal/requiredOutputKeys`（实测 task-4/5/6 payload keys），`Task.Created.assignment` 也
  只有 `kind:position/positionId`。步骤能力只以**文本形式**存在于 step 名（`capabilityLabel('backend')="Backend"`）
  和工作流 context 里，交付塑形链路读不到它。

**结论**：不是拆解错了，是**执行+交付**两层没把「步骤声明的能力」当契约：
(a) 同名容量步骤被同一座席吃掉，无分工；(b) 交付形状只由执行者座席决定 → backend 步骤产出前端页；
(c) 游戏交付物无后端形态（无 python/服务端/持久化）。所以整份交付 = 一份前端 HTML 重复三遍。

**修法方向（未实施）**：
1. 把 step 的 `capability` 结构化带进 `Task.Created/Assigned`（如 `assignment.capability` 或 `requiredOutputKeys` 旁加字段），
   `deliverableFor` 按 **step capability** 而非座席能力选形状/技术栈。
2. `SHAPE_BY_CAPABILITY` 已有区分位，但 `code` 太粗——需给 `backend` 独立形态（如 `{service, language:'python', endpoints}` + `server.py` artifact），
   并让 `gamePage` 只在 **frontend** 步骤产出；后端步骤产出排名/得分服务。
3. 交付页可考虑按 workflow 聚合呈现「前端 + 后端」两件套，而不是三张几乎一样的卡。

**相关**：沿用旧诊断工具 `scripts/diagnose-events.mjs` / `dump-events.mjs`；
与 `.workbuddy/memory/2026-10-06.md` 的 C（verificationKeys 自由文本）同族——「步骤契约没被结构化传递」。

## 回归与修复：「控制台渲染失败 · Rendered more hooks than during the previous render」

**现象**：交付页 `/results/:taskId` 一打开就整页崩（`Results.tsx` 的 `useState` 报 hooks 数量不一致）。

**根因**：新加的「整套交付」面板把 `useState` / `useCallback` 写在了 `if (task === null) { … return … }`
**之后**。首次渲染（记录未到）提前返回、少跑两个 hook；记录到达后多跑两个 → React 抛错。

**修复**：把这两个 hook 移到提前返回之前（[Results.tsx](../../apps/web/src/pages/Results.tsx) 的 `ResultsPage` 顶部，附注释说明原因）。

**新增守卫**：`tests/unit/web/hook-order.test.ts` —— 静态扫描 `apps/web/src/**/*.tsx`，
断言每个组件里所有 `useXxx(` 都出现在第一个提前返回之前；并用一个「故意写坏」的合成组件证明该守卫真的会失败。

**教训（重要）**：单元测试看不见 hooks 顺序（它需要同一组件渲染两次），所以
**控制台渲染类改动必须跑一次 `node tests/e2e/console-loop.mjs`**（真 headless Chrome，含 `[6g]/[6h]` 交付页与九页巡检）。
本次修复后该 e2e 全绿；`eslint .` 0、web `tsc --noEmit` 0、`vitest run` 134 文件 / 977 测试全绿、web bundle 重出（`turbo run build`）。

## 诊断+修复：登录页「登录按钮不显示 / 公司列表暂不可用 / GET /api/ownership 500 空响应体」

**现象**：Foundry 门页上「登录」按钮消失，报「公司列表暂不可用。」；`GET /api/ownership` 返回 **HTTP 500 且响应体为空**。

**根因（两层，都已实证）**

1. **页面层**：Vite(5173) 活着、API(3001) 不在。`http-proxy` 上游连不上时的默认响应就是 **500 + 空 body**，
   所以 `api.ts` 只能渲染成「HTTP 500: 空响应体」（`api.emptyBody`）。而 `Foundry.tsx` 用
   `organizations.length > 0` 决定是否渲染登录按钮 → 读取失败时 `data === null` → 列表为空 → **按钮消失**，
   同时唯一带「重试」的面板也进不去了（死路：报错说列表不可用，却没有任何再试的入口）。

2. **API 为何不在 —— `preview-runtime.ts` 的自杀 bug（严重）**：
   `materialize()` 把 **`process.pid`（API 自己）** 写进 `.maoeh/preview/<task>/preview.pid`；
   构造函数里的 `reapOrphans()` 读到该 marker 就 `killTree(pid)`（Windows = `taskkill /T /F`）。
   而**每次切换公司都会新建一个 PreviewRuntime**（`switchCompany` → `createPreviewApi` → 构造函数）。
   ⇒ **只要存在 preview 工作目录，一次「登录/创建公司」就会让 API 杀掉自己**，Vite 却毫发无损 —— 正是本次故障的形状。
   子进程实证：marker=自身 pid（32780===32780），第二次构造 PreviewRuntime 后进程直接消失（未打印后续日志，exit 1）。
   同一 bug 的另一半：崩溃后重新拉起时 marker 指向的是**已死的旧 API**，真正的 preview 孤儿从未被杀掉（端口泄漏）。

**修复**

- `apps/api/src/preview-runtime.ts`
  - marker 改在 `spawnPreview()` 里写**子进程 pid**，`materialize()` 不再写；新增导出 `markedPid()` 决定「该杀谁」：
    正常 pid / `'self'`（本进程：不信号、也不删目录）/ `null`（marker 不可用）。
  - 顺带修 `html` 计划：生成的静态服务器现在用 `argv[2]`（交付页自身路径）作为 `/` 的入口。此前 `readinessPath:'/'`
    却固定找根 `index.html`，于是 `client/index.html` 这类交付（本平台自己的交付就是这种布局）**永远「没有应答」**。
- `apps/web/dev-proxy.ts`（新）+ `vite.config.ts`：代理 `error` 处理器以 **502 + `{error:'api_unreachable', message:'the API at … did not answer (…) — start it with pnpm dev'}`** 回答，不再留空 body。
- `apps/web/src/ownership.ts` 新增 `signInOffered()`：只有**读取成功且确实没有公司**才隐藏登录入口，loading/failed 都保留；
  `Foundry.tsx` 改用它，并把「重试」按钮补到 hero 的错误行里。

**验证**

  `probe-static-plan.mjs`（修复后：`client/index.html` → `GET /` 200 "served"；marker=预览子进程 836 ≠ 自身 28192）。

  `tests/unit/web/foundry-gate.test.ts`、`tests/unit/web/dev-proxy.test.ts`。
- 门禁：`pnpm typecheck` 53/53 绿、`pnpm lint` 0、`npx vitest run` **143 文件 / 1050 测试全绿**、web bundle 重出（内容哈希未变，说明先前那次构建已含此改动）。
