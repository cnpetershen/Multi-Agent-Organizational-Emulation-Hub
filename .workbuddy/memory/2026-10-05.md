## 修复「未出现审批闸门」——`resolveByPosition` 被离职记录遮蔽导致工作流死锁

**用户报障**：控制台 `Start Work` 后 24 步仍无闸门 →「未出现审批闸门，运行时在 24 步后已释放」。

**根因（真死锁，非用例抖动）**：`OrgGraph.resolveByPosition` 原实现 `employees.find(e => e.positionId === id)`
**取第一个记录、不看雇佣状态**。`peter-ai-lab` 真实日志里 `qa`/`cto`/`engineer` 三个坑位都是
「先一条 `offboarded`、后一条在岗」——M1.3 re-hire 的必然结果（辞退是状态变更不是删除）。
于是生成的 4 段能力工作流推进到 target=`qa` 的第 3 步时，preflight 取到已离职的 `mack`，
以 `employee "mack" has employment status "offboarded"` 失败 → `settleSubmitted(stage-3)` 回滚 →
stage-3 永远 active → 第 4 段 + `stage-approve` 永不进入 → 闸门不出现。
证据：stage-3 那个 tick 带 `partial_failure`。
**文档 `03-data-model.md` §3.2.1 早写明「解析到当前在岗员工」——是代码违反自己的契约，契约无须改。**

**修复**：
1. `org-graph.ts` `resolveByPosition` 改为**优先取可执行占坑者**，无则回退第一个记录
   （回退保留，让上报链路/控制台仍能命名坑位主人，而非把有人的坑报成空的）。
   `holders.find(e => isExecutableEmployment(e.status)) ?? holders[0] ?? null`。
2. 把散落在 4 处的「不可执行雇佣状态」（`suspended`/`transferred`/`offboarded`）收敛为
   `organization-model` `employee.ts` 的 `NON_EXECUTABLE_EMPLOYMENT_STATUSES` + `isExecutableEmployment()`，
   `task-service` / `workflow-engine` / `permission-system` 全部改引用同一实现。
   `on_leave` 刻意**不在**列表中（休假者仍占坑，只是不能接新活）。

**回归测试（先证伪后证实，改回 `holders[0]` 会如期失败）**：
- `org-graph.test.ts`：「同岗位的离职记录不遮蔽在岗者」「同岗位只有离职者时仍返回该记录」。
- `capability-start.test.ts`：「enters a stage whose seat also carries a retired holder」——
  坑位有被辞退前任时工作流仍能进入该 stage，任务落给在岗者。

**验证**：typecheck 53/53 · **test 826/112**（+3）· lint 干净 · build 33/33。
诊断用的两个临时探针测试（重放真实 18511 行事件日志）已删除。
文档记录：`docs/review/M1.6-capability-collaboration-report.md` §7。

## 诊断：「贪吃蛇测试只有一系列步骤、游戏没写出来」（未改代码，仅查证）

用户问「是不是没给各岗位 agent 赋能、能力没有叠加」。逐条查证后确认**三处真实缺口**：

1. **能力只下发"自己那一份"**：`buildCapabilityProfiles`（organization-model）从岗位派生员工能力，
   提示词（`agent-cognition/src/prompts/cognition.ts`）也确实打印 `Position capabilities: ...`；
   **但 `renderMembers` 只渲染「名字 [id]」**，manager/reports/peers/colleagues **没有岗位、没有能力**。
   `apps/kernel/src/simulation/snapshot.ts` 的 `organizationSnapshotView` 同样只给 `named(id,name)`。
   → 认知上下文里**根本不存在"组织能力总表"**，任何 agent（含 CEO）都看不到全组织能做什么。

2. **规划不读组织能力，只读目标文本**：CEO 拆解走 `requiredCapabilitiesFor`（纯关键词）。
   实测（用 dist 直接调）：`'贪吃蛇小游戏\n做一个Web 端的贪吃蛇小游戏'` → `['frontend']`（仅 1 个）；
   `'做一个贪吃蛇游戏\n用web做一个贪吃蛇小游戏demo'` → `['implementation','frontend']`。
   差别只在 **"demo"**——词表 `implementation` 有「写一个」但**没有「做一个」**。
   日志实证：`instance-5` 的 `capabilityPlan = {"capabilities":["frontend"]}` → 只 1 个执行步骤。

3. **产出动作是空头支票**：`ProduceArtifact` 在 `shared-types` 的 `ACTIONS` 里（提示词会告诉模型可用），
   但 `apps/kernel/src/simulation/plan-executor.ts` 的 `PLAN_ACTION_BINDINGS` **没有绑定它**
   → 发出即 `unsupported_action`。`packages/artifact-system`（`createInMemoryArtifactStore`）
   **只被它自己的单测引用**，从未装进运行时。且内置认知从不调用它——每个任务只 `ProgressReport`
   同一份写死的 `TASK_OUTPUT_DATA`（churn 文本）→ `result.artifacts` 恒为 `[]`。

**另外澄清**：用户看到的"4 步 / 3 CEO + 1 CTO"是老 `product-analysis` 模板的历史实例
（intake-brief→ceo、design-approach→cto、design-gate→ceo、delivery-synthesize→cto），
最新那次贪吃蛇其实路由到了 `engineer · ravi`。且"CEO 不执行具体任务"**从没写进设计**——
M1.4 §5.5 明确「允许派给自己（终裁类工作）」，所以不是"没落实"而是"没定义"。

**附带发现（同族 bug，未修）**：`organizationSnapshotView` 查 manager 用 `.find()` 取岗位第一个匹配者、
不看 status → 坑位有前任离职者时提示词会把已离职者写成 "Manager"（同 `resolveByPosition` 那类问题）。

## 落实 W1/W2/W3：能力叠加 · 真产出 · CEO 只拆解不执行（已完成，全绿）

用户选定「两个都做」+「CEO 负责拆解任务书并派发给执行 agent」。三处落地：

**W1 能力叠加**
- `vocabulary.ts`：`implementation` 补中文线索（写个/做一个/做个/制作/搭建）；新增
  `SPECIALIZATION_PARENTS`（frontend/backend → implementation）与 `withImpliedCapabilities`，
  `requiredCapabilitiesFor` 调用它 → 「做一个Web端贪吃蛇」不再只剩 `['frontend']`。
- `snapshot.ts` 的 `capabilityMapOf(organization)` + `cognition-context.ts` 的 `CapabilityOfferView`：
  提示词新增「Capabilities the company provides (capability: seats)」总表（空坑标 `(vacant)`），
  agent 这才看得到整个组织能做什么。`agent-cognition/src/index.ts` 补导出这两个类型。
- 顺手修掉上一段记录的 manager 查找 bug：改走 `isExecutableEmployment`。

**W2 真产出（不再是一份写死的 churn 常量）**
- `deterministic-cognition.ts` 重写：删 `TASK_OUTPUT_DATA`，改 `deliverableFor(...)`——
  带 `requiredOutputKeys`（模板步）= 按名字逐键作答；无契约（生成步）= 按**座席能力**塑形
  （code→`{name,stack,entrypoint,content}` 且 content 是能跑的 HTML scaffold / test / document / report）。
  全部 quote goal 并声明 `artifacts`。`CreateProposal` 的 title 改成 `proposalTitle(instruction)`
  （取指令首行），不再恒为 'Board directive'。
- `Task.Assigned` payload 携带 `title/goal/requiredOutputKeys`（task-system 的 schema + service），
  否则被唤醒的执行者只知道「有个任务」不知道「要交什么」。
- 结论：**不需要**装 `artifact-system`（那个包始终是死代码）。Web 交付页读的是
  `result.data` + `result.artifacts`（HTTP 直读 task 记录），所以修的是「执行者提交什么」。

**W3 管理层只拆解不执行**

  （连升迁回退也跳），解不出就返回 `null`（省略该 capacity）而非回退到空坑座席。
- `workflow-engine.ts` 的 `startCapabilities`：以 actor 的 `positionId` 作 `dispatcherSeatId` 排除
  → 「谁拆解，谁就不在本计划的派发名单里」。`workflow-generation.buildCapabilityPlan` 透传 options。
- 模板任务步从 `kind: position, position_id` 改成 `kind: capability, capability`（`AssignmentRule` 扩联合类型 +
  `workflow-definition-source` 解析 + `assignmentSeat()` 在进入时实时解析）。**审批门仍用 `required_roles`**
  （治理动作本由权限持有者承担）。`product-analysis` / `product-development` 两个 YAML 已改写。

**产品级验证（新增，全绿）**：`tests/acceptance/game-mandate-deliverable.test.ts` —— 用**生产认知**
